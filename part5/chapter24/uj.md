# Clean Architecture 5부 24장 정리: 부분적 경계

**완전한 아키텍처 경계(full boundary)** 를 만들기에는 비용과 노력이 많이 들기 때문에, **부분적 경계(partial boundary)**를 만들어 미래의 변경 가능성에 대비, 추후 완전한 경계로 확장할 수 있도록 미리 구조적 여지를 남겨
둔다.

---

## 1. 왜 부분적 경계가 필요한가

```text
경계를 만들 때 드는 비용
→ 인터페이스 정의
→ 데이터 구조 분리
→ 의존성 방향 관리
→ 컴포넌트 분리
→ 테스트 작성
→ 배포 구조 고려
```

그런데 어떤 경계는 당장 필요하지 않을 수도 있음

```text
아직 DB를 바꿀 계획이 없음
아직 서비스로 분리할 계획이 없음
아직 여러 팀이 나눠 개발하지 않음
아직 배포 독립성이 필요하지 않음
```

특히 XP나 애자일처럼 **지금 필요한 것만 만들자**는 관점에서는  
미래를 위해 너무 많은 경계를 미리 설계하는 것이 불필요한 설계비용으로 간주됨

그렇다고 경계를 전혀 준비하지 않으면,  
나중에 분리가 필요할 때 더 큰 비용이 들 수 있으니까

**부분적 경계**를 활용.

```text
완전한 경계
→ 비용이 큼

경계 없음
→ 나중에 위험함

부분적 경계
→ 비용을 줄이면서 미래 분리 가능성은 남김
```

---

## 2. 부분적 경계란 무엇인가

부분적 경계 : 완전한 독립성을 제공하지는 않지만,  
나중에 독립적인 경계로 발전할 수 있도록 구조를 준비해두는 방식

```text
지금 당장 필요한 만큼만 설계
+
나중에 바뀔 가능성에 대한 최소한의 대비
```

---

## 3. 부분적 경계가 필요한 상황

```text
미래에 분리될 가능성은 있음
하지만 지금 완전한 분리 비용은 부담스러움

현재는 하나의 배포 단위로 충분함
하지만 나중에 독립 배포가 필요할 수 있음

현재는 단순한 구현체 하나만 있음
하지만 나중에 여러 구현체가 생길 수 있음

아키텍처적으로 경계가 있을 것 같지만
아직 그 경계를 강하게 만들 정도의 근거는 부족함
```

> “아직 완전히 나눌 필요는 없지만, 나중에 나눌 가능성은 있는 곳”에 부분적 경계 생성

---

# 4. 부분적 경계 생성 방법 1: 단일 컴포넌트로 컴파일하고 배포하기

가장 단순한 부분적 경계는 내부적으로는 경계를 나누되,  
컴파일과 배포는 하나의 컴포넌트로 하는 방식.

```text
소스 코드 구조
→ 경계가 있음

배포 구조
→ 하나로 묶어서 배포
```

```text
하나의 배포 파일
┌──────────────────────────────┐
│ Use Case                     │
│------------------------------│
│ Interface                    │
│------------------------------│
│ Implementation               │
└──────────────────────────────┘
```

논리적으로는 분리되어 있지만,  
물리적으로는 하나의 컴포넌트로 컴파일되고 배포.

## 장점

```text
완전한 배포 분리보다 비용이 적음
코드 구조상 경계의 흔적을 남길 수 있음
나중에 분리하기 쉬움
현재는 단순한 배포 구조를 유지할 수 있음
```

## 단점

```text
실제 배포 독립성은 없음
컴파일과 배포는 여전히 함께 이루어짐
경계가 약해서 시간이 지나면 쉽게 무너질 수 있음
```

---

# 5. 부분적 경계 생성 방법 2: 전략 패턴을 이용한 경계

전략 패턴 : 변할 수 있는 알고리즘이나 세부 구현을 인터페이스 뒤로 숨기는 방식

```text
고수준 정책
→ Strategy Interface
← 저수준 구현체
```

```text
[ Use Case / Policy ]
          |
          v
[ Strategy Interface ]
          ^
          |
[ Concrete Strategy ]
```

현재는 구현체가 하나뿐이어도  
나중에 다른 구현체로 교체할 가능성이 있다면 전략 패턴으로 부분적 경계를 만들 수 있음

## 장점

```text
구현체 교체가 쉬움
테스트에서 가짜 구현체를 넣기 쉬움
고수준 정책이 구체 구현에 덜 묶임
나중에 완전한 경계로 확장 가능
```

## 단점

```text
인터페이스와 구현체가 추가되어 코드가 늘어남
실제로 구현체가 하나뿐이면 과한 설계가 될 수 있음
모든 변경 가능성에 전략 패턴을 쓰면 구조가 복잡해짐
```

---

# 6. 부분적 경계 생성 방법 3: 퍼사드 패턴을 이용한 경계

퍼사드 패턴 : 복잡한 내부 구현을 단순한 인터페이스 뒤에 숨기는 방식

```text
고수준 코드
→ Facade
→ 내부 세부 구현들
```

```text
[ Use Case / Client ]
          |
          v
[ Facade ]
          |
          v
[ 복잡한 내부 모듈들 ]
```

퍼사드는 클라이언트가 복잡한 내부 구조를 직접 알지 않게 해줌.

## 장점

```text
클라이언트 코드가 단순해짐
복잡한 세부사항을 숨길 수 있음
적은 비용으로 경계 느낌을 만들 수 있음
기존 코드에 적용하기 비교적 쉬움
```

## 단점

```text
의존성 역전이 충분하지 않을 수 있음
퍼사드 뒤의 내부 구조가 여전히 강하게 결합될 수 있음
퍼사드가 비대해질 수 있음
진짜 독립 배포나 독립 개발을 보장하지는 않음
```

---

# 7. 세 가지 접근법 비교

| 방식          | 핵심 아이디어                            | 장점                              | 단점                                    |
| ------------- | ---------------------------------------- | --------------------------------- | --------------------------------------- |
| 단일 컴포넌트 | 코드는 나누지만 하나로 컴파일/배포       | 비용이 낮고 구조를 미리 준비 가능 | 실제 배포 독립성은 없음                 |
| 전략 패턴     | 구현체를 인터페이스 뒤로 숨김            | 교체와 테스트가 쉬움              | 인터페이스 증가, 과설계 가능            |
| 퍼사드 패턴   | 복잡한 내부 구현을 단순한 입구 뒤로 숨김 | 적용이 쉽고 클라이언트가 단순해짐 | 경계가 약하고 퍼사드가 비대해질 수 있음 |

---

## 8. 부분적 경계의 공통 장점

확실한 건 완전한 경계보다 비용이 낮다는 것

```text
완전한 경계보다 설계 비용이 낮음
지금은 단순한 구조를 유지할 수 있음
나중의 변경 가능성에 대비할 수 있음
테스트 가능성을 어느 정도 확보할 수 있음
세부사항이 핵심 로직으로 바로 침투하는 것을 줄일 수 있음
```

---

## 9. 부분적 경계의 공통 단점

부분적 경계는 완전한 경계가 아니기 때문에 한계가 존재.

```text
경계가 약해서 쉽게 무너질 수 있음
팀이 규칙을 지키지 않으면 의미가 사라짐
독립 배포나 독립 개발을 완전히 보장하지 않음
나중에 완전한 경계로 바꿀 때 추가 비용이 필요함
과하게 사용하면 불필요한 복잡성이 생김
```

완전한 경계보다 싸지만, 사전 설계 과정에서 드는 비용과 노력은 비슷함.

---

# 10. 아키텍트의 역할

**경계의 강도를 판단**

```text
지금 완전한 경계가 필요한가?
아직은 부분적 경계로 충분한가?
아예 경계를 만들지 않아도 되는가?
나중에 변경 가능성이 얼마나 큰가?
지금 경계를 만드는 비용이 나중의 변경 비용보다 작은가?
```

```text
현재 개발 속도
미래 변경 가능성
분리 비용
테스트 가능성
배포 독립성
팀의 규모와 작업 방식
```

> 아키텍트의 역할은 경계를 만들지 말지의 문제가 아니라, 지금 필요한 만큼의 경계 강도를 선택하는 것.

```text
경계 없음
→ 지금은 빠르지만 나중에 위험할 수 있음

부분적 경계
→ 비용을 줄이면서 미래 분리 가능성을 남김

완전한 경계
→ 독립성은 크지만 초기 비용이 큼
```

아키텍처 판단은 항상 균형의 문제

```text
너무 이른 완전한 경계
→ 과설계

너무 늦은 경계
→ 변경 비용 폭증

적절한 부분적 경계
→ 현재 비용과 미래 위험 사이의 절충
```
