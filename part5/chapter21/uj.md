# Clean Architecture 5부 21장 정리: 소리치는 아키텍처

> 좋은 아키텍처는 “이 시스템이 어떤 기술로 만들어졌는가”보다 “이 시스템이 무엇을 하는가”가 먼저 드러나야 함

---

## 1. 소리치는 아키텍처?!

=> 시스템 구조만 봐도 그 시스템이 무엇을 하는지 알 수 있는 아키텍처

```text
Bad Example
→ 이 시스템은 Spring 앱이다
→ 이 시스템은 Rails 앱이다
→ 이 시스템은 웹 앱이다

Good Example
→ 이 시스템은 주문을 처리한다
→ 이 시스템은 대출을 심사한다
→ 이 시스템은 회원 관리를 한다
```

> 아키텍처는 프레임워크 중심이 아니라 시스템의 목적과 유스케이스 중심이어야 함

---

## 2. 좋은 아키텍처는 유스케이스가 중심

```text
유스케이스
→ 사용자가 시스템을 통해 달성하려는 목적
→ 시스템이 수행해야 하는 주요 업무 흐름
→ 애플리케이션이 제공하는 핵심 기능
```

따라서 좋은 아키텍처는 다음 질문에 답할 수 있어야 한다.

```text
이 시스템은 무엇을 하는가?
어떤 업무 흐름을 처리하는가?
어떤 유스케이스가 핵심인가?
```

폴더 구조나 패키지 구조도 가능하면 유스케이스가 드러나도록 설계하면 좋음

```text
나쁜 방향
→ controllers
→ models
→ views
→ repositories

좋은 방향
→ CreateOrder
→ CancelOrder
→ RegisterMember
→ ApproveLoan
```

기술별 폴더가 완전히 없어야 한다는 뜻은 아님.
그런데 시스템의 중심이 기술 폴더가 되어서는 안 된다는 뜻.

---

## 3. 웹은 아키텍처가 아니라 전달 메커니즘

```text
웹
→ 입력을 받는 방식
→ 출력을 전달하는 방식
→ 시스템과 사용자를 연결하는 전달 메커니즘
```

웹 자체가 시스템의 핵심은 아님!!!

ex) 주문 취소 기능

```text
사용자가 주문 취소를 요청한다
주문 상태를 확인한다
취소 가능 여부를 판단한다
주문 상태를 변경한다
결과를 반환한다
```

=> 이 유스케이스는 웹으로 실행될 수도 있고, 모바일 앱으로 실행될 수도 있고, CLI나 내부 배치 작업으로 실행될 수도 있음.

> 웹은 유스케이스를 전달하는 수단이지, 아키텍처의 중심이 아님 주의.

---

## 4. 프레임워크도 중심이 되면 안 됨

프레임워크가 중심이 되버리면, 이 시스템이 무엇을 하는지보다, 특정 프레임워크 스타일의 애플리케이션만 보임.

좋은 구조에서는 프레임워크 여부가 중요하지 않음.

```text
중심
→ 유스케이스
→ 업무 규칙

바깥
→ 웹 프레임워크
→ DB 프레임워크
→ UI
```

---

## 5. 프레임워크 없이 유스케이스 테스트가 가능하다는 말(책)

```text
아키텍처가 유스케이스를 최우선으로 하고,
프레임워크와 적당한 거리를 둔다면,
프레임워크가 준비되지 않아도 유스케이스 단위 테스트가 가능해야 한다.
```

“이게 무슨말?”

유스케이스의 핵심은 업무 흐름

```text
입력 데이터 받기
엔티티 조회 또는 생성
업무 규칙 실행
결과 생성
```

=> 이 흐름 자체는 반드시 웹 서버나 실제 DB가 있어야만 실행되는 것이 아님.

ex) 주문취소 유스케이스 테스트

```text
주문 ID를 입력한다
가짜 주문 저장소에서 주문을 가져온다
주문 취소 가능 여부를 확인한다
주문 상태를 취소로 변경한다
결과를 반환한다
```

여기서 실제 DB 대신 mock 저장소를 사용할 수 있음.

```text
실제 DB
→ 테스트에서는 필요 없음

가짜 저장소
→ 메모리 안에 주문 데이터를 넣어두고 테스트
```

```text
[ 테스트 코드 ]
      |
      v
[ 주문 취소 유스케이스 ]
      |
      v
[ 가짜 저장소 / Mock Repository ]
```

실제 운영에서는

```text
[ 웹 컨트롤러 ]
      |
      v
[ 주문 취소 유스케이스 ]
      |
      v
[ 실제 DB 저장소 ]
```

> 유스케이스가 웹과 DB를 직접 알지 않으면, 테스트에서는 mock 입력과 mock 저장소만으로 유스케이스를 검증할 수 있다.

---

## 6. 테스트에서 중요한 점

테스트를 하기 위해 웹 서버를 띄우고, DB를 연결하고, 프레임워크를 초기화해야 한다면  
유스케이스가 세부사항에 너무 강하게 묶여 있을 수 있음.

```text
웹 없이 테스트
DB 없이 테스트
프레임워크 없이 테스트
외부 API 없이 테스트
```

=> 좋은 구조에서는 이게 가능해야 함.

=> 최종적으로는 통합 테스트를 거쳐야겠지만,
우선 유스케이스 자체는 독립적으로 단위 테스트가 가능해야 함.

```text
단위 테스트
→ 유스케이스 자체 검증

통합 테스트
→ 웹, DB, 프레임워크 연결까지 검증
```

---

## 7. 유스케이스 중심의 구조

```text
나쁜 방향

[ Web Framework ]
        |
        v
[ Controller ]
        |
        v
[ DB / ORM ]
        |
        v
[ 업무 로직이 여기저기 흩어짐 ]
```

=> 이 구조에서는 시스템이 무엇을 하는지보다 어떤 프레임워크를 쓰는지가 먼저 보임.

```text
좋은 방향

[ Web / DB / Framework ]
        |
        v
[ Use Cases ]
        |
        v
[ Entities / Business Rules ]
```

=> 핵심은 의존성이 안쪽으로 향해야 한다는 점
