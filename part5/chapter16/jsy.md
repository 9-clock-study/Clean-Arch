# 유스케이스

아키텍처는 시스템의 행위에 큰 영향을 주지 않는다. 행위와 관련해 아키텍처가 열어 둘 수 있는 선택사항은 거의 없다.
좋은 아키텍처는 행위를 명확히 하고 외부로 드러내며 이를 통해 시스템이 지닌 의도를 아키텍처 수준에서 알아볼 수 있게 만드는 것.

좋은 아키텍처든 스파게티 코드든 시스템의 동작은 정상 작동할것임
행위를 외부로 드러내는 것, 의도를 아키텍처 수준으로 올리는 법 <<이건 21장에서 다룰 내용>>

# 4가지 독립성 정리

위에서 알아본 4가지 독립성에 대해서는 실제 마주하는 프로젝트에서는 균형점을 찾기가 쉽지 않지만 그래도 그나마 더 싸게 위와 같은 독립성을 지키는 방법이 있음

# 방법1 : 계층 결합 분리

유스케이스 측면에서 아키텍트는 필요한 모든 유스케이스를 지원할 수 있는 시스템 구조를 원한다. BUT 유스케이스 전부를 알지는 못함 BUT 아키텍트는 시스템의 기본적인 의도는 분명히 알고 있음

여기서 의도란 SRP와 일맥상통

의도의 맥락에 따라서 다른 이유로 변경되는 것들은 분리, 동일한 이유로 변경되는 것들은 묶음

"데이터베이스, 쿼리 언어, 스키마" 애네들은 업무 규칙이나 UI와는 관련이 없음 이들은 시스템의 다른 측면과는 다른 속도로 그리고 다른 이유로 변경된다. 결론적으로 아키텍트는 이들을 다른 시스템의 나머지 부분으로부터 분리하여 독립적으로 변경할 수 있도록 해야만 한다."

# 중복..(진짜/가짜 중복)

- 진짜 중복 : 한 인스턴스가 변경되면 동일한 변경을 그 인스턴스의 모든 복사본에 반드시 적용해야 한다.
- 우발적 중복 : 중복으로 보이는 두 코드 영역이 각자의 경로로 발전한다면, 즉 서로 다른 속도와 다른 이유로 변경된다면 이 두 코드는 가짜 중복임

중복이라고 생각해서 코드를 합쳐놨더니 우발적중복으로 빠질경우 다시 분리해야되는 불상사 발생..

유스케이스를 수직/수평에 따른 분리를 고려할 때 진짜/가짜 중복을 잘 분간하기

> 유스케이스의 수직/수평 계층이 뭔지 잘 모르겠음
