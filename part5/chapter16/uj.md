# Clean Architecture 5부 16장 정리: 독립성

> 좋은 아키텍처는 중요한 것들이 서로 불필요하게 묶이지 않도록 분리하여, 시스템을 이해-개발-운영-배포하기 쉽게 만드는 구조

---

## 1. 16장의 흐름 이해

핵심 개념들이 어떤 순서와 관계로 연결되는지 구분이 모호해서 정리해봄.

```text
1. 좋은 아키텍처가 지원해야 하는 것
   → 유스케이스, 운영, 개발, 배포

2. 왜 분리해야 하는가
   → 선택사항을 열어두기 위해

3. 무엇을 분리해야 하는가
   → 계층과 유스케이스

4. 어떻게 분리할 수 있는가
   → 소스 수준, 배포 수준, 서비스 수준

5. 분리하면 무엇이 좋아지는가
   → 개발 독립성, 배포 독립성

6. 분리의 부작용은 무엇인가
   → 중복과 관리 비용
```

---

## 2. 좋은 아키텍처가 지원해야 하는 것

### 2.1 유스케이스

유스케이스 : 시스템이 수행해야 하는 주요 업무 흐름과 행위

```text
좋은 아키텍처
→ 이 시스템이 무엇을 하는지 유스케이스 중심으로 이해가 가능해야 함
```

---

### 2.2 운영

운영 : 시스템이 실제 환경에서 어떻게 동작하고, 얼마나 안정적으로 실행되는지

```text
운영에서 중요한 것
→ 성능
→ 확장성
→ 안정성
→ 처리량
→ 장애 대응
```

```text
좋은 아키텍처
→ 시시스템이 실제 운영 환경에서 요구되는 성능, 확장성, 안정성을 감당할 수 있게 해야 함

```

---

### 2.3 개발

개발 : 여러 개발자나 팀이 시스템을 함께 만들 수 있는가와 관련

```text
좋은 개발 구조
→ 팀별 작업 범위가 분리됨
→ 변경 충돌이 줄어듦
→ 각 팀이 맡은 부분을 독립적으로 이해하고 수정 가능
```

```text
좋은 아키텍처
→ 팀들이 서로 덜 충돌하면서 작업할 수 있도록 잘 나뉘어져 있어야함.
```

---

### 2.4 배포

배포 : 변경된 소프트웨어를 실제 실행 환경에 반영하는 과정

```text
좋은 배포 구조
→ 전체 시스템을 매번 다시 배포하지 않아도 됨
→ 변경된 부분만 독립적으로 배포 가능
→ 배포 위험이 줄어듦
```

```text
좋은 아키텍처
→ 변경된 부분을 가능한 한 독립적으로 배포할 수 있게 해야 함.
```

---

## 3. 선택사항 열어놓기

앞 장에서도 얘기했다시피 아키텍처의 중요한 목적 중 하나는 결정을 늦출 수 있게 만드는 것.
즉, 세부사항에 대한 결정을 가능한 한 오래 미룰 수 있도록 해야 함.

```text
나중에 결정해도 좋은 것
→ DB 종류
→ 웹 프레임워크
→ UI 방식
→ 외부 API
→ 배포 방식
→ 서비스 분리 방식
```

이것을 가능하게 하려면 핵심 정책과 세부사항이 강하게 묶여 있으면 안 됨.

> 좋은 아키텍처는 중요한 정책을 먼저 세우고, 바뀌기 쉬운 세부사항에 대한 결정은 최대한 늦출 수 있게 하는 구조

---

## 4. 무엇을 분리해야 하는가

중요한 분리 기준은 크게 두 가지

```text
계층 결합 분리
유스케이스 결합 분리
```

---

### 4.1 계층 결합 분리

계층 결합 분리 : 시스템을 역할별 계층으로 나누는 것

```text
예시 계층
→ UI
→ 유스케이스
→ 업무 규칙
→ 데이터 접근
→ 외부 시스템 연동
```

각 계층은 서로 다른 이유로 변경됨

```text
UI
→ 화면 요구사항 때문에 변경

유스케이스
→ 업무 흐름 변경 때문에 변경

DB
→ 저장 방식 변경 때문에 변경

외부 API
→ 외부 시스템 변경 때문에 변경
```

> 계층 결합 분리는 서로 다른 역할과 변경 이유를 가진 코드를 계층별로 나누는 것(수평적)

---

### 4.2 유스케이스 결합 분리

유스케이스 결합 분리 : 기능 흐름별로 코드를 나누는 것
같은 계층 안에서도 유스케이스가 다르면 변경 이유가 다를 수 있음.

```text
예시
→ 회원 가입 유스케이스
→ 로그인 유스케이스
→ 주문 생성 유스케이스
→ 주문 취소 유스케이스
→ 알림 발송 유스케이스
```

=> 유스케이스별로 독립성을 확보하면 변경 영향 범위를 줄일 수 있음.

> 유스케이스 결합 분리는 기능 흐름별로 변경 영향이 퍼지지 않도록 유스케이스 단위로 코드를 나누는 것(수직적)

---

### 4.3 계층 분리와 유스케이스 분리의 차이

두 분리는 서로 다른 축.

```text
계층 분리
→ 역할 기준 분리

유스케이스 분리
→ 기능 흐름 기준 분리
```

> 계층 분리는 수평 방향의 역할 분리, 유스케이스 분리는 수직 방향의 기능 흐름 분리로 이해 가능

---

## 5. 결합 분리 모드

아키텍처는 결합을 여러 수준에서 분리할 수 있음.

```text
소스 수준 분리 모드
배포 수준 분리 모드
서비스 수준 분리 모드
```

---

### 5.1 소스 수준 분리 모드

소스 수준 분리 : 코드 수준에서 의존성을 분리하는 방식

```text
특징
→ 같은 프로젝트 안에 있을 수 있음
→ 같은 실행 파일로 빌드될 수 있음
→ 코드 의존성만 규칙적으로 분리
```

## ex) 폴더, 패키지, 네임스페이스, 모듈 단위로 코드를 나누는 방식

### 5.2 배포 수준 분리 모드

배포 수준 분리 : 컴포넌트 단위로 분리하는 방식

```text
특징
→ 별도 라이브러리나 패키지로 분리 가능
→ 각 컴포넌트에 버전 부여 가능
→ 독립적으로 릴리스 가능
```

ex) `.jar`, `.dll`, npm 패키지, Python 패키지처럼 배포 가능한 단위로 나누는 방식

---

### 5.3 서비스 수준 분리 모드

서비스 수준 분리 : 실행 단위까지 분리하는 방식

```text
특징
→ 별도 프로세스 또는 별도 서비스로 실행
→ 네트워크를 통해 통신
→ 독립적인 배포와 확장 가능
```

ex) 마이크로서비스 구조

---

### 5.4 결합 분리 모드의 선택

```text
소스 수준 분리
→ 가볍지만 독립 배포는 어려움

배포 수준 분리
→ 독립 릴리스 가능하지만 버전 관리 비용 발생

서비스 수준 분리
→ 독립 운영 가능하지만 분산 시스템 복잡성 증가
```

---

## 6. 개발 독립성과 배포 독립성

### 6.1 개발 독립성

개발 독립성 : 팀이나 개발자가 서로 다른 부분을 독립적으로 개발할 수 있는 성질

```text
개발 독립성이 높으면
→ 팀 간 충돌 감소
→ 병렬 개발 가능
→ 담당 영역 이해가 쉬움
→ 변경 영향 범위가 작아짐
```

---

### 6.2 배포 독립성

배포 독립성 : 시스템의 일부를 독립적으로 배포할 수 있는 성질

```text
배포 독립성이 높으면
→ 변경된 부분만 배포 가능
→ 배포 위험 감소
→ 릴리스 주기 유연화
→ 전체 시스템 재배포 부담 감소
```

---

### 6.3 개발 독립성과 배포 독립성의 관계

```text
개발 독립성
→ 따로 개발할 수 있는가

배포 독립성
→ 따로 배포할 수 있는가
```

소스 수준 분리만 되어 있어도 개발 독립성은 어느 정도 얻을 수 있지만,
배포 독립성을 얻으려면 배포 단위나 서비스 단위의 분리가 필요할 수 있음

---

## 7. 중복

```text
진짜 중복
→ 같은 이유로 변경되는 코드가 반복됨

우발적 중복
→ 겉으로 비슷하지만 서로 다른 이유로 변경되는 코드
```

진짜 중복은 제거.
우발적 중복은 억지로 합치면 오히려 문제가 될 수 있음.

> 중복은 무조건 제거하는 것이 아니라, 같은 이유로 변경되는 중복인지부터 판단해야 함

---

# 16장에 나온 개념 한 줄 정리

| 개념                 | 한줄정리                                                 |
| -------------------- | -------------------------------------------------------- |
| 유스케이스           | 시스템이 실제로 사용자에게 제공하는 기능 흐름            |
| 운영                 | 시스템이 실제 환경에서 안정적으로 동작하도록 만드는 관점 |
| 개발                 | 여러 개발자와 팀이 충돌 없이 일할 수 있게 하는 관점      |
| 배포                 | 변경된 부분을 실제 환경에 안전하게 반영하는 관점         |
| 선택사항 열어놓기    | 세부 기술 결정을 가능한 한 늦출 수 있게 만드는 것        |
| 계층 결합 분리       | 역할이 다른 코드를 계층별로 나누는 것                    |
| 유스케이스 결합 분리 | 기능 흐름별로 변경 영향을 분리하는 것                    |
| 소스 수준 분리       | 코드 의존성만 분리하는 가장 가벼운 분리                  |
| 배포 수준 분리       | 독립 릴리스 가능한 컴포넌트 단위 분리                    |
| 서비스 수준 분리     | 별도 실행 단위로 분리하는 가장 강한 분리                 |
| 개발 독립성          | 각 팀이 맡은 부분을 독립적으로 개발할 수 있는 성질       |
| 배포 독립성          | 변경된 부분만 독립적으로 배포할 수 있는 성질             |
| 중복                 | 무조건 제거할 대상이 아니라 변경 이유를 보고 판단할 대상 |
