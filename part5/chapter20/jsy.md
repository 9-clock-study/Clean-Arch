# 업무 규칙 - Business Rule

- 업무 규칙은 사업적으로 수익을 얻거나 비용을 줄일 수 있는 규칙 또는 절차

- 핵심 업무 규칙(Critical Business Rule ) : 소프트웨어 없이 사람이 수동으로(예: 주판이나 종이로) 처리하더라도 반드시 성립되어야 하는 규칙
  그리고 핵심 업무 규칙은 보통 데이터를 요구한다.
  또한 업무 규칙과 같이 사람이 수동으로 처리하더라도 존재하는 데이터를 **핵심 업무 데이터**라고 한다.

핵심 규칙과 핵심 데이터는 본질적으로 결합되어 있기 때문에 객체로 만들기 좋은 후보가 된다.
-> 이러한 유형의 객체를 Entity라고 한다.

## 엔티티

엔티티의 인터페이스는 핵심 업무 데이터를 기반으로 동작하는 핵심 업무 규칙을 구현한 함수들로 구성된다.

```loan UML

class Loan {
- principle
- rate
- period

+ makePayment()
+ applyInterest()
+ chargeLateFee()
}

- 세 가지의 핵심 업무 데이터를 포함 + 데이터와 관련된 세 가지 핵심 업무 규칙을 인터페이스로 제공
```

이 엔티티는 업무의 대표자로서 독립적으로 존재한다. 해당 클래스는 DB, 사용자 인터페이스 등 선택사항들로 인해 오염되어서는 안된다.

- 엔티티는 순전히 업무에 대한 것
- 엔티티를 만드는데 꼭 객체 지향 언어를 사용할 필요는 없다. 유일한 요구조건은 핵심 업무 데이터 + 핵심 업무 규칙을 하나로 묶어서 별도의 소프트웨어 모듈로 만들어야 한다는 것이다.

### 내가 궁금했던 엔티티

엔티티라는 용어를 3곳에서 들었던 적이 있다.

1. DBMS
2. DDD
3. TypeORM

### DBMS

DBMS에서는 엔티티는 데이터베이스에서 저장하고 관리해야 할 중요한 객체나 개념이다.
-> 나는 "내가 특정한 목적을 가지고 투영하고 싶은 무언가(유형/무형)" 라고 해석하고싶다. <- 모델링과 구현 두개의 개념이 있다고한다면 이 문장은 모델링에 가깝다.

### DDD

고유한 식별자(ID)를 통해 구별되며, 시간에 따라 상태가 지속적으로 변화하는 핵심 도메인 객체

### TypeORM

```ts
@Entity("users") // Optional: Specify custom table name. Defaults to class name.
export class User {
  @PrimaryGeneratedColumn() // Automatically increments ID (Primary Key)
  id: number;

  @Column({ type: "varchar", length: 150 }) // Configures column constraints
  firstName: string;

  @Column({ default: true }) // Sets default value
  isActive: boolean;

  @CreateDateColumn() // Automatically populates on creation
  createdAt: Date;

  @UpdateDateColumn() // Automatically updates on modification
  updatedAt: Date;
}
```

TypeORM에서는 엔티티를 이렇게 다룬다. 여기서 나의 헷갈림이 시작되었다.
DBMS, TypeORM에서 엔티티는 핵심 업무 규칙은 없다, 핵심 데이터만 존재한다.

- DDD 엔티티는 잘 몰라서 넘기겠다.

그럼 같은 단어를 두고 왜 불일치가 발생하는 것인지 의구심이 들었다. DBMS와 TypeORM은 엔티티를 어느 맥락에서 바라보고 있는 것일까?

자료한 조사에 따르면 엔티티라는 용어의 개념은 클린 아키텍처 이전 Ivar Jacobson, Peter Chen에 의해서 언급된 적이 있다.

> - Peter Chen(1976): https://www.dragon1.com/downloads/peter-chen-entity-relationhip-model.pdf
> - Ivar Jacobson(1992): Object-Oriented-Software-Engineering

1970년대 Peter Chen이 ER모델을 만들면서 현실 세계의 "독립적으로 식별 가능한 대상"을 Entity라고 불렀고, 소프트웨어 공학도 같은 현실 세계를 모델링하다 보니 같은 단어를 가져다 썼다.

예를 들어서 현실 세계의 "사용자"라는 대상을 DB모델링 관점과 소프트웨어 공학 두 가지로 나눠 본다면

|  DB 모델링   | 소프트웨어 공학 |
| :----------: | :-------------: |
| users 테이블 |  users 클래스   |
| 데이터 저장  |  데이터 + 행동  |

#### 근데 소프트웨어 공학에서 해당 의미도 시간이 지나면서 바뀌었다.

1992년 Jacobson은 오래 지속되는 정보를 가진 객체로 아직 업무 규칙은 추가되지 않은 것이 Entity라고 불렀다.

그 이후에 클린 아키텍처의 엔티티는 Jacobson의 개념에다가 업무 규칙을 추가한게 엔티티가 된 것이다.

그래서 TypeORM을 여기서 한번 짚고 넘어가고싶다 분명 클래스 `User`로 되어 있어서 클래스인데 왜 엔티티? 단순히 DB에 저장될 필드들만 나열되어 있는데?
그 이유는 TypeORM은 DB모델링 관점에서 작성된것이며 이를 코드 수준에서 추상화 한것이 때문이다.

> User 클래스임에도 엔티티라고 부르는 이유는, TypeORM이 DB 모델링 관점을 따르기 때문이다. DB 모델링에서 엔티티는 "저장되어야 할 대상"을 의미하고, TypeORM의 @Entity()는 그 대상을 코드 수준에서 클래스로 표현한 것이다. 그래서 업무 규칙 없이 필드만 나열되어 있어도 엔티티라고 부른다.

## 유스케이스

모든 업무 규칙이 엔티티처럼 순수한 것은 아닌데, 특히 자동화된 시스템이 동작하는 방법을 정의하고 제약함으로써 수익을 얻거나 비용을 줄이는 업무 규칙도 존재한다.

이러한 업무 규칙은 자동화된 시스템의 요소로 존재해야만 의미가 있으므로 기존의 업무 규칙과 구별된다.

```
e.g
신규 대출을 위한 신상정보 수집하기

READ: 이름, 주소, 생일, 주민번호 등
WRITE: 사용자 확인을 위한 동일한 전보 + 신용도

PROCESS
1. 이름을 받아서 검증한다.
2. 주소, 생일, 주민번호 등을 검증한다.
3. 신용도를 얻는다.
4. 신용도가 500보다 낮으면 Denial(거절)을 활성화
5. 높으면 Customer를 생성하고 Loan Estimation을 활성화
```

유스케이스는 자동화된 시스템이 사용되는 방법을 설명한다.
유스케이스는 입력,출력,과정을 기술한다.

- 엔티티 내의 핵심 업무 규칙과는 반대로 유스케이스는 애플리케이션에 특화된 업무 규칙을 설명한다.

유스케이스도 객체... 엔티티도 객체... 온 세상이 다 객체...

- 유스케이스는 애플리케션에 특화된 업무 규칙을 구현하는 하나 이상의 함수를 제공한다. 또한 유스케이스는 입력 데이터, 출력 데이터, 유스케이스가 상호작용하는 엔티티에 대한 참조 데이터 등의 데이터 요소를 포함한다.

근데 여기서 엔티티와 같은 고수준 개념은 저수준인 유스케이스에 대해 알지 못한다(DIP)

유스케이스가 저수준인 이유는 입력/출력에 더 가까운 위치에 있기 때문, 그리고 유스케이스는 엔티티에 의존한다.
