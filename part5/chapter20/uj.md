# Clean Architecture 5부 20장 정리: 업무 규칙

> 업무 규칙은 시스템이 반드시 지켜야 하는 핵심 규칙. 좋은 아키텍처는 이 업무 규칙을 세부사항으로부터 분리해 보호하는 구조

---

## 1. 업무 규칙이란 무엇인가

```text
업무 규칙
→ 시스템이 어떤 조건에서 무엇을 해야 하는지 정한 규칙
→ 업무적으로 반드시 지켜야 하는 판단 기준
→ 시스템의 목적과 직접 연결되는 규칙
```

예를 들어 다음과 같은 것들이 업무 규칙에 해당

```text
주문은 어떤 조건에서 승인되는가
대출 한도는 어떻게 계산되는가
회원 등급은 어떤 기준으로 결정되는가
결제는 어떤 조건에서 실패 처리되는가
```

---

## 2. 핵심 업무 규칙

핵심 업무 규칙 : 업무 규칙 중에서 가장 본질적인 규칙

```text
핵심 업무 규칙
→ 시스템의 중심에 위치해야 하는 규칙
→ UI, DB, 프레임워크와 무관하게 유지되어야 하는 규칙
→ 애플리케이션이 없어도 업무 자체에 존재할 수 있는 규칙
```

ex) 대출 시스템
“대출 가능 여부를 판단하는 규칙” -> 핵심 업무 규칙

“그 결과를 화면에 어떤 색으로 보여줄 것인가” -> UI 세부사항

---

## 3. 핵심 업무 데이터

```text
핵심 업무 규칙
→ 판단과 계산을 수행함

핵심 업무 데이터
→ 그 판단과 계산에 필요한 데이터
```

```text
핵심 업무 규칙
→ 회원 등급을 계산한다

핵심 업무 데이터
→ 가입일
→ 누적 구매 금액
→ 최근 활동 이력
```

---

## 4. 엔티티

```text
엔티티
→ 핵심 업무 데이터와 핵심 업무 규칙을 함께 담은 객체
```

엔티티는 핵심 업무 데이터를 기반으로 동작하는  
작은 핵심 업무 규칙들을 포함

```text
회원 엔티티
├─ 회원 ID
├─ 가입일
├─ 누적 구매 금액
└─ 등급 계산 규칙
```

```text
주문 엔티티
├─ 주문 금액
├─ 주문 상태
├─ 주문 상품 목록
└─ 주문 취소 가능 여부 판단 규칙
```

---

## 5. 엔티티의 인터페이스

```text
엔티티 인터페이스
→ 핵심 업무 데이터를 사용하는 핵심 업무 규칙 함수들
```

ex) 주문 엔티티

```text
cancel()
calculateTotalPrice()
canBeCancelled()
changeStatus()
```

```text
잘못된 이해
→ 엔티티 = DB 테이블과 1:1로 대응되는 데이터 객체

좋은 이해
→ 엔티티 = 핵심 업무 데이터와 핵심 업무 규칙을 함께 가진 객체
```

한 줄 정리

> 엔티티의 함수는 핵심 업무 규칙을 수행

---

## 6. 유스케이스

유스케이스 : 자동화된 시스템이 사용되는 방법을 설명

```text
유스케이스
→ 사용자가 무엇을 입력하는가
→ 시스템이 어떤 처리를 하는가
→ 사용자에게 무엇을 출력하는가
```

유스케이스는 애플리케이션에 특화된 업무 규칙

```text
유스케이스
→ 입력 데이터
→ 처리 단계
→ 출력 데이터
```

=> 유스케이스는 엔티티 내부의 핵심 업무 규칙을  
언제, 어떤 순서로, 어떤 목적을 위해 호출할지 정한다.

```text
유스케이스
→ 사용자와 엔티티 사이의 상호작용을 규정
→ 엔티티의 핵심 업무 규칙을 조율
```

ex) 주문 취소 유스케이스

```text
1. 사용자가 주문 취소 요청
2. 주문 엔티티 조회
3. 주문 엔티티의 취소 가능 여부 확인
4. 취소 가능하면 상태 변경
5. 결과를 사용자에게 반환
```

“취소 가능 여부를 판단하는 규칙” -> 핵심 업무 규칙(엔티티)

“사용자 요청을 받아 어떤 순서로 처리할 것인가" -> 유스케이스

---

## 7. 엔티티와 유스케이스의 관계

엔티티와 유스케이스는 모두 업무 규칙과 관련이 있음.
하지만 수준이 다름.

```text
엔티티
→ 고수준
→ 핵심 업무 규칙과 핵심 업무 데이터를 담음
→ 애플리케이션과 독립적인 규칙

유스케이스
→ 저수준
→ 특정 애플리케이션의 사용 흐름을 설명
→ 엔티티를 어떻게 사용할지 정함
```

```text
높은 수준
┌──────────────────────────────┐
│ 엔티티                        │
│ - 핵심 업무 데이터             │
│ - 핵심 업무 규칙               │
└──────────────────────────────┘
              ↑
              │ 사용 / 호출
              │
┌──────────────────────────────┐
│ 유스케이스                    │
│ - 입력 데이터                 │
│ - 처리 절차                   │
│ - 출력 데이터                 │
│ - 엔티티 호출 순서            │
└──────────────────────────────┘
낮은 수준
```

여기서 중요한 점은 유스케이스가 엔티티를 사용하지만,  
엔티티가 유스케이스를 알아서는 안 된다는 것.

```text
유스케이스 → 엔티티
엔티티 → 유스케이스  X
```

> 엔티티는 핵심 규칙 자체이고, 유스케이스는 그 핵심 규칙을 애플리케이션 흐름 안에서 사용하는 방식.

---

## 8. 요청 및 응답 모델

유스케이스는 보통 입력 데이터와 출력 데이터를 가짐

```text
요청 모델
→ 유스케이스가 실행되기 위해 필요한 입력 데이터

응답 모델
→ 유스케이스 실행 결과로 반환되는 출력 데이터
```

ex) 주문 취소 유스케이스

```text
요청 모델
→ 주문 ID
→ 사용자 ID
→ 취소 사유

응답 모델
→ 취소 성공 여부
→ 변경된 주문 상태
→ 메시지
```

요청 및 응답 모델은 유스케이스의 경계를 명확하게 함.

```text
외부 세계
→ 요청 모델
→ 유스케이스
→ 응답 모델
→ 외부 세계
```

중요한 점은 요청/응답 모델이 UI나 DB 모델과 같을 필요가 없다는 것.  
유스케이스는 자신에게 필요한 입력과 출력 형식을 따로 가질 수 있음.

> 요청 및 응답 모델은 유스케이스가 외부와 데이터를 주고받는 경계를 명확히 하기 위한 모델.

---

## 9. 왜 업무 규칙을 알아야 하는가

```text
UI는 바뀔 수 있음
DB는 바뀔 수 있음
프레임워크는 바뀔 수 있음
외부 API는 바뀔 수 있음

하지만 핵심 업무 규칙은 쉽게 바뀌면 안 됨
```

업무 규칙을 제대로 분리하지 않으면,

```text
DB 변경이 업무 규칙 변경으로 이어짐
UI 변경이 핵심 로직 수정으로 이어짐
프레임워크 교체가 시스템 전체 수정으로 이어짐
```

그래서 업무 규칙을 시스템 중심에 두고, 세부사항을 바깥으로 밀어내야 함

```text
중심
→ 엔티티
→ 유스케이스

바깥
→ UI
→ DB
→ 프레임워크
→ 외부 시스템
```

> 업무 규칙을 알아야 무엇을 시스템의 중심에 두고 보호해야 하는지 판단할 수 있음.
