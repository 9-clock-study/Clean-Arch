# Clean Architecture 5부 22장 정리: 클린 아키텍처

---

## 1. 핵심은 관심사 분리

```text
관심사의 분리
→ 서로 다른 이유로 변경되는 것들을 분리하는 것
→ 업무 규칙과 세부사항을 분리하는 것
→ 시스템의 중심과 바깥을 나누는 것
```

```text
좋은 아키텍처는 다음과 같은 계층을 포함
1. 업무 규칙을 위한 계층
2. 사용자와 시스템 인터페이스를 위한 계층
```

---

## 2. 클린 아키텍처가 중시하는 독립성

```text
프레임워크 독립성
→ 프레임워크가 시스템의 중심 구조를 결정하지 않음

테스트 용이성
→ UI, DB, 웹 서버 없이도 업무 규칙과 유스케이스 테스트 가능

UI 독립성
→ 화면이 바뀌어도 업무 규칙은 영향받지 않음

DB 독립성
→ DB 종류나 저장 방식이 바뀌어도 업무 규칙은 영향받지 않음

외부 에이전시 독립성
→ 외부 API, 장치, 프레임워크가 바뀌어도 핵심 규칙은 보호됨
```

> 어쨌든, 업무 규칙은 외부 세계와 인터페이스에 대해 몰라야 한다.

---

## 3. 의존성 규칙

```text
의존성 규칙
→ 소스코드 의존성은 반드시 고수준 정책(안쪽)을 향해야 한다.
```

```text
바깥쪽(저수준 세부사항)
→ UI
→ DB
→ 웹
→ 프레임워크
→ 외부 시스템

안쪽(고수준 정책)
→ 유스케이스
→ 엔티티
→ 업무 규칙
```

의존성 방향

```text
UI / DB / Framework
        ↓
Use Case
        ↓
Entity
```

안쪽의 엔티티나 유스케이스가  
바깥쪽의 UI, DB, 프레임워크를 직접 알아서는 안 됨.

```text
나쁜 방향
Entity → DB
Use Case → Web Framework

좋은 방향
DB Adapter → Use Case
Controller → Use Case
Use Case → Entity
```

---

## 4. 주요 계층

```text
안쪽
┌──────────────────────────┐
│ Entity                   │
│ 전사 핵심 업무 규칙       │
└──────────────────────────┘
┌──────────────────────────┐
│ Use Case                 │
│ 애플리케이션 특화 업무규칙 │
└──────────────────────────┘
┌──────────────────────────┐
│ Interface Adapter        │
│ Controller, Presenter    │
│ View, Gateway, SQL 변환   │
└──────────────────────────┘
┌──────────────────────────┐
│ Frameworks & Drivers     │
│ Web, DB, UI, Framework   │
└──────────────────────────┘
바깥쪽
```

---

## 4.1. 엔티티 계층

엔티티 계층은 가장 안쪽에 위치.

```text
엔티티
→ 전사 핵심 업무 규칙을 캡슐화
→ 핵심 업무 데이터와 핵심 업무 규칙을 포함
→ 가장 고수준의 정책
```

=> 엔티티는 특정 애플리케이션, UI, DB, 프레임워크에 의존하지 않음.

---

## 6. 유스케이스 계층

유스케이스 계층은 애플리케이션 특화 업무 규칙을 담고 있음

```text
유스케이스
→ 시스템의 모든 사용 흐름을 캡슐화
→ 입력을 받아 처리 절차를 수행
→ 엔티티의 핵심 업무 규칙을 호출
→ 출력 데이터를 생성
```

유스케이스는 엔티티를 사용하지만,  
엔티티에 영향을 주면 안 됨.

```text
Use Case → Entity
Entity → Use Case  X
```

=> 유스케이스는 엔티티의 핵심 업무 규칙을 애플리케이션 흐름 안에서 어떻게 사용할지 정의

---

## 7. 인터페이스 어댑터 계층

인터페이스 어댑터는 안쪽 계층과 바깥쪽 세부사항 사이에서 데이터를 변환

```text
인터페이스 어댑터
→ Controller
→ Presenter
→ View
→ Gateway
→ SQL 변환
```

바깥쪽 형식을 안쪽에서 쓰기 좋은 형식으로 바꾸고,  
안쪽 결과를 바깥쪽에서 쓰기 좋은 형식으로 바꾸는 것.

```text
외부 입력 형식
→ 유스케이스 입력 모델

유스케이스 출력 모델
→ 화면 출력 형식
```

---

## 8. 프레임워크와 드라이버 계층

```text
프레임워크와 드라이버
→ 웹 프레임워크
→ DB
→ UI
→ 외부 API
→ 장치
```

이 계층은 바뀌기 쉬운 기술적 선택.
-> 안쪽의 업무 규칙이 이 계층에 의존해서는 안 됨.

> 프레임워크와 드라이버는 시스템의 중심이 아니라 바깥쪽 세부사항에 속함.

---

## 9. 경계 횡단과 제어 흐름

사용자가 웹 요청을 보내면 컨트롤러가 요청을 받고,  
유스케이스를 실행하고, 결과를 프레젠터가 화면에 맞게 변환.

```text
제어 흐름

[ Controller ] → [ Use Case ] → [ Presenter ] → [ View ]
```

=> 소스코드 의존성은 항상 안쪽을 향해야 함.

```text
소스코드 의존성

[ Controller ] → [ Use Case ]
[ Presenter ] → [ Use Case Output Port ]
[ Use Case ] → [ Entity ]
```

```text
제어 흐름
Controller → Use Case → Presenter

의존성 방향
Controller → Use Case
Presenter → Use Case 쪽 인터페이스
```

> 실행 흐름이 바깥쪽으로 나가더라도, 소스코드 의존성은 안쪽을 향해야 한다.

---

## 10. 왜 이렇게 분리하는가

이렇게 분리하는 이유는 "업무 규칙"을 보호하기 위해서

```text
UI 변경
→ 업무 규칙에 영향 없음

DB 변경
→ 업무 규칙에 영향 없음

프레임워크 변경
→ 업무 규칙에 영향 없음

외부 API 변경
→ 업무 규칙에 영향 없음
```

=> 클린 아키텍처는 바뀌기 쉬운 세부사항이  
시스템의 핵심을 흔들지 못하게 만드는 구조

---

# 정리

```text
클린 아키텍처
→ 관심사의 분리를 통해 업무 규칙을 보호하는 구조

핵심 원칙
→ 소스코드 의존성은 반드시 안쪽, 즉 고수준 정책을 향해야 함

안쪽
→ 엔티티
→ 유스케이스
→ 업무 규칙

바깥쪽
→ UI
→ DB
→ 웹
→ 프레임워크
→ 외부 시스템
```

> 클린 아키텍처는 엔티티와 유스케이스를 중심에 두고, UI·DB·프레임워크 같은 세부사항이 안쪽 업무 규칙에 의존하도록 만드는 구조
