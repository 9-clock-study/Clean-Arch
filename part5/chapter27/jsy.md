# '크고 작은 모든' 서비스들

- 서비스 지향 아키텍처
- 마이크로서비스 아키텍처

## 서비스 아키텍처?

서비스를 사용한다는 것이 본질적으로 아키텍처에 해당하는가? -> 명백히 아니다.  
why? -> 시스템의 아키텍처는 의존성 규칙을 준수하며, 고수준의 정책을 저수준의 세부사항으로부터 분리하는 경계에 의해 정의된다.

> 아키텍처란 절대 내가 사용하고 있는 프레임워크가 아니다. "이번 프로젝트를 NestJS의 의존성 주입을 활용해 모듈 기반으로 프로젝트를 진행했습니다" 이딴게 아니다/
> 아키텍처란 내가 시스템에서 정의한 고수준 정책은 무엇인지, 유스케이스는 어떻게 나눴는지 그에 따른 세부사항은 어떻게 의존성 규칙을 준수하며 설계했는지에 대한 것이다.

서비스 아키텍처가 단순히 애플리케이션의 행위를 분리할 뿐인 서비스라면 값비싼 함수 호출에 불과하며, 아키텍처 관점에서 꼭 중요하진 않다.

## 서비스의 이점?

서비스들 사이의 결합은 잘 분리되지만, 프로세서 또는 네트워크 상의 공유자원 때문에 강한 결합이 일어난다.

## 야옹이 문제

그러니깐 마이크로"서비스"라는 것도 의존성 규칙을 무시하면서 코드를 짰을 떄 새로운 기능(고양이 배달)을 추가하려면 모든 코드를 다 고쳐야된다는건데
컴포넌트 기반으로하면 Rides랑 kitten을 분리하고 하나의 고수준 인터페이스나 추상클래스를 바라보게하면 기존 코드 수정없이 런타임에 교체할 수 있다는 말인데
무튼 이런 횡단 관심사를 처리하기 위해서는 의존성 규칙을 준수하는 컴포넌트 아키텍처로 설계해야된다는 것

```
Kitten Selector-> Taxi Selector <- Ride Selector
```
