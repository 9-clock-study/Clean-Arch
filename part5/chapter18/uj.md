# Clean Architecture 5부 18장 정리: 경계 해부학

17장 -> “경계를 왜 그어야 하는가”
18장 -> “그 경계가 실제 코드와 실행 환경에서 어떤 모습으로 나타나는가”

> 아키텍처 경계는 함수 호출 수준의 가벼운 경계부터 네트워크 서비스 수준의 강한 경계까지 다양하며, 경계가 강해질수록 독립성은 커지지만 통신 비용과 복잡성도 커진다.

---

## 1. 아키텍처 경계의 형태

```text
아키텍처 경계
│
├─ 소스 수준 경계
│   └─ 단일체 / 모놀리식 구조
│      └─ 같은 실행 파일, 같은 주소 공간
│
├─ 배포 수준 경계
│   └─ 배포형 컴포넌트
│      └─ jar, dll, gem, npm package 등
│
├─ 실행 수준 경계
│   ├─ 로컬 프로세스
│   │  └─ 같은 컴퓨터 안의 별도 프로세스
│   │
│   └─ 서비스
│      └─ 네트워크를 통해 통신하는 독립 실행 단위
│
└─ 스레드(경계X)
    └─ 아키텍처 경계가 아니라 실행 흐름을 조직하는 방식
```

---

## 2. 경계 횡단하기

"경계를 횡단한다" => 한쪽 기능이 경계 너머의 다른 기능을 호출하거나 데이터를 전달한다

```text
[ 컴포넌트 A ]  ---- 경계 ---->  [ 컴포넌트 B ]

A가 B의 함수를 호출
A가 B에게 데이터를 전달
A가 B의 결과를 받음
A가 B의 타입이나 인터페이스를 사용
```

=> 소스코드 의존성도 함께 고려해야 함

---

## 3. 소스코드 의존성이 중요한 이유

```text
런타임 호출 방향
→ 실행 중 실제로 누가 누구를 호출하는가 (A -> B)

소스코드 의존성
→ 코드 안에서 누가 누구의 이름, 타입, 함수, 클래스를 알고 있는가
  (A가 B의 이름, 타입, 함수, 클래스 등을 알고 있음)
```

ex) A가 B를 알아야 컴파일/실행될 수 있음

```js
const b = new B();
b.doSomething();
```

=> 아키텍처 경계에서는 이 **소스코드 의존성의 방향**이 중요!  
왜 ? 변경은 보통 소스코드 의존성을 따라 전파되기 때문.

---

## 4. 경계는 변경 전파를 막는 방화벽?

뭔 말이냐하면,

```text
B가 바뀌었을 때
그 변경이 A까지 퍼지지 않도록 막는 구조
```

경계가 없거나 약하면 하나의 변경이 다른 쪽으로 쉽게 퍼지니까

```text
B 내부 변경
→ A도 수정 필요
→ A를 사용하는 C도 영향
→ 변경 범위 확산
```

경계가 잘 그어져 있으면?!

```text
B 내부 변경
→ 안정된 인터페이스는 유지
→ A는 영향받지 않음
```

```text
나쁜 구조

[ A ] ---> [ B 구현체 ]
              |
              v
          B 내부 변경
              |
              v
          A도 영향받음
```

```text
좋은 구조

[ A ] ---> [ 안정된 인터페이스 ] | 경계 | [ B 구현체 ]
                    ↑
                    |
              A는 이것만 앎

B 구현체가 바뀌어도
인터페이스가 유지되면 A는 영향받지 않음
```

> 경계는 호출 자체를 막는 것이 아니라, 변경이 넘어오는 것을 막는 장치라는 걸 "방화벽 어쩌고"로 말하고 싶었던 듯.

---

## 5. 두려운 단일체

모놀리식 구조를 저렇게 말한듯. 뭐가 왜 때문에 두렵다는 건지 알아보자..

단일체 : 모든 코드가 하나의 실행 파일, 하나의 프로세스, 하나의 주소 공간 안에 들어 있는 구조

```text
하나의 실행 파일
┌──────────────────────────────┐
│ GUI 코드                      │
│ 유스케이스 코드                │
│ 업무 규칙 코드                 │
│ DB 접근 코드                  │
│ 외부 API 코드                 │
└──────────────────────────────┘
```

실행 관점에서는 걍 하나의 덩어리.

```text
같은 프로세스
같은 주소 공간
함수 호출로 통신
네트워크 통신 없음
마샬링 없음
```

이게 뭐 반드시 나쁜 구조는 아님.
하나의 실행 파일 안에서도 **소스코드 수준의 경계**를 만들 수 있다.

---

## 6. 단일체 안의 경계

모놀리식 구조라도 내부 의존성을 규칙적으로 관리하면 논리적 경계를 만들 수 있음. "소스 수준 분리 모드"

```text
하나의 실행 파일
┌──────────────────────────────┐
│ UI Layer                     │
│------------------------------│
│ Use Case Layer               │
│------------------------------│
│ Business Rule Layer          │
│------------------------------│
│ DB Adapter                   │
└──────────────────────────────┘
```

```text
코드 의존성
UI → Use Case → Business Rule
DB Adapter → Business Rule 쪽 인터페이스
```

이렇게 하면 배포 단위는 하나여도,  
고수준 업무 규칙은 저수준 세부사항으로부터 어느 정도 독립적으로 유지됨.

---

## 7. 정적 다형성와 동적 다형성

정적 다형성 : 컴파일 시점에 어떤 함수가 호출될 지 결정되는 방식.
실행 전에 이미 어떤 코드가 연결될지 정해짐.

동적 다형성 : 런타임에 실제 객체에 따라 호출 대상이 결정되는 방식.

```text
고수준 코드 → 인터페이스 호출
실제 구현체는 런타임에 결정
```

```text
고수준 정책
    |
    v
인터페이스  <----- 저수준 구현체
```

그래서 모놀리식은 정적이라는 거야 동적이라는 거야. 헷갈렸는데 결론은.

모놀리식 실행 파일은 정적으로 링크될 수 있음.
모든 코드가 빌드 시점에 하나의 실행 파일로 묶이는 구조이기 때문에.
근데 그 안에서 의존성 방향 관리할 때는 동적 다형성을 활용 할 수 있다는 얘기였음.

```text
정적 링크
→ 실행 파일을 만드는 방식

동적 다형성
→ 코드 내부 의존성을 뒤집는 방식
```

```text
정적으로 링크된 모놀리식 실행 파일
→ 하나의 파일로 빌드됨

그 내부에서 동적 다형성 사용
→ 고수준 정책이 저수준 구현체에 직접 의존하지 않게 함
```

> 모놀리식이라도 내부를 규칙적으로 분리하고, 동적 다형성으로 의존성을 관리하면 고수준 컴포넌트를 저수준 세부사항으로부터 보호할 수 있음.

---

## 8. 모놀리식 내부의 경계 횡단

### 8.1 저수준 클라이언트가 고수준 서비스를 호출하는 경우

가장 단순한 형태의 경계 횡단

```text
[ 저수준 클라이언트 ] ---> [ 고수준 서비스 ]
```

이 경우 런타임 호출 방향과 컴파일타임 의존성이 같은 방향

```text
런타임 호출 방향
저수준 → 고수준

소스코드 의존성
저수준 → 고수준
```

---

### 8.2 고수준 클라이언트가 저수준 서비스를 호출해야 하는 경우

현실에서는 고수준 정책이 DB 저장, 파일 저장, 외부 API 호출 같은 저수준 기능을 필요로 하는 경우가 있음.

```text
[ 고수준 정책 ] ---> [ 저수준 구현체 ]
```

그런데 소스코드 의존성까지 이렇게 되면 저수준 구현체가 바뀔 때 고수준 정책도 영향을 받게 되므로 안 좋잖슴. 앞에서 의존성 역전하면서 다 배움.

```text
나쁜 구조
고수준 정책 → 저수준 구현체
```

그래서 의존성 역전을 사용.

```text
          런타임 호출
[ 고수준 정책 ] ----------------> [ 저수준 구현체 ]
       |                                  |
       | 소스코드 의존성                  | 소스코드 의존성
       v                                  v
[ 고수준이 정의한 인터페이스 ] <------------
```

> 실행 중에는 고수준 정책이 저수준 기능을 사용, 소스코드 의존성은 저수준 구현체가 고수준 쪽 인터페이스에 의존하도록 뒤집는다(역전).

---

## 9. 배포형 컴포넌트

배포형 컴포넌트 : 별도의 배포 가능한 단위로 분리된 컴포넌트

```text
.jar
.dll
.gem
npm package
python package
```

배포형 컴포넌트는 배포 수준 결합 분리 모드에 해당

```text
[ Application ]
    |
    +-- core.jar
    +-- db-adapter.jar
    +-- web-adapter.jar
```

의존관계는 핵심 쪽을 향하도록.

```text
web.jar  → core.jar
db.jar   → core.jar
```

```text
포함관계
→ 배포형 컴포넌트는 시스템의 일부

의존관계
→ 바깥 세부 컴포넌트가 핵심 컴포넌트를 향해야 함
```

## 10. 스레드(경계 아님 주의)

스레드 : 하나의 프로세스 안에서 실행 흐름을 나누는 방식

```text
프로세스
├─ 스레드 1
├─ 스레드 2
└─ 스레드 3
```

스레드는 같은 주소 공간을 공유

```text
같은 메모리 사용
같은 객체 접근 가능
같은 프로세스 안에서 실행
```

따라서 스레드는 컴포넌트 경계도 아니고 배포 단위도 아님.

```text
[ 하나의 프로세스 ]
┌──────────────────────────────┐
│ Component A                   │
│ Component B                   │
│ Component C                   │
│                               │
│ Thread 1 ────────────────▶    │
│ Thread 2 ───────▶             │
│ Thread 3 ─────────────────▶   │
└──────────────────────────────┘
```

스레드는 하나의 컴포넌트 안에서만 돌 수도 있고,  
여러 컴포넌트를 가로질러 실행될 수도 있음.

```text
스레드
→ 실행 흐름

컴포넌트
→ 코드, 배포, 책임 단위
```

## 11. 로컬 프로세스

로컬 프로세스 : 같은 컴퓨터 또는 같은 머신 안에서 실행되는 서로 다른 프로세스

```text
내 컴퓨터
├─ Process A: React 개발 서버
├─ Process B: Node 백엔드 서버
├─ Process C: Python 애플리케이션
└─ Process D: Local DB
```

이들은 모두 같은 컴퓨터 안에서 실행될 수 있지만,  
각각은 서로 다른 프로세스이면서, 자기만의 메모리 공간을 가짐(프로세스간 직접적인 메모리 공유 X).

```text
Process A 메모리 ≠ Process B 메모리
```

즉, 서로의 변수나 객체를 직접 가져다 쓸 수 없기때문에,
통신하려면 운영체제가 제공하는 기능을 사용해야 함.

```text
HTTP 요청
소켓
메일박스
메시지 큐
파이프
공유 메모리
```

```text
[ Process A ]  -- OS 통신 / 메시지 큐 / 소켓 -->  [ Process B ]
   주소공간 A                                      주소공간 B
```

```text
같은 컴퓨터 안에 있음
하지만 메모리는 분리되어 있음
서로의 객체를 직접 공유하지 못함
운영체제 통신을 통해서만 대화 가능
```

> 로컬 프로세스는 같은 컴퓨터 안에 있지만 주소 공간이 분리되어 있는 강한 물리적 경계이므로, 경계 횡단 비용이 발생(큼)

---

## 12. 로컬 프로세스에서 “서로의 존재를 모른다”는 말

로컬 프로세스들은 기본적으로 서로의 메모리를 직접 모른다.  
하지만 통신하도록 설계되어 있다면 서로의 존재를 알 수는 있다.

예를 들어 Node 백엔드가 `localhost:5432`의 DB에 접속한다면,  
Node 프로세스는 DB 프로세스의 존재를 알고 있는 것.

```text
존재를 알 수는 있음
하지만 메모리를 직접 공유하지는 않음
반드시 경계 너머 통신을 해야 함
```

=> 로컬 프로세스의 핵심은 “같은 컴퓨터 안에 있다”가 아니라,  
“서로 다른 주소 공간을 가지고 직접 메모리를 공유하지 않는다”

---

## 13. 서비스

서비스 : 네트워크를 통해 접근 가능한 독립 실행 단위

서비스는 같은 컴퓨터에서 실행될 수도 있고, 다른 컴퓨터에서 실행될 수도 있움.

```text
같은 컴퓨터 안

[ Service A ] -- localhost 통신 --> [ Service B ]
```

```text
다른 컴퓨터 사이

[ Service A on Server 1 ] -- network --> [ Service B on Server 2 ]
```

서비스의 핵심은 물리적 위치가 아닌 **"네트워크 통신"**.

```text
서비스
→ 독립적으로 실행됨
→ 네트워크를 통해 통신함
→ 같은 머신에 있을 수도 있고 다른 서버에 있을 수도 있음
```

서비스는 가장 강한 형태의 물리적 경계

```text
서비스 경계
→ 프로세스 분리
→ 주소 공간 분리
→ 네트워크 통신
→ 지연, 실패, 타임아웃, 재시도 고려
```

서비스는 외부 사용자에게 공개된 API일 수도 있고,  
시스템 내부에서만 사용하는 내부 서비스일 수도 있음

```text
외부 API 서비스
내부 인증 서비스
내부 결제 서비스
내부 알림 서비스
검색 서비스
로그 수집 서비스
```

> 서비스는 독립적으로 실행되며 네트워크를 통해 접근되는 가장 강한 물리적 경계

---

## 14. 로컬 프로세스와 서비스의 차이

로컬 프로세스와 서비스는 모두 독립된 실행 단위이고 메모리를 공유하지 않는다.  
차이는 통신 범위와 경계의 강도에 있다.

| 구분        | 로컬 프로세스                           | 서비스                                      |
| ----------- | --------------------------------------- | ------------------------------------------- |
| 위치        | 같은 컴퓨터 안                          | 같은 컴퓨터일 수도, 다른 컴퓨터일 수도 있음 |
| 메모리      | 분리                                    | 분리                                        |
| 통신        | OS IPC, 소켓, 큐 등                     | 네트워크 통신                               |
| 비용        | 함수 호출보다 비쌈                      | 보통 더 비쌈                                |
| 실패 가능성 | 있음                                    | 더 큼                                       |
| 예시        | 내 컴퓨터의 Node 프로세스와 DB 프로세스 | 인증 서버, 결제 서버, API 서버              |

정리하면 다음과 같다.

```text
로컬 프로세스
→ 같은 컴퓨터 안인데도 메모리가 분리되어 있어서 생기는 경계

서비스
→ 네트워크를 통해 연결될 수 있는 더 강한 실행 경계
```

## 15. 경계 강도 비교

| 형태              | 포함관계                    | 경계 강도 | 통신 방식                |               비용 |
| ----------------- | --------------------------- | --------: | ------------------------ | -----------------: |
| 단일체 / 모놀리식 | 하나의 실행 파일 안         |      약함 | 함수 호출                |               낮음 |
| 배포형 컴포넌트   | 별도 jar/dll/package        |      중간 | 함수 호출 또는 동적 링크 |          낮음~중간 |
| 스레드            | 프로세스 안 실행 흐름       | 경계 아님 | 공유 메모리              | 낮지만 동시성 위험 |
| 로컬 프로세스     | 같은 컴퓨터의 별도 프로세스 |      강함 | OS IPC, 소켓, 큐         |               높음 |
| 서비스            | 별도 프로세스/서버/네트워크 | 가장 강함 | 네트워크 통신            |          매우 높음 |

> 경계가 약할수록 통신은 빠르고 단순함. 경계가 강할수록 독립성은 커지지만 비용도 커짐

## 16. 포함관계와 의존관계

### 포함관계

포함관계 : 무엇 안에 무엇이 들어 있는지

```text
시스템
├─ 실행 파일
│  ├─ 컴포넌트
│  │  ├─ 클래스
│  │  └─ 함수
│  └─ 스레드
└─ 서비스
```

```text
하나의 프로세스
├─ 여러 컴포넌트
├─ 여러 객체
└─ 여러 스레드
```

### 의존관계

의존관계 : 누가 누구를 알고 사용하는지

```text
A → B
```

```text
A가 B를 안다
A가 B를 호출한다
A가 B의 타입이나 인터페이스에 의존한다
B가 바뀌면 A가 영향받을 수 있다
```

아키텍처에서 더 중요한 것은 보통 포함관계보다 의존관계.  
변경이 전파되는 방향은 포함관계가 아니라 의존관계를 따라가기 때문.

## 17. 정리

한 시스템 안에는 여러 강도의 경계가 함께 존재(단일한 형태가 아님.)

```text
어떤 경계는 단순 함수 호출처럼 가볍고
어떤 경계는 프로세스 통신처럼 무겁고
어떤 경계는 네트워크 서비스 통신처럼 매우 무거움
```

따라서 경계를 그을 때는 독립성만 볼 것이 아니라,  
통신 빈도와 지연 비용도 함께 고려해야 한다는 것.

```text
자주 오가는 관계
→ 가벼운 경계가 적합할 수 있음

독립성이 중요한 관계
→ 강한 경계가 필요할 수 있음
```
