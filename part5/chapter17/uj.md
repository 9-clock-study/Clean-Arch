# Clean Architecture 5부 17장 정리: 선 긋기(경계)

## 1. 경계선이란 무엇인가

소프트웨어 아키텍처에서 경계선은 시스템 내부의 중요한 부분과 덜 중요한 부분을 나누는 선

경계선을 긋는 목적은 변경의 영향이 핵심 업무 규칙까지 퍼지지 않게 하기 위함.
경계선을 그음으로써 의존성의 방향을 결정할 수 있다.

---

## 2. 아키텍트의 목표

아키텍트의 목표 : 필요한 시스템을 만들고 유지하는 데 드는 인적자원을 최소화하는 것

```text
인적자원 효율 저하 요인
→ 결합
```

결합 : 한 부분의 변경이 다른 부분까지 끌고 가는 정도

```text
결합이 강한 구조
→ 작은 변경도 여러 곳에 퍼짐
→ 수정해야 할 코드 증가
→ 테스트 범위 증가
→ 빌드와 배포 부담 증가
→ 개발 생산성 저하
```

=> 좋은 아키텍처는 결합이 생기는 위치와 방향을 통제하는 구조

---

## 3. 시스템을 컴포넌트 단위로 분할하기

경계선을 그으려면 먼저 시스템을 컴포넌트 단위로 분할

```text
시스템
→ 핵심 업무 규칙 컴포넌트
→ 세부사항 컴포넌트
```

핵심 업무 규칙 컴포넌트는 시스템의 중심.  
나머지 컴포넌트들은 핵심 업무 규칙을 실행하기 위해 필요한 세부사항.

```text
핵심 업무 규칙
→ 시스템이 반드시 지켜야 하는 중요한 정책

세부사항
→ DB, UI, 웹, 프레임워크, 외부 API, 통신 방식 등
```

```text
핵심 업무 규칙 컴포넌트 외의 나머지 컴포넌트는 플러그인
```

---

## 4. 의존성 방향

경계선을 제대로 긋기 위해서는 의존성 방향이 중요.

```text
저수준(세부사항) → 고수준(정책)
```

```text
나쁜 구조
핵심 업무 규칙 → DB
핵심 업무 규칙 → UI
핵심 업무 규칙 → 프레임워크

좋은 구조
DB → 핵심 업무 규칙
UI → 핵심 업무 규칙
프레임워크 → 핵심 업무 규칙
```

```text
실행 흐름
UI → 유스케이스 → DB

소스코드 의존성
UI → 유스케이스 ← DB 구현체
```

이렇게 해야 핵심 업무 규칙이 DB나 UI의 변경에 끌려다니지 않음.

---

## 5. 플러그인 아키텍처

플러그인 아키텍처 : 핵심 시스템을 안정적으로 유지하고,  
바깥의 세부사항을 끼워 넣거나 교체할 수 있게 만드는 구조.

```text
핵심 업무 규칙
← UI 플러그인
← DB 플러그인
← 웹 프레임워크 플러그인
← 외부 API 플러그인
```

플러그인은 핵심 업무 규칙이 요구하는 인터페이스나 규칙에 맞춰 들어온다.

```text
핵심 업무 규칙
→ 무엇을 해야 하는지 정의

플러그인
→ 그것을 어떤 기술로 실행할지 담당
```

> 핵심 업무 규칙은 세부 기술을 모르고, 세부 기술은 핵심 업무 규칙에 맞춰 붙는 구조

---

## 6. 왜 경계선을 그어야 하는가

경계선을 긋지 않으면 세부사항이 핵심 업무 규칙 안으로 들어옴

그 결과 다음 문제 발생

```text
DB 변경이 업무 규칙 변경으로 이어짐
UI 변경이 유스케이스 변경으로 이어짐
통신 방식 변경이 핵심 로직 변경으로 이어짐
프레임워크 교체가 시스템 전체 수정으로 이어짐
```

=> 세부사항 하나를 바꾸는 일이 시스템 전체를 흔드는 일이 될 수 있음

경계선을 제대로 그으려면,

```text
바뀌기 쉬운 것과 바뀌면 안 되는 것을 분리
세부사항의 변경이 핵심 정책에 영향을 주지 않게 함
중요한 코드를 덜 중요한 코드로부터 보호
```

---

## 7. 강한 결합도를 보여주는 예시(책에 나옴)

책의 예시는 기존 레코드에 새로운 필드를 추가하는 상황.

겉으로는 단순한 변경.

```text
기존 레코드에 새로운 필드 1개 추가
```

하지만 GUI 티어, 미들웨어 티어, DB 티어가 강하게 결합되어 있다면,  
이 변경은 모든 티어와 메시지 프로토콜로 퍼진다.

```text
                  필드 1개 추가
                       |
                       v
        -------------------------------------
        |                |                 |
        v                v                 v
 [ GUIRecord ]   [ MiddlewareRecord ]   [ DBRecord ]
   수정               수정                 수정

        GUI <-------> Middleware <-------> DB
          |               |                  |
          |---- P1 -----> |                  |
          |<--- P2 ------ |                  |
                          |---- P3 --------> |
                          |<--- P4 --------- |

P1: GUI -> Middleware
P2: Middleware -> GUI
P3: Middleware -> DB
P4: DB -> Middleware

각 프로토콜마다
  - 송신 핸들러 1개
  - 수신 핸들러 1개

=> 총 4개 프로토콜 × 2 = 8개 핸들러

최종적으로 다시 빌드해야 하는 것
  - GUI 실행 파일
  - Middleware 실행 파일
  - DB 실행 파일
```

그래서,

```text
변경은 1개
하지만 수정 포인트는 다수
```

=> 계층 간 결합이 강하면,
작은 데이터 변경도 시스템 전체의 수정, 재빌드, 재검증으로 이어질 수 있다는 점이 중요.

---

## 8. 메시지와 통신이 만드는 추가 비용

티어를 물리적으로 분리하면 각 실행 파일은 단순히 자기 업무 로직만 처리하지 않는다.  
티어 사이의 통신과 데이터 변환을 위한 부가 작업도 함께 담당해야 한다.

```text
객체 초기화
직렬화
역직렬화
마샬링
언마샬링
메시지 구성
메시지 파싱
소켓 통신
타임아웃 관리
재시도 시나리오
에러 처리
프로토콜 호환성 관리
```

```text
[ GUI 실행 파일 ]
   |
   | 요청 메시지 구성
   | 직렬화 / 마샬링
   | 소켓 통신
   v
[ Middleware 실행 파일 ]
   |
   | 메시지 파싱
   | 언마샬링 / 역직렬화
   | 객체 초기화
   |
   | DB 요청 메시지 구성
   | 직렬화 / 마샬링
   | 소켓 통신
   v
[ DB 실행 파일 ]
   |
   | 메시지 파싱
   | 언마샬링 / 역직렬화
   | 객체 초기화
   | DB 처리
   |
   | 응답 메시지 구성
   | 직렬화 / 마샬링
   v
[ Middleware 실행 파일 ]
   |
   | 응답 파싱
   | 언마샬링
   | GUI용 메시지 재구성
   v
[ GUI 실행 파일 ]
```

=> 서비스나 티어를 나누는 것은 독립성을 줄 수 있지만,  
동시에 경계마다 통신, 변환, 장애 처리 비용을 만든다.

---

## 9. 경계선과 물리적 분리

```text
경계선
→ 의존성 방향과 변경 영향 범위를 나누는 설계적 분리

물리적 분리
→ 실행 파일, 프로세스, 서비스, 서버를 실제로 나누는 운영적 분리
```

아키텍처적으로는 경계선을 먼저 잘 그어야 한다.  
그 후 필요에 따라 물리적 분리를 선택.

처음부터 모든 경계를 서비스나 서버 단위로 나누면,  
통신 비용과 배포 복잡성이 불필요하게 커질 수 있음

```text
좋은 접근
→ 먼저 소스 코드 수준에서 경계를 명확히 함
→ 필요하면 배포 단위로 분리
→ 더 필요하면 서비스 단위로 분리
```

=> 경계는 일찍 그을 수 있지만,  
물리적 분리는 가능한 한 늦게 결정하는 것이 좋다!

## 10. 책 읽으면서 모르는 개념 정리

### 마샬링(Marshalling)

마샬링 : 한 객체의 메모리 표현 방식을 저장이나 전송에 적합한 다른 데이터 형식으로 변환하는 과정(by Wiki)

- 데이터를 프로그램의 서로 다른 부분 간에 이동하거나,  
  한 프로그램에서 다른 프로그램으로 이동할 때 사용

- 직렬화와 유사하지만, 마샬링은 보통 프로세스 간 호출, 원격 호출, 네트워크 통신 같은 맥락에서 더 넓게 쓰임

### 직렬화(Serialization)

직렬화 : 객체의 상태를 저장하거나 전송하기 위해  
객체를 바이트 스트림 또는 연속적인 데이터 형식으로 변환하는 과정

ex) 객체를 파일에 저장하거나 네트워크로 보내기 위해 JSON, XML, 바이너리 데이터 등으로 바꾸는 것

### 서버 팜(Server Farm)

서버 팜 : 여러 대의 서버를 모아 놓고 요청을 나눠 처리하게 만든 서버 집합

```text
서버 팜
→ 여러 서버를 묶어 하나의 큰 처리 시스템처럼 운영하는 구조

사용자 요청
   ↓
로드 밸런서
   ↓
 -------------------------
 | 서버 1 | 서버 2 | 서버 3 |
 -------------------------
```

서버 팜을 사용하면 다음이 가능해지는데,

```text
처리량 증가
트래픽 분산
장애 대응
확장성 확보
```

서버 팜 역시 운영 복잡성을 만듦

```text
배포 복잡성 증가
서버 간 상태 관리 문제
네트워크 통신 증가
동기화 문제 발생 가능
```

따라서 서버 팜은 운영 확장성을 위한 선택지이지만,  
아키텍처 경계와 결합을 잘못 설계하면 복잡성을 더 키울 수 있다고 한다.
