# 17장 경계: 선 긋기

“좋은 시스템 아키텍처란 이러한 결정(업무 요구사항과 무관한 결정)이 부수적이며, 결정을 연기할 수 있는 아키텍처다”

소프트웨어 아키텍처는 **선, 경계를 긋는 기술**이다

경계의 역할은 소프트웨어 요소를 서로 분리하고, 경계 한편에 있는 요소가 반대편에 있는 요소를 알지 못하도록 막음

너무 일찍 내려진 결정에 따른 결합(coupling)은 **인적자원의 효율**을 떨어트린다

좋은 아키텍처란 다음과 같다.

- 이른 결정 : 시스템의 업무 요구사항(유스케이스)와 무관한 결정
- 예시 : 프레임워크, DB, 웹 서버, 유틸리티 라이브러리, 의존성 주입에 대한 결정 등
- 이러한 결정이 부수적이며, 결정을 연기할 수 있는 아키텍처

경계를 긋는 방법은 관련이 있는 것과 없는 것 사이에 선을 그어야 한다.

### 업무 규칙과 데이터베이스

- DB는 업무 규칙이 간접적으로 사용할 수 있는 도구
- 업무 규칙은 스키마, 쿼리, DB와 관련된 나머지 세부 사항에 대해 어떤 것도 알아서는 안 된다
- 업무 규칙이 알아야 할 것은 데이터를 가져오고 저장할 때 사용할 수 있는 함수 집합이 있다는 사실
- 함수 집합을 통해서 DB를 인터페이스 뒤로 숨길 수 있다

### 경계선

- 경계선은 DB Interface와 DB Access 사이에 그어진다
- DB Access에서 출발하는 화살표는 DB Access 클래스로부터 바깥쪽으로 향함
- DB Access가 존재한다는 사실을 아는 클래스는 없다는 의미다

**화살표 방향의 의미**

- 화살표의 방향을 보면 DB에서 비즈니스 룰로 향하고 있음
- DB는 비즈니스 룰에 대해 알고 있지만 비즈니스 룰은 DB에 대해 알지 못한다는 것을 알 수 있음
- 두 컴포넌트 사이에 이러한 경계선을 긋고 화살표의 방향이 비즈니스 룰을 향하도록 만들었으므로, 비즈니스 룰에서는 어떤 종류의 DB도 사용할 수 있음
- DB 컴포넌트는 다양한 구현체로 교체될 수 있으며, 비즈니스 룰은 이에 대해 개의치 않음

**업무 규칙과 GUI**

- 비디오 게임의 사용자 경험은 인터페이스에 의해 좌우됨
- 인터페이스의 뒷단에는 인터페이스를 조작하는 모델(데이터 구조와 함수로 구성된 정교한 집합)이 존재
- 모델에게 중요한 것은 인터페이스가 아닌 업무 규칙
- 예시) 비디오 게임

**경계선과 화살표의 방향과 의미**

- GUI와 BusinessRules가 경계선에 의해 분할됨
- GUI가 BusinessRules를 신경쓰는 것을 알 수 있음

### 플러그인 아키텍처

플러그인 아키텍처의 정의

- 시스템의 핵심은 고수준 정책(비즈니스 룰)으로 구성되고, 저수준 구현(세부사항)은 나중에 ‘꽂는(plug-in)’ 방식으로 설계하는 아키텍처 패턴
- 시스템의 주요 동작은 추상화된 인터페이스에 의존하고, 구체적인 구현은 외부에서 독립적으로 연결될 수 있도록 만든 구조

- 업무 규칙과 무관한 컴포넌트 추가는 시스템에서 서드파티 플러그인을 사용할 수 있도록한 패턴과 동일
- 사용자 인터페이스는 플러그인 형태로 고려되었기 때문에 수 많은 사용자 인터페이스를 플러그인 형태로 연결 가능
- DB도 마찬가지로 플러그인으로 다루기로 결정했기 때문에 다양한 임의의 DB 기술로 대체 가능

### 플러그인과 단일 책임 원칙

- 경계는 **변경의 축이 있는 지점**에 그어짐
- 업무 규칙과 **다른 시점, 다른 속도로 변경되는 컴포넌트와 업무 규칙 사이에는 반드시 경계가 필요**
- 시스템을 플러그인 아키텍처로 배치하면 변경이 전파될 수 없는 방화벽 생성 가능

### 결론

### 소프트웨어 아키텍처에 경계선 긋기

1. 시스템을 컴포넌트 단위로 **분할**
2. 컴포넌트 사이의 **화살표가 특정 방향, 즉 핵심 업무를 향하도록** 이들 컴포넌트의 소스를 배치

### 컴포넌트 분류

- 핵심 업무 규칙
- 플러그인: 핵심 업무와는 직접적인 관련이 없지만 필수 기능 포함

### 소프트웨어 경계의 의미?

- 의존성 역전 원칙과 안정된 추상화 원칙 응용
- 의존성 화살표는 저수준 세부사항에서 고수준의 추상화를 향하도록 배치됨

### 느낀점

이번 장에서는 DB와 비즈니스 로직의 **경계선과 플러그인 아키텍처**에 대한 설명이 주로 이루어졌다.

나는 포트폴리오에서 아키텍처 그리는 게 정말 귀찮았다.

그 이유는 이번 장에서 설명한 경계선들이 정말 애매했던 게 가장 컸다.

ERD도 그렇고 시스템 아키텍처도 항상 연결하고자 하는 선들이 어떤 식으로 표현해야 명확하게 다른 사람에게도 분명하게 전달되는지 항상 고민이 된다.

대규모 시스템 설계 책 스터디도 해보고, 이 책을 기반한 화이트보드 설계도 진행했지만

아직까지도 아키텍처를 직접 그리는 것이 참 어렵다고 생각한다.

최근 이러한 시스템 아키텍처를 그리는 테스트를 보게 되었는데,

시스템 아키텍처의 필요한 기술도 고려하는 것도 어렵지만 

결국 기술들을 어떻게 연결하느냐가 관건이었다.

결국 아키텍처는 컴포넌트를 잘 분류하고, 컴포넌트 사이의 흐름이 잘 향하도록 컴포넌트를 연결해야 한다는 느낌이 들었다.

또한 이번 장에서 플러그인 아키텍처를 보며, 처음 스터디를 시작할 때 말했던 내용이 이어진다고 생각했다.

플러그인 아키텍처에 대한 정의를 몰라서 구체적인 용어가 없다고 생각했는데

소프트웨어 공학 안에 아키텍처가 있고, 우리가 현재 사용하는 AI도 결국 플러그인 아키텍처라고 볼 수 있지 않을까? 라고 생각이 들었다…
