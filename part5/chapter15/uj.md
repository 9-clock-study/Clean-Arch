# Clean Architecture 5부 15장 정리: 아키텍처란?

```text
아키텍처의 목적
→ 시스템의 생명주기를 지원하는 것

좋은 아키텍처
→ 시스템을 쉽게 이해하고, 쉽게 개발하며, 쉽게 유지보수하고, 쉽게 배포하게 해주는 구조
```

=> 아키텍처는 시스템이 오랫동안 살아남고 변화할 수 있도록 만드는 구조적 판단

---

## 1. 아키텍처의 주된 목적

아키텍처의 주된 목적은 "시스템의 생명주기를 지원"하는 것

```text
시스템의 생명주기
→ 개발
→ 배포
→ 운영
→ 유지보수
→ ...
```

=> 이 모든 과정에서 비용을 줄이고 생산성을 높이는 방향으로 작동하도록!

---

## 2. 좋은 아키텍처란 무엇인가

```text
시스템을 쉽게 이해할 수 있음
시스템을 쉽게 개발할 수 있음
시스템을 쉽게 유지보수할 수 있음
시스템을 쉽게 배포할 수 있음
```

```text
이해하기 쉬운 구조
→ 새로운 개발자가 시스템의 큰 흐름을 빠르게 파악 가능

개발하기 쉬운 구조
→ 기능을 추가할 때 불필요한 충돌과 복잡성이 적음

유지보수하기 쉬운 구조
→ 변경이 생겼을 때 수정해야 할 범위가 제한됨

배포하기 쉬운 구조
→ 시스템 전체를 매번 건드리지 않고 필요한 부분을 안정적으로 배포 가능
```

=> 좋은 아키텍처는 소프트웨어의 변화 비용을 줄이는 구조

---

## 3. 아키텍처의 궁극적 목표

```text
시스템 수명과 관련된 비용은 최소화
프로그래머의 생산성은 최대화
```

소프트웨어는 시간이 지날수록 점점 복잡해짐.
기능이 추가되고, 요구사항이 바뀌고, 기술 환경도 변하기 때문.

아키텍처가 좋지 않으면 시간이 지날수록 이런 문제를 야기.

```text
작은 수정에도 많은 코드가 영향받음
새 기능 추가가 점점 어려워짐
버그 수정이 다른 버그를 만듦
배포가 부담스러워짐
개발자가 시스템을 이해하기 어려워짐
```

## <=> 좋은 아키텍처는 시스템이 커져도 변경 비용이 급격히 증가하지 않도록 함

## 4. 아키텍트의 목표

아키텍트의 핵심 목표는 시스템에서 **정책**을 가장 중요한 요소로 식별하는 것

```text
아키텍트의 목표
→ 시스템에서 정책을 핵심 요소로 식별
→ 세부사항이 정책에 영향을 주지 않도록 구조 설계
```

여기서 중요한 것은 '정책'과 '세부사항'을 구분하는 일!

아키텍트는 시스템의 중심에 무엇이 있어야 하는지,  
그리고 무엇을 바깥으로 밀어낼 수 있는지를 잘 판단할 수 있어야 함.

---

## 5. 정책이란 무엇인가

정책 : 시스템이 반드시 지켜야 하는 중요한 규칙. 시스템 목적과 직접 연결되는 부분.

```text
정책
→ 모든 업무 규칙과 업무 절차를 구체화한 것
```

```text
업무 규칙
업무 흐름
판단 기준
계산 규칙
상태 변경 규칙
사용자가 기대하는 핵심 행위
```

정책은 시스템이 어떤 기술을 쓰든 유지되어야 하는 핵심(시스템이 "무엇을 해야하는가").

```text
어떤 조건에서 사용자가 승인되는가
어떤 절차로 주문이 완료되는가
어떤 기준으로 금액이 계산되는가
어떤 상태에서 다음 단계로 넘어갈 수 있는가
```

---

## 6. 세부사항이란 무엇인가

세부사항 : 정책을 실행하기 위해 필요한 "기술적 수단"

```text
입출력 장치
데이터베이스
웹 시스템
웹 프레임워크
외부 API
UI
파일 시스템
네트워크
```

세부사항은 필요하지만, 정책의 본질을 결정하지는 않음.

예를 들어,

- 데이터베이스를 MySQL에서 PostgreSQL로 바꾸는 것이
  업무 규칙 자체가 바뀌어서는 안 됨.

- 웹 프레임워크를 바꾼다?
  그게 시스템의 핵심 업무 절차도 달라지게 해선 안 됨.

---

## 7. 정책과 세부사항의 관계

좋은 아키텍처는 정책이 세부사항에 의존하지 않아야 함.

```text
정책은 세부사항에 관한 지식을 가지면 안 됨
정책은 세부사항에 의존하면 안 됨
세부사항은 정책의 행위에 영향을 주면 안 됨
```

이 구조가 중요한 이유는 세부사항이 자주 바뀌기 때문.

```text
DB는 바뀔 수 있음
프레임워크는 바뀔 수 있음
UI는 바뀔 수 있음
외부 API는 바뀔 수 있음
입출력 방식은 바뀔 수 있음
```

---

## 8. 좋은 아키텍트의 역할

```text
좋은 아키텍트
→ 세부사항을 정책으로부터 가려냄
→ 정책이 세부사항을 알지 못하게 만듦
→ 정책이 세부사항에 의존하지 않게 만듦
→ 세부사항에 대한 결정을 가능한 한 늦게 미룸
```

**결정을 늦게 미룬다**라는 표현..

=> 아키텍처는 모든 기술 결정을 빨리 확정하는 일이 아님.
좋은 아키텍처는 바뀔 가능성이 높은 결정에 대해 최대한 늦게 해도 되도록 만드는 것.

```text
DB를 나중에 선택할 수 있게 하기
프레임워크를 나중에 바꿀 수 있게 하기
UI를 나중에 교체할 수 있게 하기
외부 시스템 연동 방식을 나중에 바꿀 수 있게 하기
```

=> 좋은 아키텍처는 중요한 정책을 먼저 안정적으로 세우고,  
세부 기술은 가능한 한 나중에 선택할 수 있도록 여지를 남겨줘야 함.

---

## 9. 세부사항을 미룬다는 것의 의미

```text
기술을 사용하되, 핵심 정책이 그 기술에 종속되지 않게 하기
```

=> 해당 세부사항(기술스택들)이 시스템의 중심 구조를 결정하게 두지 않는 것

```text
나쁜구조 예시 ->
프레임워크 구조가 곧 시스템 구조가 되는 경우
데이터베이스 테이블 구조가 곧 업무 규칙이 되는 경우
UI 흐름이 곧 유스케이스 구조가 되는 경우
```

=> 이 말이, "세부사항은 시스템의 중심이 아니라 가장자리로 밀려나야 한다"는 말.

---

## 10. 15장 정리

```text
아키텍처
→ 시스템의 생명주기를 지원하는 구조

아키텍처의 목적
→ 시스템의 생명주기 지원

좋은 아키텍처
→ 이해, 개발, 유지보수, 배포를 쉽게 만듦

궁극적 목표
→ 비용 최소화, 생산성 최대화

아키텍트의 역할
→ 정책과 세부사항을 분리

핵심 방향
→ 정책은 중심에, 세부사항은 바깥에
```

```text
정책
→ 시스템이 반드시 지켜야 하는 업무 규칙과 업무 절차

세부사항
→ DB, UI, 프레임워크, 입출력 장치, 외부 시스템 같은 기술적 선택
```

좋은 아키텍처의 핵심

> 중요한 정책은 세부사항으로부터 보호하고,  
> 세부사항에 대한 결정은 가능한 한 오래 미룰 수 있게 만드는 것

=> 시스템의 중심을 기술이 아니라 정책에 두는 것.
