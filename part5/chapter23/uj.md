# Clean Architecture 5부 23장 정리: 프레젠터와 험블 객체

## 1. 프레젠터와 뷰

프레젠터와 뷰의 역할

```text
Presenter
→ 출력 데이터를 화면에 보여주기 좋은 형식으로 재구성

View
→ 재구성된 데이터를 실제 화면에 로드
```

ex) 유스케이스가 다음과 같은 출력 데이터를 만든다고 하면.

```text
주문 상태: CANCELLED
취소 일자: 2026-06-19
환불 금액: 15000
```

프레젠터 => 이 데이터를 화면 표시용으로 바꿈.

```text
주문 상태: 취소 완료
취소 일자: 2026년 6월 19일
환불 금액: 15,000원
버튼 표시 여부: false
안내 문구: 환불이 정상적으로 접수되었습니다.
```

뷰 => 이 데이터를 실제 화면에 그림.

```text
텍스트 표시
버튼 숨김
색상 적용
화면 렌더링
```

## 2. 험블 객체 패턴이란?!

험블 객체 패턴 : 테스트하기 어려운 행위와 테스트하기 쉬운 행위를 분리하는 패턴

```text
험블 객체 패턴
→ 테스트하기 어려운 행위를 한 객체로 몰아냄
→ 테스트하기 쉬운 로직은 별도 객체에 남김
```

```text
테스트하기 쉬운 객체
→ 판단, 계산, 변환, 규칙

테스트하기 어려운 객체
→ 화면 출력, DB 접근, 네트워크 호출, 파일 입출력, 프레임워크 호출
```

> 험블 객체는 테스트하기 어려운 외부 행위를 맡고, 중요한 판단 로직은 테스트하기 쉬운 객체에 남기기 위한 객체

---

## 3. 테스트하기 쉽고 어려움의 기준

```text
테스트하기 쉬운 것
→ 입력을 주면 결과가 예측 가능함
→ 외부 환경이 없어도 실행 가능함
→ 빠르게 실행됨
→ 화면, DB, 네트워크, 파일 시스템이 필요 없음
→ 단위 테스트로 검증 가능함
```

```text
테스트하기 어려운 것
→ 실제 화면 렌더링이 필요함
→ DB 연결이 필요함
→ 네트워크 상태에 영향을 받음
→ 파일 시스템이나 운영체제에 의존함
→ 프레임워크 실행이 필요함
→ 느리고 불안정함
```

“쉽다/어렵다”는  
-> 코드가 논리적으로 쉽다는 뜻(X)
-> **자동화된 테스트로 검증하기 쉬운가**(O)

> 그러니까, 테스트하기 쉬운 객체는 외부 환경 없이 입력과 출력만으로 검증할 수 있는 객체

## 4. View와 Presenter의 관계

View는 험블 객체에 해당

```text
View
→ 실제 화면을 다룸
→ GUI 프레임워크에 의존
→ 렌더링 결과 확인이 어려움
→ 테스트하기 어려움
→ Humble Object
```

Presenter는 테스트하기 쉬운 객체(험블객체의 반대)

```text
Presenter
→ 출력 데이터를 화면 표시용 데이터로 변환
→ 계산과 변환 로직을 가짐
→ 화면 없이도 테스트 가능
→ 테스트하기 쉬움
```

```text
[ Use Case Output ]
        |
        v
[ Presenter ]
        |
        | 화면 표시용 데이터 생성
        v
[ View Model ]
        |
        v
[ View ]
        |
        | 실제 화면에 로드
        v
[ Screen ]
```

여기서 테스트 대상은 주로 Presenter

```text
입력: 유스케이스 출력 데이터
검증: View Model이 올바르게 만들어졌는가
```

```text
View의 역할
→ Presenter가 만든 데이터를 화면에 그대로 표시
```

## 5. 왜 View가 험블 객체임?

화면은 테스트하기 어렵다고 함.

```text
왜?
-> 렌더링 엔진 필요
-> UI 프레임워크 필요
-> 사용자 이벤트 필요
-> 화면 상태 확인 필요
-> 환경에 따라 결과가 달라질 수 있음
```

=> 화면 관련 판단 로직을 View 안에 많이 넣으면 테스트가 어려워짐

나쁜 구조 예시

```text
View
→ 날짜 형식 변환
→ 금액 포맷팅
→ 버튼 표시 여부 판단
→ 상태 메시지 선택
→ 실제 화면 렌더링
```

좋은 구조 예시

```text
Presenter
→ 날짜 형식 변환
→ 금액 포맷팅
→ 버튼 표시 여부 판단
→ 상태 메시지 선택

View
→ Presenter가 만든 데이터를 화면에 표시
```

이렇게 하면 Presenter에서 화면 없이(without) 테스트할 수 있잖슴

> View를 험블 객체로 만드는 이유는 화면 출력 자체만 View에 남기고, 테스트 가능한 표시 로직은 Presenter로 분리하기 위해서

## 6. 험블 객체 경계란?!

```text
험블 객체 경계
→ 테스트 가능한 로직과 테스트하기 어려운 외부 행위를 나누는 경계
```

도식으로 보면 다음과 같다.

```text
테스트하기 쉬운 쪽              테스트하기 어려운 쪽
┌──────────────┐     경계     ┌──────────────┐
│ Presenter    │ ----------> │ View         │
│ 변환/판단     │              │ 화면 출력     │
└──────────────┘              └──────────────┘
```

```text
테스트 어려운 행위를 최소화
중요한 판단 로직을 테스트 가능한 쪽에 배치
외부 세부사항을 바깥으로 밀어냄
```

## 7. 유스케이스 인터랙터와 DB Gateway

험블 객체 패턴은 DB 경계에서도 비슷하게 나타남

```text
Use Case Interactor
→ 애플리케이션 특화 업무 규칙
→ 테스트하기 쉬운 객체

DB Gateway Interface
→ 유스케이스가 DB에 접근하기 위해 사용하는 인터페이스

DB / ORM
→ 실제 DB 접근
→ 테스트하기 어려운 세부사항
→ Humble Object에 가까움
```

```text
[ Use Case Interactor ]
          |
          v
[ Gateway Interface ]
          ^
          |
[ Gateway Implementation / ORM ]
          |
          v
[ Database ]
```

유스케이스 인터랙터는 실제 DB는 모르는채,
Gateway Interface를 호출한다.

테스트할 때는 실제 DB 대신 Mock이나 Fake Gateway를 넣을 수 있음.

```text
테스트 시

[ Use Case Interactor ]
          |
          v
[ Mock Gateway / Fake Gateway ]
```

운영 시에는 실제 DB 구현체가 들어감

```text
운영 시

[ Use Case Interactor ]
          |
          v
[ Gateway Implementation / ORM ]
          |
          v
[ Database ]
```

## 8. 유스케이스 인터랙터는 왜 험블 객체가 아닌가

유스케이스 인터랙터는 테스트해야 하는 핵심 로직을 담고 있기 때문

```text
유스케이스 인터랙터
→ 애플리케이션 특화 업무 규칙을 캡슐화
→ 입력을 받아 처리 흐름을 수행
→ 엔티티를 호출
→ 출력 데이터를 생성
```

=> 유스케이스 인터랙터는 험블 객체로 밀어낼 대상이 아니다.
(험블 객체 == 테스트하기 어려운 외부 행위를 담당하는 객체)

```text
험블 객체
→ View
→ DB 구현체
→ ORM 호출부
→ 네트워크 호출부
→ 파일 시스템 호출부
```

## 9. “캡슐화하는 것”과 험블 객체의 관계

캡슐화 : 어떤 책임을 객체 안에 묶는 것
어떤 책임을 묶느냐에 따라 테스트 가능성이 달라짐

```text
유스케이스 인터랙터
→ 애플리케이션 특화 업무 규칙을 캡슐화
→ 테스트해야 할 핵심 로직

험블 객체
→ 테스트하기 어려운 외부 행위를 캡슐화
→ 가능하면 단순하게 유지
```

=> “캡슐화했다”는 사실만으로 험블 객체가 되는 것은 아님

```text
그 객체가 테스트하기 어려운 외부 행위를 담당하는가?
그 객체에 중요한 판단 로직이 들어 있는가?
```

> 험블 객체 여부는 캡슐화 자체가 아니라, 테스트하기 어려운 외부 행위를 맡고 있는지로 판단!

## 10. Gateway Interface, ORM, DB 사이의 험블 객체 경계

DB 접근에서도 험블 객체 경계가 만들어진다.

```text
테스트하기 쉬운 쪽              테스트하기 어려운 쪽
┌──────────────────┐   경계   ┌──────────────────┐
│ Use Case          │ ------> │ Gateway Impl      │
│ Gateway Interface │         │ ORM / DB          │
└──────────────────┘          └──────────────────┘
```

여기서 테스트하기 어려운 부분은 실제 DB와 ORM 시스템

```text
ORM
→ 프레임워크 설정 필요
→ 실제 DB 연결 필요
→ 쿼리 실행 필요
→ 느리거나 환경 영향을 받음

DB
→ 외부 시스템
→ 상태 관리 필요
→ 테스트 데이터 준비 필요
```

> Gateway Interface는 유스케이스를 테스트하기 쉬운 쪽에 남기고, ORM과 DB를 험블 객체 쪽으로 밀어내기 위한 경계다.

## 11. 서비스 리스너

서비스 리스너 : 외부 요청을 받아 유스케이스를 호출

```text
Service Listener
→ 네트워크 요청 수신
→ 요청 데이터 파싱
→ 유스케이스 입력 모델 생성
→ 유스케이스 호출
→ 응답 반환
```

서비스 리스너는 네트워크, 프레임워크, 프로토콜과 가까움.
=> 테스트하기 어렵고 바깥쪽 세부사항에 해당(험블객체)

```text
[ Network / HTTP / Message ]
          |
          v
[ Service Listener ]
          |
          v
[ Use Case Interactor ]
```

> 서비스 리스너는 외부 요청을 받아 유스케이스에 전달하는 험블 객체에 가까운 바깥쪽 연결 객체

## 12. 각 아키텍처 경계마다 험블 객체 패턴이 숨어 있다는 말

“각 아키텍처 경계마다 험블 객체 패턴을 발견할 수 있다”는 말(책 p.227)
=> 경계의 한쪽에는 보통 테스트하기 어려운 세부사항이 있고,  
다른 한쪽에는 테스트 가능한 핵심 로직이 있다는 뜻

```text
화면 경계
Presenter ↔ View

DB 경계
Use Case / Gateway Interface ↔ ORM / DB

서비스 경계
Use Case Interactor ↔ Service Listener

외부 API 경계
Use Case ↔ API Client

파일 시스템 경계
Use Case ↔ File Adapter
```

각 경계에서의 공통 구조

```text
테스트하기 쉬운 핵심 로직
        |
        | 경계
        v
테스트하기 어려운 외부 세부사항
```

```text
[ 테스트 가능한 정책/로직 ]
              |
              v
[ 인터페이스 / 경계 ]
              |
              v
[ 험블 객체 ]
              |
              v
[ 외부 세계: UI, DB, Network, File, Framework ]
```

=> 험블 객체 패턴은 특정 UI 패턴만 말하는 것이 아니라,  
아키텍처 전반에서 세부사항을 바깥으로 밀어내는 방식으로 반복해서 나타나는 것을 말함.
