# 프레젠터와 험블 객체

## 험블 객체 패턴

디자인 패턴중 하나로, 테스트하기 어려운 행위와 테스트하기 쉬운 행위를 단위 테스트 작성자가 분리하기 쉽게 하는 방법
행위들을 두 개의 모듈 or 클래스로 나눈다 이들 중 하나가 험블이다.
가장 기본적인 본질을 남기고 테스트하기 어려운 행위를 모두 험블 객체로 옮긴다. 나머지 모듈에는 테스트하기 쉬운 행위를 모두 옮긴다.

e.g) GUI의 경우 보여주는 부분은 테스트하기가 어렵지만 GUI에서 수행하는 행위는 쉽게 테스트가능하다.

이번 장에서는 험블객체를 어떻게 나누는지에 대한 장으로 경계 나누기의 일종 같다.

## 프레젠터와 뷰

뷰는 험블 객체이고 테스트하기 어렵다. 뷰는 데이터를 GUI로 이동시킬 뿐 데이터를 직접 처리하지는 않는다.
프레젠터는 애플리케이션으로부터 데이터를 받아서 화면에 표현할 수 있는 포멧으로 만드는 것.

이를통해 뷰는 데이터를 화면으로 전달하는 간단한 일만 처리하도록 남김(다른 행위가 끼어있으면 테스트 하기 어려움)

## 데이터베이스 게이트웨이

유스케이스 인터렉터와 데이터베이스 사이에는 데이터베이스 게이트웨이가 위치한다. 이 게이트웨이는 다형적 인터페이스로 애플리케이션이 데이터베이스에 수행되는 생성,조회,삭제와 같은 모든 작업과 관련된 모든 메서드를 포함한다.

유스케이스 계층은 SQL을 허용하지 않는다. 따라서 유스케이스 계층은 필요한 메서드를 제공하는 게이트웨이 인터페이스를 호출한다. 그리고 인터페이스의 구현체는 데이터베이스 계층에 위치한다.이 구현체는 험블객체다.
해당 구현체에서 직접 SQL을 사용하거나 데이터베이스에 접근한다.

## 데이터 매퍼

ORM은 게이트웨이 언터페이스와 데이터베이스 사이에서 일종의 또 다른 험블객체 경계를 형성한다.

## 서비스 리스너

애플리케이션이 다른 서비스와 통신한다면?

애플리케이션은 데이터를 간단한 데이터 구조 형태로 로드한 후 이 데이터는 다른 경계로 전달된다. 그러면 해당 모듈은 데이터를 적절한 포맷으로 만들어 외부 서비스로 전송한다.
외부데이터를 수신하는 경우 서비스 리스너가 서비스 인터페이스로부터 데이터를 수신하고 데이터를 애플리케이션에서 사용할 수 있게 간단한 데이터 구조로 포맷을 변경한 후 경계를 가로질러 내부로 전달된다.
