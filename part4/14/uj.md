# Clean Architecture 4부 14장 정리: 컴포넌트 결합

Clean Architecture 14장은 **컴포넌트 사이의 관계**를 다룬다.  
13장이 “어떤 클래스와 모듈을 같은 컴포넌트로 묶을 것인가”에 대한 이야기였다면,  
14장은 “그렇게 만들어진 컴포넌트들이 서로 어떻게 의존해야 하는가”에 대한 이야기다.

즉, 14장의 핵심 질문은 다음과 같다.

```text
컴포넌트 사이의 의존성은 어떤 방향이어야 하는가
컴포넌트 의존성 그래프에 순환이 생기면 왜 위험한가
안정적인 컴포넌트와 불안정한 컴포넌트는 어떻게 구분하는가
추상화는 어느 정도까지 해야 하는가
```

컴포넌트 결합과 관련된 원칙은 세 가지다.

```text
ADP
→ 의존성 비순환 원칙

SDP
→ 안정된 의존성 원칙

SAP
→ 안정된 추상화 원칙
```

세 원칙을 한 문장으로 요약하면 다음과 같다.

```text
ADP
→ 컴포넌트 의존성 그래프에 순환이 없어야 함

SDP
→ 더 안정적인 방향으로 의존해야 함

SAP
→ 안정적인 컴포넌트일수록 추상화되어 있어야 함
```

---

## 1. 컴포넌트 사이의 의존성

컴포넌트는 혼자 존재하지 않는다.  
하나의 컴포넌트는 다른 컴포넌트의 기능, 타입, 인터페이스, 데이터 구조를 사용할 수 있다.

이때 한 컴포넌트가 다른 컴포넌트를 사용하면 의존성이 생긴다.

```text
A 컴포넌트가 B 컴포넌트를 사용
→ A는 B에 의존
```

그림으로 표현하면 다음과 같다.

```text
A → B
```

이 말은 다음 의미다.

```text
A를 이해하려면 B도 알아야 함
B가 바뀌면 A가 영향을 받을 수 있음
A를 빌드하거나 테스트할 때 B가 필요할 수 있음
```

컴포넌트 설계에서 중요한 것은 단순히 컴포넌트를 나누는 것이 아니라,  
나눠진 컴포넌트들이 어떤 방향으로 서로 의존하는지 관리하는 것이다.

---

## 2. ADP: 의존성 비순환 원칙

ADP는 Acyclic Dependencies Principle의 약자이며,  
한국어로는 **의존성 비순환 원칙**이라고 부른다.

핵심은 다음과 같다.

```text
컴포넌트 의존성 그래프에 순환이 있어서는 안 된다.
```

여기서 의존성 그래프란 컴포넌트 사이의 의존 관계를 화살표로 그린 것이다.

```text
A → B → C
```

이 구조에서는 A가 B에 의존하고, B가 C에 의존한다.  
하지만 C가 다시 A에 의존하지는 않는다.

이 경우 의존성은 한 방향으로 흐른다.

---

## 3. 순환 의존성이란 무엇인가

순환 의존성이란 컴포넌트들이 서로 돌고 돌아 다시 자기 자신에게 돌아오는 의존 구조를 말한다.

예를 들어 다음과 같은 구조가 있다.

```text
A → B → C → A
```

이 경우 A는 B에 의존하고, B는 C에 의존하고, C는 다시 A에 의존한다.

즉, 의존성 흐름을 따라가다 보면 다시 출발점으로 돌아온다.  
이것이 순환이다.

조금 더 쉽게 보면 다음과 같다.

```text
A를 고치려면 B를 봐야 함
B를 고치려면 C를 봐야 함
C를 고치려면 다시 A를 봐야 함
```

이렇게 되면 세 컴포넌트는 사실상 하나의 덩어리처럼 묶인다.

겉으로는 A, B, C 세 개의 컴포넌트로 나뉘어 있어도,  
의존성이 순환하면 독립성이 크게 떨어진다.

---

## 4. 순환 의존성이 위험한 이유

순환 의존성이 위험한 이유는 컴포넌트의 독립성을 깨뜨리기 때문이다.

순환이 생기면 다음 문제가 발생한다.

```text
하나의 컴포넌트를 독립적으로 이해하기 어려움
하나의 컴포넌트를 독립적으로 테스트하기 어려움
하나의 컴포넌트를 독립적으로 릴리스하기 어려움
변경 영향 범위가 순환 전체로 퍼짐
빌드 순서가 복잡해짐
팀 간 작업 충돌 가능성이 커짐
```

예를 들어 A 컴포넌트를 수정했는데,  
A가 B에 의존하고, B가 C에 의존하고, C가 다시 A에 의존한다면  
A만 따로 릴리스하기 어려워진다.

이 경우 세 컴포넌트는 따로 배포 가능한 단위라기보다,  
서로 엉켜 있는 하나의 큰 컴포넌트처럼 행동한다.

---

## 5. ADP와 릴리스 가능한 컴포넌트

책에서 말하는 절차는 다음과 같이 이해할 수 있다.

```text
개발 환경을 릴리스 가능한 컴포넌트 단위로 분리
각 컴포넌트에 릴리스 번호 부여
어떤 개발자는 최신 코드를 계속 수정
다른 개발자들은 안정된 릴리스 버전을 기준으로 작업
```

이 방식이 성공하려면 컴포넌트들이 독립적으로 릴리스될 수 있어야 한다.

그런데 의존성에 순환이 있으면 문제가 생긴다.

```text
A를 릴리스하려면 B가 필요
B를 릴리스하려면 C가 필요
C를 릴리스하려면 다시 A가 필요
```

이 경우 어느 하나를 독립적으로 릴리스하기 어려워진다.  
결국 순환에 묶인 모든 컴포넌트를 함께 릴리스해야 한다.

따라서 ADP의 핵심은 다음과 같다.

```text
컴포넌트를 독립적으로 개발하고 릴리스하려면
컴포넌트 의존성 그래프에 순환이 없어야 함
```

---

## 6. 순환 의존성을 끊는 방법

순환 의존성이 생겼을 때는 의존 방향을 끊거나 뒤집어야 한다.

대표적인 방법은 다음과 같다.

```text
의존성 역전 적용
중간 인터페이스 도입
공통으로 필요한 부분을 별도 컴포넌트로 분리
컴포넌트 경계 재조정
```

예를 들어 다음과 같은 순환이 있다고 하자.

```text
A → B → C → A
```

이 순환을 끊기 위해 공통으로 필요한 부분을 D로 분리할 수 있다.

```text
A → B → C
A → D
C → D
```

또는 C가 A의 구체적인 구현을 직접 의존하지 않고,  
A가 제공하는 추상적인 인터페이스에 의존하도록 구조를 바꿀 수 있다.

핵심은 다음과 같다.

```text
순환을 없애려면 어느 한 방향의 의존성을 끊어야 함
의존성을 끊기 위해 추상화나 컴포넌트 분리를 사용할 수 있음
```

---

## 7. SDP: 안정된 의존성 원칙

SDP는 Stable Dependencies Principle의 약자이며,  
한국어로는 **안정된 의존성 원칙**이라고 부른다.

핵심은 다음과 같다.

```text
안정성의 방향으로 의존하라.
```

또는 조금 더 쉽게 표현하면 다음과 같다.

```text
변경되기 쉬운 컴포넌트가 변경되기 어려운 컴포넌트에 의존해야 한다.
```

반대로 말하면 다음 구조를 피해야 한다.

```text
변경하기 어려운 컴포넌트 → 변경하기 쉬운 컴포넌트
```

왜냐하면 변경하기 어려운 컴포넌트가 변경하기 쉬운 컴포넌트에 의존하면,  
변경하기 쉬운 쪽의 변화가 변경하기 어려운 쪽까지 흔들기 때문이다.

---

## 8. 안정성이란 무엇인가

여기서 말하는 안정성은 “코드가 절대 바뀌지 않는다”는 뜻이 아니다.  
안정성은 **변경하기 얼마나 어려운가**에 가깝다.

어떤 컴포넌트에 많은 다른 컴포넌트가 의존하고 있다면,  
그 컴포넌트는 함부로 바꾸기 어렵다.

```text
A → X
B → X
C → X
D → X
```

이 경우 X를 변경하면 A, B, C, D가 영향을 받을 수 있다.  
따라서 X는 변경하기 어렵다.

이런 의미에서 X는 안정적이다.

즉, 안정성은 다음과 같이 이해할 수 있다.

```text
많은 컴포넌트가 나에게 의존함
→ 내가 바뀌면 많은 곳이 영향받음
→ 함부로 바꾸기 어려움
→ 안정적
```

여기서 중요한 점은 안정성이 “좋다/나쁘다”의 문제가 아니라는 것이다.  
안정적이라는 것은 단순히 변경하기 어렵다는 의미다.

---

## 9. 의존성이 많다 = 안정적이라는 말의 의미

“의존성이 많다”는 표현은 조심해서 이해해야 한다.

안정성을 판단할 때 중요한 것은 두 방향이다.

```text
나에게 들어오는 의존성
→ 다른 컴포넌트들이 나를 의존하는 정도

내가 바깥으로 나가는 의존성
→ 내가 다른 컴포넌트들을 의존하는 정도
```

안정적인 컴포넌트는 보통 다음 특징을 가진다.

```text
나에게 들어오는 의존성이 많음
내가 바깥으로 나가는 의존성은 적음
```

즉, 많은 컴포넌트가 나를 의존하지만,  
나는 다른 컴포넌트에 많이 기대지 않는 상태다.

```text
A → X
B → X
C → X
D → X

X는 다른 것에 거의 의존하지 않음
```

이 경우 X는 안정적이다.

반대로 다음과 같은 컴포넌트는 불안정하다.

```text
Y → A
Y → B
Y → C
Y → D

다른 컴포넌트는 Y에 거의 의존하지 않음
```

Y는 많은 것에 의존하지만, 다른 것들은 Y를 거의 의존하지 않는다.  
이 경우 Y는 쉽게 바뀔 수 있고, 바뀌어도 영향받는 쪽이 상대적으로 적다.

따라서 정확한 이해는 다음과 같다.

```text
나를 의존하는 컴포넌트가 많을수록 안정적
내가 의존하는 컴포넌트가 많을수록 불안정
```

그러므로 “의존성이 많다 = 안정적”이라는 말은 무조건 맞지 않다.  
정확히는 “나에게 들어오는 의존성이 많다 = 안정적”에 가깝다.

---

## 10. SDP의 의미

SDP는 의존성 방향이 안정적인 쪽을 향해야 한다고 말한다.

```text
불안정한 컴포넌트 → 안정적인 컴포넌트
```

이 구조는 자연스럽다.  
자주 바뀌는 쪽이 덜 바뀌는 쪽에 의존하기 때문이다.

반대로 다음 구조는 위험하다.

```text
안정적인 컴포넌트 → 불안정한 컴포넌트
```

안정적인 컴포넌트는 많은 곳에서 사용되기 때문에 변경하기 어렵다.  
그런데 안정적인 컴포넌트가 자주 바뀌는 컴포넌트에 의존하면,  
불안정한 컴포넌트의 변화가 안정적인 컴포넌트 전체를 흔들 수 있다.

SDP의 핵심은 다음과 같다.

```text
많은 곳에서 의존하는 중요한 컴포넌트가
자주 바뀌는 컴포넌트에 휘둘리지 않도록 의존성 방향을 관리하는 것
```

---

## 11. SAP: 안정된 추상화 원칙

SAP는 Stable Abstractions Principle의 약자이며,  
한국어로는 **안정된 추상화 원칙**이라고 부른다.

핵심은 다음과 같다.

```text
컴포넌트는 안정된 정도만큼만 추상화되어야 한다.
```

이 말도 처음 보면 어렵게 느껴질 수 있다.  
쉽게 말하면 다음과 같다.

```text
변경하기 어려운 컴포넌트일수록 추상적이어야 한다.
변경하기 쉬운 컴포넌트일수록 구체적이어도 된다.
```

---

## 12. 왜 안정적인 컴포넌트는 추상적이어야 하는가

안정적인 컴포넌트는 많은 다른 컴포넌트가 의존하는 컴포넌트다.  
따라서 함부로 변경하기 어렵다.

그런데 안정적인 컴포넌트가 구체적인 구현으로 가득 차 있다면 문제가 생긴다.

```text
많은 곳에서 의존함
그런데 내부 구현이 구체적임
구체적인 구현은 변경될 가능성이 있음
하지만 바꾸기 어려움
→ 경직된 구조
```

즉, 안정적인데 구체적이면 시스템이 딱딱하게 굳는다.

반대로 안정적인 컴포넌트가 추상적이면,  
많은 컴포넌트가 안정적인 규칙이나 인터페이스에 의존할 수 있다.

```text
많은 곳에서 의존함
하지만 구체 구현이 아니라 추상 규칙을 제공
세부 구현은 바깥에서 바뀔 수 있음
→ 안정성과 확장성의 균형
```

따라서 SAP는 안정적인 컴포넌트가 추상화되어 있어야 한다고 말한다.

---

## 13. 안정성과 추상화의 균형

SAP는 모든 컴포넌트를 무조건 추상화하라는 뜻이 아니다.

핵심은 안정성과 추상화의 정도가 맞아야 한다는 것이다.

```text
안정적인 컴포넌트
→ 추상적이어야 함

불안정한 컴포넌트
→ 구체적이어도 됨
```

이유는 다음과 같다.

```text
안정적인 컴포넌트는 바꾸기 어려움
따라서 구체적인 구현보다 추상적인 규칙을 담는 편이 안전함

불안정한 컴포넌트는 바꾸기 쉬움
따라서 구체적인 구현을 담아도 상대적으로 부담이 적음
```

즉, 추상화는 아무 곳에나 많이 넣는 것이 아니라,  
변경하기 어려운 안정적인 지점에 배치해야 한다.

---

## 14. SDP와 SAP의 관계

SDP와 SAP는 함께 이해해야 한다.

SDP는 의존성 방향에 대한 원칙이다.

```text
의존성은 안정적인 방향으로 향해야 함
```

SAP는 안정적인 컴포넌트의 내부 성격에 대한 원칙이다.

```text
안정적인 컴포넌트는 추상적이어야 함
```

두 원칙을 합치면 다음과 같다.

```text
컴포넌트는 안정적인 쪽으로 의존해야 하고,
그 안정적인 쪽은 구체 구현이 아니라 추상적인 규칙을 제공해야 한다.
```

즉, 이상적인 구조는 다음과 같다.

```text
구체적이고 변경 쉬운 컴포넌트
→ 추상적이고 안정적인 컴포넌트
```

이 구조는 Clean Architecture의 의존성 규칙과도 연결된다.

```text
바깥쪽 세부 구현
→ 안쪽의 추상적인 규칙
```

즉, 바뀌기 쉬운 구체적인 기술이  
더 안정적이고 추상적인 규칙에 의존하는 형태다.

---

## 15. 안정적인데 구체적인 컴포넌트의 문제

안정적인데 구체적인 컴포넌트는 위험하다.

```text
많은 곳에서 의존함
변경하기 어려움
그런데 내부 구현은 구체적임
구체 구현은 변경 가능성이 있음
```

이 경우 컴포넌트는 변경하기 어렵지만,  
동시에 변경될 가능성이 있는 구체적인 내용을 많이 담고 있다.

이런 구조는 시스템을 경직되게 만든다.

```text
변경하고 싶어도 영향 범위가 너무 큼
기존 사용자들이 많아서 쉽게 수정하지 못함
확장보다 수정이 필요해짐
컴포넌트가 시스템 전체의 병목이 됨
```

이런 컴포넌트는 “너무 안정적이어서 문제”가 아니라,  
“안정적인 위치에 구체적인 구현이 들어 있어서 문제”인 것이다.

---

## 16. 추상적인데 불안정한 컴포넌트의 문제

반대로 추상적인데 불안정한 컴포넌트도 문제가 될 수 있다.

```text
아무도 거의 의존하지 않음
자주 바뀔 수 있음
그런데 추상화만 많이 들어 있음
```

이 경우 추상화가 실제로 시스템을 보호하지 못한다.

추상화는 많은 코드가 의존하는 안정적인 규칙을 제공할 때 가치가 커진다.  
아무도 사용하지 않거나 자주 바뀌는 영역에 과도한 추상화를 넣으면,  
오히려 코드만 복잡해질 수 있다.

```text
불필요한 인터페이스 증가
이해 비용 증가
구현과 추상화가 함께 계속 바뀜
실질적인 보호 효과 없음
```

따라서 SAP는 “추상화는 많을수록 좋다”가 아니라,  
“안정성에 맞는 만큼 추상화해야 한다”는 원칙이다.

---

## 17. ADP, SDP, SAP의 연결

14장의 세 원칙은 서로 연결되어 있다.

```text
ADP
→ 컴포넌트 의존성 그래프에 순환이 없도록 만들기

SDP
→ 의존성 방향이 안정적인 쪽을 향하도록 만들기

SAP
→ 안정적인 컴포넌트가 추상적인 규칙을 제공하도록 만들기
```

세 원칙을 흐름으로 보면 다음과 같다.

```text
1. 먼저 순환 의존성을 제거
2. 의존성 방향을 안정적인 쪽으로 정리
3. 안정적인 컴포넌트가 구체 구현이 아니라 추상 규칙을 담도록 조정
```

즉, 컴포넌트 결합은 단순히 “A가 B를 사용한다”의 문제가 아니다.

```text
순환이 없는가
의존성 방향이 안정적인가
안정적인 쪽이 충분히 추상적인가
```

이 세 가지를 함께 봐야 한다.

---

## 18. 의존성 규칙과의 연결

Clean Architecture의 의존성 규칙은 다음과 같이 요약할 수 있다.

```text
소스코드 의존성은 안쪽을 향해야 한다.
```

안쪽은 중요한 규칙이 있는 영역이고,  
바깥쪽은 세부 구현이 있는 영역이다.

```text
안쪽
→ 핵심 규칙, 유스케이스, 정책, 추상화

바깥쪽
→ UI, DB, 프레임워크, 외부 API, 장치, 구체 구현
```

14장의 원칙들은 이 의존성 규칙을 컴포넌트 수준에서 뒷받침한다.

```text
ADP
→ 의존성 흐름이 순환하지 않도록 만들어 안쪽/바깥쪽 경계를 흐리지 않게 함

SDP
→ 더 안정적인 핵심 방향으로 의존하게 함

SAP
→ 안정적인 핵심 컴포넌트가 추상적인 규칙을 담도록 함
```

즉, 14장의 컴포넌트 결합 원칙은 Clean Architecture의 큰 방향과 연결된다.

```text
바깥쪽의 구체적인 컴포넌트
→ 안쪽의 안정적이고 추상적인 컴포넌트
```

이 구조가 유지되어야 핵심 규칙이 세부 구현에 끌려다니지 않는다.

---

# 정리

14장의 핵심은 컴포넌트를 나눈 뒤,  
그 컴포넌트들이 서로 어떤 방향으로 의존해야 하는지를 다루는 것이다.

세 원칙을 정리하면 다음과 같다.

```text
ADP
→ 컴포넌트 의존성 그래프에 순환이 없어야 한다.

SDP
→ 의존성은 안정적인 방향으로 향해야 한다.

SAP
→ 안정적인 컴포넌트일수록 추상적이어야 한다.
```

조금 더 쉽게 표현하면 다음과 같다.

```text
ADP
→ 돌고 도는 의존 관계를 만들지 말기

SDP
→ 자주 바뀌는 쪽이 덜 바뀌는 쪽에 의존하게 만들기

SAP
→ 많은 곳에서 의존하는 컴포넌트는 구체 구현보다 추상 규칙을 제공하게 만들기
```

14장의 핵심 관점은 다음과 같다.

```text
컴포넌트는 나누는 것만으로 충분하지 않음
나눠진 컴포넌트 사이의 의존 방향이 중요
의존성이 순환하면 독립성이 깨짐
의존성이 불안정한 쪽을 향하면 변경에 취약해짐
안정적인 컴포넌트가 구체적이면 시스템이 경직됨
```

최종적으로 컴포넌트 결합 원칙은 다음 목표를 가진다.

> 컴포넌트들이 독립적으로 개발, 릴리스, 배포될 수 있도록  
> 순환 없는 의존성 구조와 안정적인 의존 방향을 만드는 것
