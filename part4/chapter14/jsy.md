# 컴포넌트 결합

이번 챕터에서도 개발 가능성, 논리적 설계 사이의 균형을 다룸

# ADP: 의존성 비순환 원칙

의존성 그래프에 cycle을 제거해보자~

주 단위빌드는 개발 방법론에 더 가깝다고 느낌

## 순환 의존성 제거하기

- 개발 환경을 릴리스 가능한 컴포넌트 단위로 분리하는 것 -> 분리된 단위대로 개발 팀이 책임을 짐 -> 해당 컴포넌트 개발, 릴리스 -> 다른 팀에서 해당 릴리스 버전 적용을 결정

  이 개발 순서를 지키기 위해서는 "의존성 구조"를 반드시 관리해야 함
  즉, 컴포넌트를 정점, 의존성 관계는 간선으로 놓았을 때 비순환 방향 그래프(DAG)형태가 되야 함
  DAG형태로 컴포넌트를 분리하면 가장 아래에 있는 컴포넌트의 새로운 릴리스가 진행된다면 상향식으로 점진적 통합을 진행하면된다.

## 순환이 컴포넌트 의존성 그래프에 미치는 영향

- p120(그림 14.2)참고

`Entities`의 `User`클래스가 `Authorizer`의 `Permissions`클래스를 사용한다고 가정

```
Entities -> Authorizer -> Interactors -> Entities 라는 cycle 발생
```

이로 인해 Entities를 의존하는 다른 컴포넌트 A가 릴리스되려면 순환되는 `Entities -> Authorizer -> Interactors` 이 3가지의 컴포넌트가 하나의 컴포넌트로 통합되어야 A가 비로서 릴리스 가능
그렇기에 순환을 끊는것이 중요

## 순환 끊기

순환 끊는 2가지 매커니즘

1. DIP 적용하기 (p122)
   Entities-User<<class>>가 Authorizer-Permissions<<class>>을 사용함,
   User가 필요로하는 메서드를 제공하는 인터페이스를 Entities에 만들고 Authorizer에서 상속받음 -> 의존성 역전으로 순환 끊김

2. 새로운 컴포넌트 만들기(Jitters, 흐트러짐)
   Entiteis와 Authorizer가 모두 의존하는 새로운 컴포넌트 Permissions를 만듦

두번째 해결책의 핵심적인 사항은 요구사항이 변경되면 컴포넌트 구조도 변경될 수 있다는 점

- 순환이 발생하면 어떤 식으로든 끊어야 한다.(테스트,릴리스 용이성을 갖자!)

# 하향식 설계 / top-down

컴포넌트와 같이 큰 단위로 분해된 구조는 고수준의 기능적인 구조로 다시 분해할 수 있다고 기대한다.
컴포넌트 의존성 구조와 같이 큰 단위로 분해된 집단을 관찰하면 시스템의 기능적 측면을 컴포넌트가 어떤 식으로든 표현하리라고 믿음 하지만 실제로는 그렇지 않다.
의존성을 끊기위해 "순환끊기 2번째 처럼" 빈 껍데기 컴포넌트를 만드는 경우들이 생김 그렇기 때문에 컴포넌트 자체가 기능적인 구조는 아님

컴포넌트 의존성 다이어그램은 프로젝트 초기 단계에서 그릴 수도 없고 필요하지도 않음 이건 실제 개발되면서 만들어가는 것

# SDP: 안정된 의존성 원칙

컴포넌트가 다른 유형의 변경에는 영향받지 않으면서도 특정 유형의 변경에만 민감하게 만들 수 있다. 즉, 일부는 변동성을 유지할 수 있게 만들 수 있다.
변동성을 지닌 컴포넌트는 후에 요구사항을 통해 변경될 것이다.

변경이 쉽지 않은 컴포넌트가 변동이 예상되는 컴포넌트에 의존하게 만들어서는 안된다.

> 예시로 비즈니스 규칙을 가진 곳이 의존성을 갖게 하지 말라는 말 같음

안정성이란 변화가 발생하는 빈도가 아니라 컴포넌트를 변경하기 어렵게 만드는 것
변경을 어렵게 만드는 방법 중 하나는 다른 컴포넌트가 해당 컴포넌트에 의존하게 만들면된다.(Fan in)

이렇게 의존된 개수에 따라 안정성 지표를 만들 수 있는데
Fan in : 안으로 들어오는 의존성 A -> B
Fan out : 밖으로 나가는 의존성 B -> A
I(불안정성) : I = Fan out % (Fan in + Fan out)

> I = 0 최고로 안정 I = 1 최고로 불안정

## 모든 컴포넌트가 안정적이진 않아도 된다.

모든 컴포넌트가 안정적이라는 것은 변경이 불가능하다는 것이고 이것은 하드웨어지 소프트웨어가 아님
아니 뭔 의존성만 나오면 DIP로 그냥 추상화 해버리는데.. 이건 또 역효과 날듯

# SAP: 안정된 추상화 원칙 Stable Abstractions Principle

고수준 정책을 안정화된 추상클래스에 만들어라

왜? 안정된 컴포넌트는 Fan-in되는 컴포넌트들이 많을테니깐 안정적이어야 돼, 근데 또 실질적인 로직은 없어야 할테니깐 인터페이스나, 추상 클래스로 만들면 OCP도 지키면서 비즈니스 규칙들이 잘 지켜지것지

- SAP와 SDP를 결합하면 컴포넌트에 대한 DIP나 마찬가지가 된다. 실제로 SDP에서는 의존성이 반드시 안정적인 컴포넌트가 있는 방향으로 향해야 한다고 말하며, SAP는 안정성이 결국 추상화이기 때문, 따라서 의존성은 추상화 방향으로 향하게 된다.
  BUT! DIP는 클래스에 대한 원칙, 클래스의 경우 중간은 존재하지 않는다. 즉 클래스는 추상적이거나 아니거나 둘 중 하나.
  SDP와 SAP의 조합은 컴포넌트에 대한 원칙, 컴포넌트는 어떤 부분은 추상적이면서 다른 부분은 안정적일 수 있다.

> 뒤지게 어렵네..

## 추상화 정도

Nc: 컴포넌트의 클래스 개수
Na: 컴포넌트의 추상클래스 & 인터페이스 개수
A: 추상화 정도 A = Na % Nc

## 주계열

책에서는 주계열, 컴포넌트의 추상화 정도 지표를 통해서 해당 컴포넌트가 가진 Nc Na를 xy에 그린다. x에는 안정성 y에는 추상화
그리고 배제해야할 구역(고통의 구역, 쓸모없는 구역), 주계열로 나숴서 어느 위치에 있는게 최적인지를 알 수 있는 방법을 제공한다.

내용이 길고 그림에 따른 예문으로만 되어있어서 이부분은 본문을 읽는 것이 좋다.

그중에서 기억에 남는 내용중 하나는 "엔티티 즉 데이터베이스 스키마는 변동성이 높지만, 많은 컴포넌트가 여기에 의존해서 애플리케이션과 데이터베이스 사이에 위치한 인터페이스는 관리하기가 어렵고 고통을 수반한다."
