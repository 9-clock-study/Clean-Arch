# Clean Architecture 4부 13장 정리: 컴포넌트 응집도

Clean Architecture 13장은 **컴포넌트를 어떻게 묶어야 하는가**에 대한 원칙을 다룬다.

12장에서 컴포넌트를 “배포 가능한 가장 작은 단위”로 이해했다면,  
13장에서는 그 컴포넌트 안에 어떤 클래스와 모듈을 함께 넣어야 하는지,  
또 어떤 클래스와 모듈은 함께 넣으면 안 되는지를 다룬다.

즉, 13장의 핵심 질문은 다음과 같다.

```text
무엇을 같은 컴포넌트로 묶을 것인가
무엇을 다른 컴포넌트로 분리할 것인가
컴포넌트 내부의 응집도를 어떻게 판단할 것인가
```

컴포넌트 응집도와 관련된 원칙은 세 가지다.

```text
REP
→ 재사용/릴리스 등가 원칙

CCP
→ 공통 폐쇄 원칙

CRP
→ 공통 재사용 원칙
```

이 세 원칙은 각각 다른 관점에서 컴포넌트의 경계를 정한다.

```text
REP
→ 재사용하는 단위와 릴리스하는 단위는 같아야 함

CCP
→ 같은 이유로 함께 바뀌는 것들은 같은 컴포넌트에 있어야 함

CRP
→ 함께 쓰이지 않는 것들은 같은 컴포넌트에 있으면 안 됨
```

---

## 1. REP: 재사용/릴리스 등가 원칙

REP는 Reuse/Release Equivalence Principle의 약자이며,  
한국어로는 **재사용/릴리스 등가 원칙**이라고 부른다.

핵심은 다음과 같다.

```text
재사용 단위는 릴리스 단위와 같아야 한다.
```

처음 보면 이 말이 추상적으로 느껴질 수 있다.  
쉽게 말하면 다음과 같다.

```text
다른 사람이 가져다 쓰는 단위라면,
그 단위는 정식으로 릴리스되고 관리되는 단위여야 한다.
```

즉, 어떤 코드를 재사용하려면 그 코드는 아무렇게나 복사해서 쓰는 코드 조각이 아니라,  
버전 번호가 있고, 릴리스 기록이 있고, 변경 내역이 관리되는 단위여야 한다.

---

## 2. 릴리스란 무엇인가

여기서 말하는 릴리스는 단순히 “코드를 서버에 올리는 것”만을 의미하지 않는다.

릴리스는 어떤 소프트웨어 단위를 외부에서 사용할 수 있는 형태로 공개하거나 제공하는 행위다.

릴리스에는 보통 다음이 포함된다.

```text
버전 번호
릴리스 날짜
변경 내역
호환성 정보
문서
사용 방법
배포 가능한 파일 또는 패키지
```

예를 들어 어떤 라이브러리를 재사용하는 입장에서는 다음 정보를 알고 싶어 한다.

```text
현재 버전이 무엇인지
이전 버전과 무엇이 달라졌는지
업데이트해도 기존 코드가 깨지지 않는지
어떤 기능이 추가되거나 제거되었는지
버그가 수정되었는지
```

따라서 재사용 가능한 컴포넌트라면 반드시 릴리스 관리가 필요하다.

---

## 3. 릴리스와 배포의 차이

책에서 릴리스와 배포를 구분해서 말하는 이유도 이해할 필요가 있다.

두 단어는 비슷하게 쓰이지만, 엄밀히 보면 강조점이 다르다.

```text
릴리스
→ 사용할 수 있는 버전으로 공식 제공하는 것

배포
→ 실제 실행 환경이나 사용자에게 전달하고 설치하는 것
```

예를 들어 라이브러리 관점에서는 다음과 같이 볼 수 있다.

```text
릴리스
→ version 1.2.0을 공식적으로 공개

배포
→ 그 버전을 실제 서버, 앱, 패키지 저장소, 사용자 환경에 전달
```

즉, 릴리스는 “버전으로 관리되는 공식 제공”에 가깝고,  
배포는 “그 버전을 실제 환경에 전달하고 적용하는 과정”에 가깝다.

정리하면 다음과 같다.

```text
릴리스
→ 무엇을 어떤 버전으로 내보낼 것인가

배포
→ 그것을 어디에 어떻게 적용할 것인가
```

그래서 컴포넌트는 단순히 배포 가능한 단위일 뿐 아니라,  
릴리스 번호와 문서로 추적 가능한 단위여야 한다.

---

## 4. REP의 의미

REP는 재사용 가능한 컴포넌트가 반드시 릴리스 단위로 관리되어야 한다고 본다.

하나의 컴포넌트로 묶인 클래스와 모듈은 다음 조건을 만족해야 한다.

```text
함께 릴리스할 수 있어야 함
같은 버전 번호를 가져야 함
같은 릴리스 문서에 포함되어야 함
같은 변경 이력으로 추적 관리되어야 함
```

즉, 하나의 컴포넌트 안에 들어간 코드들은  
같은 릴리스 단위로 다뤄져도 어색하지 않아야 한다.

REP의 핵심은 다음과 같이 정리할 수 있다.

```text
같이 재사용되는 것들은 같이 릴리스되어야 한다.
같이 릴리스될 수 없는 것들은 같은 재사용 단위가 되기 어렵다.
```

---

## 5. REP와 컴포넌트의 응집성

소프트웨어 설계와 아키텍처 관점에서 보면,  
하나의 컴포넌트는 응집성 높은 클래스와 모듈로 구성되어야 한다.

컴포넌트를 구성하는 모든 모듈은 서로 공유하는 중요한 테마나 목적이 있어야 한다.

```text
같은 목적을 위해 사용됨
같은 사용자에게 함께 제공됨
같은 기능 영역을 구성함
같은 버전으로 관리해도 자연스러움
함께 릴리스되어도 이상하지 않음
```

예를 들어 하나의 컴포넌트에 다음과 같은 코드들이 함께 들어 있다면 응집성이 높다고 볼 수 있다.

```text
특정 도메인 규칙을 표현하는 클래스들
그 도메인 규칙을 처리하는 서비스들
그 도메인에서 공통으로 쓰는 값 객체들
그 도메인 기능을 외부에 제공하는 인터페이스들
```

반대로 다음과 같은 코드들이 한 컴포넌트에 섞여 있다면 응집성이 낮을 수 있다.

```text
사용자 인증 기능
엑셀 파일 생성 기능
결제 연동 기능
이미지 압축 기능
관리자 화면 기능
```

이 기능들이 항상 함께 사용되고 함께 릴리스되어야 하는 이유가 없다면,  
하나의 컴포넌트로 묶는 것은 부적절할 수 있다.

REP는 컴포넌트가 단순한 코드 저장소가 아니라,  
재사용과 릴리스가 함께 관리되는 응집된 단위여야 한다고 말한다.

---

## 6. REP의 약점

REP만 강하게 적용하면 문제가 생길 수 있다.

REP는 “같이 재사용되는 것들을 같이 릴리스하라”는 방향을 제공하지만,  
무엇을 같이 묶어야 하는지에 대한 기준이 충분히 구체적이지 않을 수 있다.

REP의 약점은 다음과 같다.

```text
컴포넌트에 무엇을 넣어야 하는지 충분히 설명하지 못함
같이 릴리스된다는 이유만으로 너무 많은 코드가 묶일 수 있음
재사용 단위를 지나치게 크게 만들 위험
변경 이유가 다른 코드까지 한 컴포넌트에 섞일 수 있음
```

따라서 REP만으로는 컴포넌트 경계를 정하기 부족하다.  
그래서 CCP와 CRP가 함께 필요하다.

---

## 7. CCP: 공통 폐쇄 원칙

CCP는 Common Closure Principle의 약자이며,  
한국어로는 **공통 폐쇄 원칙**이라고 부른다.

핵심은 다음과 같다.

```text
동일한 이유로 동일한 시점에 변경되는 클래스를 같은 컴포넌트로 묶어라.
서로 다른 시점에 다른 이유로 변경되는 클래스는 다른 컴포넌트로 분리하라.
```

CCP는 변경의 관점에서 컴포넌트 경계를 정하는 원칙이다.

즉, 어떤 클래스들이 자주 함께 바뀐다면 같은 컴포넌트에 두는 것이 좋다.  
반대로 서로 다른 이유로 바뀐다면 같은 컴포넌트에 두지 않는 것이 좋다.

---

## 8. CCP와 SRP의 연결

CCP는 SRP의 컴포넌트 버전이라고 볼 수 있다.

SRP는 모듈이나 클래스 수준에서 다음과 같이 말한다.

```text
하나의 모듈은 하나의 변경 이유만 가져야 한다.
```

CCP는 이 생각을 컴포넌트 수준으로 확장한다.

```text
하나의 컴포넌트는 하나의 변경 이유를 중심으로 묶여야 한다.
```

즉, SRP가 클래스와 모듈의 책임을 나누는 원칙이라면,  
CCP는 컴포넌트의 변경 이유를 나누는 원칙이다.

정리하면 다음과 같다.

```text
SRP
→ 하나의 모듈이 하나의 변경 이유를 갖도록 분리

CCP
→ 하나의 컴포넌트가 하나의 변경 이유를 중심으로 묶이도록 분리
```

---

## 9. CCP의 예시

예를 들어 어떤 시스템에 다음과 같은 코드들이 있다고 생각할 수 있다.

```text
회원 등급 계산 규칙
회원 포인트 적립 규칙
회원 쿠폰 발급 규칙
회원 혜택 정책
```

이 코드들이 모두 “회원 혜택 정책 변경”이라는 이유로 함께 바뀐다면,  
같은 컴포넌트에 묶는 것이 자연스럽다.

반대로 다음 코드들이 같은 컴포넌트에 있다면 문제가 될 수 있다.

```text
회원 혜택 정책
이미지 업로드 처리
메일 발송 템플릿
관리자 통계 화면
```

이 코드들은 서로 다른 이유로 바뀔 가능성이 높다.

```text
회원 혜택 정책
→ 서비스 정책 변경 때문에 변경

이미지 업로드 처리
→ 파일 저장 방식이나 이미지 처리 방식 변경 때문에 변경

메일 발송 템플릿
→ 마케팅 문구나 발송 정책 변경 때문에 변경

관리자 통계 화면
→ 운영팀의 화면 요구사항 변경 때문에 변경
```

이런 코드들이 같은 컴포넌트에 있으면,  
서로 상관없는 변경이 하나의 컴포넌트에 계속 영향을 준다.

CCP의 관점에서는 다음이 중요하다.

```text
함께 바뀌는 것은 함께 묶기
따로 바뀌는 것은 따로 분리하기
```

---

## 10. CCP의 목적

CCP는 소프트웨어를 릴리스하고, 재검증하고, 배포하는 작업량을 줄이기 위한 원칙이다.

어떤 변경이 발생했을 때 관련된 코드가 여러 컴포넌트에 흩어져 있으면,  
여러 컴포넌트를 동시에 수정하고, 릴리스하고, 테스트하고, 배포해야 한다.

반대로 함께 변경되는 코드가 하나의 컴포넌트에 모여 있으면,  
변경의 영향 범위를 더 좁게 관리할 수 있다.

```text
관련 변경이 한 컴포넌트 안에서 끝남
릴리스해야 할 컴포넌트 수 감소
재검증해야 할 범위 감소
배포 영향 범위 감소
```

즉, CCP는 변경이 발생했을 때 영향을 받는 컴포넌트의 수를 최소화하려는 원칙이다.

---

## 11. CCP와 OCP의 연결

CCP는 OCP와도 연결된다.

OCP는 다음과 같은 원칙이다.

```text
확장에는 열려 있고, 변경에는 닫혀 있어야 한다.
```

이 말은 새로운 요구사항이 생겼을 때 기존 코드를 무조건 수정하지 말라는 뜻이 아니라,  
변경의 영향을 통제할 수 있는 구조를 만들라는 뜻이다.

CCP는 이 생각을 컴포넌트 수준에 적용한다.

```text
같은 종류의 변경에 함께 영향을 받는 클래스들을 하나의 컴포넌트로 묶기
다른 종류의 변경에는 영향을 받지 않도록 컴포넌트 경계 나누기
```

즉, 어떤 컴포넌트가 특정 유형의 변경에 대해서만 바뀌고,  
다른 유형의 변경에는 닫혀 있다면 OCP의 생각이 컴포넌트 수준에서 적용된 것이다.

예를 들어 하나의 컴포넌트가 “회원 정책 변경”에는 열려 있지만,  
“파일 저장 방식 변경”이나 “화면 디자인 변경”에는 영향을 받지 않는다면,  
그 컴포넌트는 자신의 변경 이유에 대해서만 열려 있고 다른 변경 이유에는 닫혀 있는 구조라고 볼 수 있다.

정리하면 다음과 같다.

```text
OCP
→ 변경의 영향을 통제하는 원칙

CCP
→ 같은 유형의 변경에 함께 반응하는 클래스들을 같은 컴포넌트로 묶어
   다른 유형의 변경으로부터 컴포넌트를 닫아두는 원칙
```

즉, CCP는 OCP에서 얻은 교훈을 컴포넌트 수준으로 확장한 원칙이다.

---

## 12. CRP: 공통 재사용 원칙

CRP는 Common Reuse Principle의 약자이며,  
한국어로는 **공통 재사용 원칙**이라고 부른다.

핵심은 다음과 같다.

```text
컴포넌트 사용자들을 필요하지 않은 것에 의존하게 강요하지 말라.
```

CRP는 어떤 클래스를 한 컴포넌트에 묶어야 하는지가 아니라,  
어떤 클래스를 한 컴포넌트에 묶으면 안 되는지를 알려주는 원칙이다.

즉, CRP는 배제의 원칙이다.

---

## 13. CRP의 의미

컴포넌트를 사용하는 쪽은 보통 컴포넌트 전체에 의존한다.

따라서 컴포넌트 안에 사용하지 않는 클래스가 들어 있어도,  
그 클래스의 변경 때문에 컴포넌트 버전이 바뀌면 사용자는 영향을 받을 수 있다.

예를 들어 어떤 사용자가 컴포넌트 안의 일부 기능만 사용한다고 해도,  
같은 컴포넌트 안의 다른 기능이 변경되어 새 릴리스가 나오면  
그 사용자는 새 버전을 검토하고 테스트해야 할 수 있다.

CRP는 이런 상황을 피하려는 원칙이다.

```text
함께 사용되지 않는 것들을 같은 컴포넌트에 넣지 않기
강하게 결합되지 않은 클래스들을 같은 컴포넌트에 넣지 않기
사용자에게 불필요한 의존을 강요하지 않기
```

즉, CRP는 다음과 같이 이해할 수 있다.

```text
같이 쓰이지 않는 것은 같이 묶지 말기
```

---

## 14. CRP와 ISP의 연결

CRP는 ISP와도 연결된다.

ISP는 인터페이스 수준에서 다음과 같이 말한다.

```text
사용하지 않는 메서드에 의존하지 않게 하라.
```

CRP는 이 생각을 컴포넌트 수준으로 확장한다.

```text
사용하지 않는 클래스와 모듈에 의존하지 않게 하라.
```

정리하면 다음과 같다.

```text
ISP
→ 사용하지 않는 기능이 포함된 큰 인터페이스에 의존하지 않게 하는 원칙

CRP
→ 사용하지 않는 클래스가 포함된 큰 컴포넌트에 의존하지 않게 하는 원칙
```

즉, CRP는 컴포넌트 수준의 인터페이스 분리 원칙처럼 이해할 수 있다.

---

## 15. CRP의 예시

예를 들어 어떤 컴포넌트 안에 다음 기능들이 함께 들어 있다고 생각할 수 있다.

```text
날짜 계산 기능
문자열 포맷 기능
파일 압축 기능
이미지 리사이징 기능
```

이 기능들이 항상 함께 사용되는 것이 아니라면,  
이들을 하나의 공통 유틸리티 컴포넌트로 묶는 것은 문제가 될 수 있다.

어떤 사용자는 날짜 계산 기능만 필요할 수 있다.  
그런데 같은 컴포넌트에 이미지 리사이징 기능까지 들어 있다면,  
사용자는 필요 없는 기능이 포함된 컴포넌트 전체에 의존하게 된다.

이 경우 이미지 리사이징 기능의 변경 때문에 컴포넌트가 새로 릴리스되면,  
날짜 계산 기능만 쓰던 사용자도 영향을 받을 수 있다.

CRP의 관점에서는 다음이 더 적절할 수 있다.

```text
날짜 관련 컴포넌트
문자열 포맷 컴포넌트
파일 처리 컴포넌트
이미지 처리 컴포넌트
```

즉, 함께 재사용되지 않는 것들을 억지로 하나의 컴포넌트에 넣지 않는 것이 중요하다.

---

## 16. REP, CCP, CRP의 차이

세 원칙은 모두 컴포넌트 응집도와 관련되지만, 강조점이 다르다.

```text
REP
→ 같이 재사용되고 릴리스될 수 있는가

CCP
→ 같이 변경되는가

CRP
→ 같이 사용되는가
```

조금 더 풀어 쓰면 다음과 같다.

```text
REP
→ 함께 릴리스할 수 있는 것들을 묶기

CCP
→ 함께 변경되는 것들을 묶기

CRP
→ 함께 사용되지 않는 것들은 제외하기
```

이 중 REP와 CCP는 포함의 성격이 강하다.

```text
REP
→ 재사용과 릴리스 관점에서 함께 묶어야 할 것 제시

CCP
→ 변경 관점에서 함께 묶어야 할 것 제시
```

반면 CRP는 배제의 성격이 강하다.

```text
CRP
→ 함께 사용되지 않는 것은 같은 컴포넌트에 넣지 말 것 제시
```

정리하면 다음과 같다.

```text
REP, CCP
→ 무엇을 컴포넌트에 넣을 것인가

CRP
→ 무엇을 컴포넌트에서 뺄 것인가
```

---

## 17. 세 원칙의 균형

REP, CCP, CRP는 모두 맞는 말이지만,  
하나의 원칙만 과하게 적용하면 문제가 생긴다.

### REP에 치우친 경우

REP에만 치우치면 “같이 릴리스하면 편하다”는 이유로 너무 많은 코드가 한 컴포넌트에 묶일 수 있다.

```text
컴포넌트가 지나치게 커짐
변경 이유가 다른 코드들이 섞임
사용하지 않는 기능까지 함께 의존하게 됨
릴리스 단위가 무거워짐
```

### CCP에 치우친 경우

CCP에만 치우치면 “같이 바뀐다”는 이유로 컴포넌트를 너무 변경 중심으로만 나누게 된다.

```text
재사용 관점이 약해짐
사용자 입장에서 불필요한 의존이 생길 수 있음
컴포넌트 경계가 현재 변경 패턴에 지나치게 묶임
```

특히 시간이 지나 변경 패턴이 달라지면,  
기존 컴포넌트 경계가 더 이상 적절하지 않을 수 있다.

### CRP에 치우친 경우

CRP에만 치우치면 “함께 쓰이지 않는 것은 절대 묶지 말자”는 방향으로 컴포넌트가 너무 작게 쪼개질 수 있다.

```text
컴포넌트 수가 과도하게 많아짐
의존성 관리가 복잡해짐
버전 관리가 어려워짐
작은 변경에도 여러 컴포넌트를 조정해야 함
개발과 배포 관리 비용이 증가
```

따라서 세 원칙은 균형이 필요하다.

```text
너무 크게 묶으면 불필요한 의존이 생김
너무 작게 나누면 관리 비용이 증가
변경 기준만 보면 재사용성이 떨어질 수 있음
재사용 기준만 보면 변경 이유가 섞일 수 있음
```

---

## 18. 컴포넌트 응집도 원칙의 핵심 관계

세 원칙의 관계를 간단히 정리하면 다음과 같다.

```text
REP
→ 재사용하는 사람 입장에서 신뢰할 수 있는 릴리스 단위인가

CCP
→ 변경하는 사람 입장에서 함께 바뀌는 코드가 모여 있는가

CRP
→ 사용하는 사람 입장에서 필요 없는 것까지 의존하지 않는가
```

즉, 세 원칙은 각각 다른 관점의 질문을 던진다.

```text
REP의 질문
→ 이것들은 함께 릴리스되어야 하는가

CCP의 질문
→ 이것들은 함께 변경되는가

CRP의 질문
→ 이것들은 함께 사용되는가
```

좋은 컴포넌트는 이 세 질문 사이에서 균형을 찾은 결과다.

# 정리

13장의 핵심은 컴포넌트 응집도를 판단할 때  
단순히 “관련 있어 보이는 코드끼리 묶기”로는 부족하다는 점이다.

컴포넌트는 다음 세 관점에서 응집적이어야 한다.

```text
재사용 관점
→ 함께 재사용되고 함께 릴리스될 수 있어야 함

변경 관점
→ 같은 이유로 같은 시점에 변경되어야 함

사용 관점
→ 함께 사용되지 않는 것을 억지로 포함하지 않아야 함
```

세 원칙을 한 번에 정리하면 다음과 같다.

```text
REP
→ 재사용 단위와 릴리스 단위를 일치시키는 원칙

CCP
→ 같은 이유로 함께 바뀌는 것들을 같은 컴포넌트로 묶는 원칙

CRP
→ 함께 사용되지 않는 것들을 같은 컴포넌트에 넣지 않는 원칙
```

최종적으로 컴포넌트 응집도는 다음 균형으로 이해할 수 있다.

```text
같이 릴리스되는가
같이 변경되는가
같이 사용되는가
```

이 세 질문에 모두 어느 정도 자연스럽게 답할 수 있을 때,  
그 컴포넌트는 응집도 높은 컴포넌트라고 볼 수 있다.

> 컴포넌트 응집도는 코드를 단순히 기능별로 모으는 문제가 아니라,  
> 재사용, 릴리스, 변경, 사용 방식이 서로 맞물리도록 경계를 정하는 문제다.
