# Component Cohesion

어떤 클래스를 어떤 컴포넌트에? -> 소프트웨어 엔지니어링 원칙의 도움을 받자 -> 컴포넌트 응집도와 관련된 3가지 원칙

REP, CCP, CRP

Reuse/Release Equivalence Principle
Common Closure Principle
Common Reuse Principle

## 질문

1. 바로 어떤 클래스를 어떤 컴포넌트에 넣을지 결정하기 전에 어떤 모듈에 넣을지부터가 우선이 아닌가 모듈들도 클래스들의 집합이라는 관점에서 본다면 해당 말도 틀린건 아니긴함

2. 3가지 원칙들 중에 "Reuse", "Common" 두 단어가 나옴 즉, 3가지 원칙들 모두 추상화와 재사용성을 기반으로 원칙들이 작성되어있지 않을까 유추해봄 내 유추가 맞는지도 한번 이번 챕터를 읽어나가면서 확인해보자

# REP

- "재사용 단위는 릴리스 단위와 같다."

컴포넌트가 릴리스 절차를 통해 추적 관리되지 않거나 릴리스 번호가 부여되지 않는다면 해당 컴포넌트를 재사용하고 싶어도 할 수 없고, 하지도 않을 것

> 릴리스 기록이 없다면 언제 어디가 바뀌었는지 재사용하는 사람은 알 수 없으니 컴포넌트가 재사용되기 위해서는 릴리스 절차가 필요하다.

컴포넌트를 구성하는 모든 모듈은 서로 공유하는 중요한 테마나 목적이 있어야한다.

> 질문 1번에 해당하는데 여기서는 정확하게 "모듈" 언급을 해주네

REP는 잠수함 패치같은거 하지말라는거 아닌가 정확하게 어떤 모듈들이 수정되었는지 명확히 하라 추적성?

# CCP

- "동일한 이유로 동일한 시점에 변경되는 클래스를 같은 컴포넌트로 묶어라."
  즉, 서로 다른 시점에 다른 이유로 변경되는 클래스는 다른 컴포넌트로 분리하라. SRP에서 말하는 **변경 이유가 오직 하나여야한다.**

- 애플리케이션에서 유지보수성은 재사용성보다 중요하다. 코드가 반드시 변경되어야 한다면, 이러한 변경이 여러 컴포넌트에서 일어나기보다는 단일 컴포넌트에서 발생하는 편이 낫다.
- 물리적 또는 개념적으로 강하게 결합되어 항상 함계 변경되는 클래스들은 하나의 컴포넌트에 속하게 하라.
- CCP에서는 동일한 유형의 변경에 대해 닫혀 있는 클래스들을 하나의 컴포넌트로 묶음으로써 OCP에서 얻은 교훈을 확대 적용한다.

> 시간개념에 대한 애기인데 "동일한 시점에 변경되는..." 이 문장이 완전하게 모듈, 클래스들이 독립적이지는 않다는 말, 서로 간 의존성이 생겼을 때 어디 한곳을 수정한다면 다른 한 곳도 동일한 시점에 수정을 해야된다 뜻

# CRP

- "컴포넌트 사용자들을 필요하지 않는 것에 의존하게 강요하지 말라."
- "CRP에서는 같이 재사용되는 경향이 있는 클래스와 모듈들은 같은 컴포넌트에 포함하라."

> CRP에서 말하는 Reuse는 재사용이 아니라, 다른 개발자가 컴포넌트 자체를 가져다가 쓰는 의존행위(using하는)

# 정리

3가지 원칙들은 어느 한쪽에 치중되면 나머지에 대한 단점이 발현됨 (p113 다이어그램 참고)
어느 클래스들을 묶어서 컴포넌트로 만들지를 결정할 때, 재사용성과 개발 가능성이라는 상충하는 힘을 반드시 고려해야한다.

이 균형점은 거의 항상 유동적(소프트웨어라 불리는 이유이지 않을까)
