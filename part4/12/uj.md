# Clean Architecture 4부 12장 정리: 컴포넌트

```text
SOLID 원칙
→ 벽과 방에 벽돌을 배치하는 방법

컴포넌트 원칙
→ 빌딩에 방을 배치하는 방법
```

=> SOLID : 코드 내부의 작은 단위 설계,  
컴포넌트 원칙 : 그 코드들을 묶어 배포하고 결합하는 더 큰 단위의 설계

---

## 1. 이번 장에서 다루는 것들

```text
소프트웨어 컴포넌트란 무엇인가
컴포넌트를 구성하는 요소는 무엇인가
컴포넌트를 어떻게 결합해 시스템을 구성하는가
```

---

## 2. 컴포넌트의 기본 정의

```text
컴포넌트 : 시스템의 구성요소로 배포 가능한 가장 작은 단위
```

```text
Java
→ .jar 파일

Ruby
→ .gem 파일

.NET
→ .dll 파일

인터프리터형 언어
→ 소스 파일들의 결합체

컴파일형 언어
→ 바이너리 파일들의 결합체
```

즉, 컴포넌트의 물리적 형태는 언어마다 다르지만, 핵심은 같다.

```text
독립적으로 묶을 수 있는 단위
독립적으로 배포할 수 있는 단위
다른 부분과 결합해 실행될 수 있는 단위
```

---

## 3. 그렇다면, JS, TS, Python에서는

### JavaScript / TypeScript

JavaScript나 TypeScript에서의 컴포넌트에 가까운 단위는

```text
npm 패키지
라이브러리
모듈 묶음
빌드 결과물
배포 가능한 번들
```

등이 될 수 있겠다.

- Node.js 프로젝트에서는 특정 기능을 npm 패키지로 분리할 수 있음
  프론트엔드에서는 여러 소스 파일을 번들러가 묶어 하나의 배포 가능한 결과물로 만들 수 있음.

- TypeScript는 실행 전에 JavaScript로 컴파일되니까,  
  개발 시점에는 `.ts` 소스 파일들이 중심이고,  
  배포 시점에는 컴파일된 `.js` 파일과 타입 정의 파일 등이 함께 배포될 수 있음

### Python

```text
Python 패키지
모듈 묶음
wheel 파일
라이브러리 배포 단위
```

Python은 보통 소스 파일을 직접 실행하는 인터프리터형 언어에 가깝지만, 패키지 단위로 묶어 설치하고 배포할 수 있음

=> JS, TS, Python에서는 Java의 `.jar`나 .NET의 `.dll`처럼 항상 하나의 바이너리 파일로 떨어지지는 않더라도,  
기능을 묶고 배포하고 결합할 수 있는 단위가 컴포넌트 역할.

```text
Java / .NET
→ 컴파일된 바이너리 중심의 컴포넌트

JavaScript / TypeScript / Python
→ 소스 파일, 빌드 결과물, 패키지 단위 중심의 컴포넌트
```

---

## 4. 잘 설계된 컴포넌트의 조건

```text
독립적으로 배포 가능
독립적으로 개발 가능
독립적으로 변경 가능
다른 컴포넌트와 명확한 경계로 결합 가능
```

독립적으로 배포 가능하고, 독립적으로 개발 가능해야 한다는 점!!

컴포넌트가 다른 코드와 너무 강하게 얽혀 있으면 안 됨.
한 컴포넌트를 수정하거나 배포하기 위해 시스템 전체를 매번 다시 수정해야 한다면,  
그 컴포넌트는 독립적인 단위라고 보기 어려움.

## 5. 소스코드와 바이너리의 차이

그러면 소스코드랑 바이너리 그게 뭘까

### 소스코드

소스코드는 사람이 읽고 작성하는 코드

```text
.java
.js
.ts
.py
.cs
.rb
```

소스코드는 개발자가 이해하고 수정할 수 있는 형태

### 바이너리

바이너리는 컴퓨터가 실행하거나 로드할 수 있는 형태로 변환된 결과물

```text
.class
.jar
.dll
.exe
.so
컴파일된 실행 파일
번들링된 배포 파일
```

컴파일형 언어에서는 소스코드가 컴파일 과정을 거쳐 바이너리 형태로 바뀐다.  
인터프리터형 언어에서는 소스코드가 직접 실행되거나, 런타임이 내부적으로 해석·변환하면서 실행된다.

```text
소스코드
→ 사람이 작성하고 읽는 코드

바이너리
→ 컴퓨터가 실행하거나 로드할 수 있는 형태의 결과물
```

컴포넌트는 이 둘 중 하나의 형태로 존재할 수 있음.
컴파일형 언어에서는 바이너리 파일의 결합체로 나타날 수 있고,  
인터프리터형 언어에서는 소스 파일의 결합체로 나타날 수 있음.

---

## 6. 컴파일, 로드, 링크

컴포넌트의 역사를 이해하려면 컴파일, 로드, 링크의 개념도 필요.

### 컴파일

컴파일은 사람이 작성한 소스코드를 기계가 이해할 수 있는 형태로 변환하는 과정

```text
소스코드
→ 컴파일
→ 목적 파일 또는 실행 가능한 코드
```

### 로드

로드는 프로그램을 실행하기 위해 메모리에 올리는 과정

```text
프로그램 파일
→ 메모리로 로드
→ 실행 준비
```

### 링크

링크는 여러 개로 나뉜 코드 조각이나 라이브러리를 서로 연결해 하나의 실행 가능한 프로그램으로 만드는 과정

```text
개별적으로 컴파일된 코드 조각들
→ 링크
→ 실행 가능한 프로그램
```

초기에는 링크 과정이 지금보다 훨씬 번거롭고, 프로그래머가 직접 신경 써야 하는 부분이 많았음.  
즉, 프로그램을 여러 조각으로 나누어 컴파일하더라도,  
그 조각들을 다시 결합하는 책임이 프로그래머에게 크게 남아 있었음.

---

## 7. 링킹 로더의 등장

링킹 로더의 등장은 컴포넌트 개념의 발전과 연결

링킹 로더는 프로그램을 개별적으로 컴파일하고,  
로드할 수 있는 단위로 분할할 수 있게 해주었음.

```text
프로그램 전체를 한 번에 컴파일하고 실행
↓
프로그램을 여러 단위로 나누어 컴파일
↓
필요한 단위들을 로드하고 링크
```

이 변화는 프로그램을 더 작은 단위로 나누고,  
각 단위를 독립적으로 관리할 수 있는 가능성을 열었다.

---

## 8. 프로그램의 크기와 시간 비용

프로그램은 계속 커지고,
그리고 프로그램이 커질수록 컴파일과 링크에 필요한 시간도 늘어남.

```text
컴파일하고 링크하는 데 사용 가능한 시간을 모두 소모할 때까지 프로그램은 커진다.
```

이 말은 기술 발전이 프로그램의 크기를 줄이는 방향으로만 작동하지 않는다는 뜻이다.  
컴퓨터가 더 빨라지고 저장공간이 커지면, 개발자들은 그만큼 더 큰 프로그램을 만들게 된다.

즉, 도구가 빨라져도 소프트웨어는 그 여유를 다시 소비한다.
현대에도 이 문제는 여전히 유효한 듯.

```text
빌드 시간이 길어지는 문제
배포 파일 크기가 커지는 문제
의존성 패키지가 과도하게 늘어나는 문제
애플리케이션이 무거워지는 문제
CI/CD 시간이 증가하는 문제
개발 피드백 루프가 느려지는 문제
```

컴포넌트를 잘 나누는 것은
개발 속도와 배포 비용, 시스템 유지보수 비용과도 연결됨

---

## 9. 무어의 법칙과 소프트웨어 크기

무어의 법칙은 반도체 집적도가 일정 기간마다 증가한다는 관찰에서 출발한 법칙이다.  
일반적으로는 하드웨어 성능이 시간이 지나며 빠르게 향상된다는 의미로 이해된다.

```text
하드웨어 성능이 좋아짐
→ 더 큰 프로그램을 만들 수 있음
→ 프로그램이 더 복잡해짐
→ 다시 빌드, 배포, 유지보수 비용이 증가
```

즉, 하드웨어 발전은 소프트웨어 문제를 완전히 없애주지 않는다.  
오히려 더 큰 소프트웨어를 만들 수 있게 하면서 복잡성을 다시 키우기도 한다.

이 관점에서 컴포넌트는 커지는 소프트웨어를 다루기 위한 구조적 대응으로 볼 수 있다.

```text
커지는 시스템을 작은 배포 단위로 나누기
변경되는 부분과 변경되지 않는 부분을 분리하기
독립적으로 개발하고 배포할 수 있는 단위 만들기
```

## 10. 이 장에서의 컴포넌트 정의

이 장의 흐름에서 컴포넌트는 다음과 같이 정의할 수 있다.

```text
소프트웨어 컴포넌트
→ 런타임에 플러그인 형태로 결합할 수 있는 동적 링크 파일
```

이 정의에서 중요한 부분은 두 가지다.

```text
런타임에 결합 가능
플러그인 형태로 결합 가능
```

즉, 컴포넌트는 시스템의 일부로 존재하지만,  
반드시 처음부터 하나로 단단히 묶여 있어야 하는 것은 아니다.

잘 설계된 컴포넌트는 필요할 때 결합되고,  
필요하면 교체될 수 있는 구조를 가진다.

---

## 11. 컴포넌트와 플러그인 아키텍처

컴포넌트의 최종적인 의미는 플러그인 아키텍처와 연결된다.

플러그인 아키텍처는 핵심 시스템은 유지한 채,  
바깥의 기능을 끼워 넣거나 교체할 수 있는 구조다.

```text
핵심 시스템
→ 안정적으로 유지되어야 하는 부분

컴포넌트
→ 독립적으로 개발·배포·교체 가능한 부분

플러그인 아키텍처
→ 컴포넌트를 핵심 시스템에 결합하는 방식
```

즉, 컴포넌트는 단순한 파일 묶음이 아니라,  
시스템을 플러그인 구조로 만들기 위한 배포 단위이자 결합 단위다.

컴포넌트를 잘 나누면 다음이 가능해진다.

```text
기능별 독립 개발
기능별 독립 배포
변경 영향 범위 축소
시스템 일부 교체 가능
빌드와 배포 단위 분리
팀 단위 개발 구조 정리
```

---

## 12. SOLID와 컴포넌트 원칙의 관계

SOLID와 컴포넌트 원칙은 서로 다른 수준의 설계 원칙이다.

```text
SOLID
→ 클래스, 모듈, 작은 코드 단위를 어떻게 나눌 것인가

컴포넌트 원칙
→ 더 큰 배포 단위와 결합 단위를 어떻게 나눌 것인가
```

책의 비유를 다시 가져오면 다음과 같다.

```text
SOLID
→ 벽돌을 어떻게 배치해 벽과 방을 만들 것인가

컴포넌트 원칙
→ 방들을 어떻게 배치해 빌딩을 만들 것인가
```

즉, SOLID가 코드 내부의 책임과 의존성을 정리하는 원칙이라면,  
컴포넌트 원칙은 그 정리된 코드들을 배포 가능한 단위로 묶고,  
시스템 전체 안에서 결합하는 방법을 다룬다.

---

# 정리

12장의 핵심은 컴포넌트를 단순한 코드 묶음이 아니라,  
독립적으로 개발하고 배포하고 결합할 수 있는 시스템 구성 단위로 이해하는 것이다.

```text
컴포넌트
→ 시스템의 구성요소로 배포 가능한 가장 작은 단위

잘 설계된 컴포넌트
→ 독립적으로 개발 가능
→ 독립적으로 배포 가능
→ 독립적으로 교체 가능

컴포넌트 아키텍처
→ 커지는 소프트웨어를 관리 가능한 단위로 나누는 방법

플러그인 아키텍처
→ 컴포넌트를 런타임에 결합하거나 교체할 수 있는 구조
```

이 장에서 얻을 수 있는 핵심 관점은 다음과 같다.

> 소프트웨어가 커질수록 중요한 것은 코드를 단순히 많이 작성하는 것이 아니라,  
> 변경과 배포를 감당할 수 있는 단위로 시스템을 나누는 것

SOLID가 작은 코드 단위의 배치 원칙이라면,  
컴포넌트 원칙은 시스템을 구성하는 큰 단위의 배치 원칙이다.
