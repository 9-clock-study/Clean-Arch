# 12장 컴포넌트

컴포넌트는 배포 단위이며 시스템의 구성 요소로 배포할 수 있는 가장 작은 단위다.

자바의 경우 jar 파일이 컴포넌트다.

루비에서는 gem, 닷넷에서는 DLL이다.

컴포넌트는 바이너리 파일의 결합체다.

인터프리터형 언어의 경우는 소스 파일의 결합체다.

모든 언어에서 컴포넌트는  배포할 수 있는 단위 입자다.

이 컴포넌트를 서로 연결하여 실행 가능한 단일 파일로 생성할 수 있다.

또는 여러 컴포넌트를 묶어서 .war 파일과 같은 단일 아카이브로 만들 수 있다.

또는 컴포넌트 각각을 .jar나 .dll 같이 동적으로 로드할 수 있는 플러그인이나

exe 파일로 만들어서 독립적으로 배포할 수 있다.

컴포넌트가 마지막에 어떤 형태로 배포되든 잘 설계된 컴포넌트라면 반드시 독립적으로 배포 가능한 능력을 갖춰야 한다.

컴포넌트 이전은 소스 코드를 애플리케이션 코드에 직접 포함시켜서 단일 프로그램으로 컴파일 했다.

라이브러리는 바이너리가 아니라 소스 코드 형태로 유지되었다.

이 시대에는 장치는 느리고 메모리는 너무 비싸서 자원이 한정적이었기에 이러한 접근법은 문제가 있다.

컴파일 과정이 오래 걸렸고 함수 라이브러리가 크면 클수록 컴파일은 더 오래 걸렸다.

따라서 컴파일 시간을 단축시키기 위해 함수 라이브러리의 소스 코드를 애플리케이션 코드로부터 분리

함수 라이브러리를 개별적으로 컴파일 → 컴파일된 바이너리를 메모리의 특정 위치로 로드

함수 라이브러리에 대한 심벌 테이블 생성 → 애플리케이션 코드 컴파일

애플리케이션 실행 시 바이너리 함수 라이브러리를 로드한 다음 애플리케이션을 로드

함수 라이브러리에 더 많은 함수를 추가하면 할당된 메모리 주소를 넘어서는 순간이 생기고

결국 추가 공간을 할당해야 한다.

프로그램과 라이브러리가 사용하는 메모리가 늘어날수록 단편화는 계속됨.

### 재배치성

해결책은 로더를 사용해 메모리에 재배치할 수 있는 형태의 바이너리를 생성하도록 컴파일러를 수정

로더는 재배치 코드가 자리할 위치 정보를 전달받음 → 재배치 코드에는 로드한 데이터에서 어느 부분을 수정해야 정해진 주소에 로드할 수 있는지 알려주는 플래그 삽입

플래그는 바이너리에서 참조하는 메모리의 시작 주소

함수 라이브러리를 로드할 위치와 애플리케이션을 로드할 위치를 로더에게 지시할 수 있게 됨

실제 로더는 여러 개의 바이너리를 입력받은 후, 차례로 메모리로 로드하면서 재배치하는 작업 처리

이를 통해 오직 필요한 함수만 로드 가능

컴파일러는 재배치 가능한 바이너리 안의 함수 이름을 메타데이터 형태로 생성하도록 수정

라이브러리 함수를 호출할 시 컴파일러는 라이브러리 함수 이름을 외부 참조로 생성

라이브러리 함수를 정의하는 프로그램이라면 컴파일러는 해당 이름을 외부 정의로 생성

외부 정의를 로드할 위치가 정해지기만 하면 로더가 외부 참조를 외부 정의에 링크시킬 수 있는 것을 링킹 로더라 한다.

### 링커

링킹 로더는 컴파일하고 로드할 수 있는 단위로 분할할 수 있게 되었다.

작은 프로그램과 비교적 작은 라이브러리를 링크할 때 이러한 방식으로 잘 동작함

링킹 로더가 너무 느려서 함수 라이브러리는 자기 테이프와 같이 느린 장치에 저장되었다.

링킹 로더는 대체로 느린 장치를 사용해 수십에서 수백 개의 바이너리 라이브러리를 읽고 외부 참조를 해석해야 했다.

프로그램은 커지고 라이브러리 함수가 라이르러리로 쌓이면서 링킹 로더가 프로그램 하나를 로드하는 데 한 시간 이상 소요됨

따라서 로드와 링크가 두 단계로 분리되었다.

링커라는 별도의 애플리케이션으로 작업을 처리하도록 만듬

링커는 링크가 완료된 재배치 코드를 만들고 로더의 로딩 과정이 빨라짐

느린 링커를 사용해 실행 파일을 만들었지만 한번 만든 실행 파일은 빠르게 로드 가능해짐

각 모듈을 컴파일 하는 과정은 빨랐지만 전체 모듈을 컴파일하는 일을 시간이 걸렸다.

이후에 링커에서는 더 많은 시간이 소요되었다.

전체 소요 시간이 늘어났다.

수만은 과정 속 로드 시간은 여전히 빨랐지만 컴파일-링크 시간이 병목 구간이었다.

“컴파일하고 링크하는 데 사용 가능한 시간을 모두 소모할 때까지 프로그램은 커진다”

하지만 디스크가 작아지고 빨라졌다.

메모리는 저렴해져서 저장된 많은 데이터를 모두 램에 캐싱할 수 있다.

링크 시간은 초단위 수준으로 감소되었다.

소규모 작업이라면 링킹 로더 마저도 다시 사용할 수 있을 정도였다.

이렇게 액티브 X와 공유 라이브러리 시대가 생기며 .jar 파일도 등장하였다.

컴퓨터와 장치가 빨라져 로드와 링크를 동시에 할 수 있게 되었다.

다수의 .jar 파일 또는 다수의 공유 라이브러리를 순식간에 서로 링크하고 링크가 끝난 프로그램을 실행 가능

이렇게 컴포넌트 플러그인 아키텍처가 탄생

### 결론

런타임에 플러그인 형태로 결합할 수 있는 동적 링크 파일이 이 책에서 말하는 소프트웨어 컴포넌트에 해당

과거에는 노력을 들여야 컴포넌트 플러그인 아키텍처를 적용할 수 있었지만 이제는 기본적으로 쉽게 사용 가능
