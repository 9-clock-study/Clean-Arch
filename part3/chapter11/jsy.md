# DIP

DIP에서 말하는 유연성이 극대화된 시스템이란 소스 코드 의존성이 추상에 의존하며 구체에는 의존하지 않는 시스템

DIP가 적용되는 대상은 변동성이 큰 구체적인 요소!
OS처럼 변하지 않는 구체는 무시하는 편

특히 구체적인 요소란 우리가 열심히 개발하는 중이라서 자주 변경될 수밖에 없는 모듈들

# 안정된 추상화

- 인터페이스를 변경하지 않고도 구현체에 기능을 추가하는 방법을 찾기 위해 애쓸 것
  안정된 s/w 아키텍처란 변동성이 큰 구현체에 의존하는 일은 지양, 안정된 추상 인터페이스를 선호하라

## 매우 구체적인 실전 코딩법!

1. 변동성이 큰 구체 클래스를 참조하지 말 것 : 추상 인터페이스의 사용 (추상 팩토리의 강제성)
2. 변동서이 큰 구체 클래스로부터 파생하지 말 것 : 상속은 소스 코드에 존재하는 모든 관계중 가장 강력한 동시에 뻣뻣해서 변경하기 어렵다, 따라서 상속은 신중히 사용해야한다. (신중에 신중에 신중을 가할 것 )
3. 구체 함수를 오버라이드 하지 말 것 : 차라리 추상함수로 선언하고 구현체들에서 각자의 용도에 맞게 구현할 것 <LSP랑도 연관이 있겠네, 인터페이스(추상)이 너무 뚱뚱해지면 안되니깐>

# 팩토리

아키텍처 경계 : 이 경계선은 컴포넌트를 나누는 경계로 쓰일수도있고, 추상/구체에 대한 경계로서 쓰일 수도 있음

소스코드 의존성은 해당 경계와 교차할 때 모두 한 방향, 즉 추상적인 쪽으로 향한다.(p94, 그림 11.1)

경계는 시스템을 두 가지 컴포넌트로 분리한다.

하나는 추상 컴포넌트이며 다른 하나는 구체 컴포넌트이다. 추상 컴포넌트는 app의 모든 고수준 업무 규칙을 포함(ocp에서 interactor를 생각하면됨)한다.

구체 컴포넌트는 업무 규칙을 다루기 위해 필요한 모든 세부사항을 포함한다.

제어흐름은 소스 코드 의존성과는 정반대 방향으로 곡선을 가로지른다.
다시 말해 소스 코드 의존성은 제어흐름과는 반대 방향으로 역전(의존성 역전이라 함)
