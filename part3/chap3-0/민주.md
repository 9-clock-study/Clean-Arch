# 3장 설계 원칙 - 서론

좋은 소프트웨어 시스템은 깔끔한 코드, **클린 코드**로부터 시작된다.

좋은 벽돌을 사용하지 않으면 빌딩의 아키텍처가 좋고 나쁨은 그리 큰 의미가 없는 것과 같다.

반대로 좋은 벽돌을 사용하더라도 빌딩의 아키텍처를 엉망으로 만들 수 있다.

그래서 좋은 아키텍처를 정의하는 원칙 중 SOLID가 필요하다.

SOLID 원칙은 함수와 데이터 구조를 클래스로 배치하는 방법과

이들 클래스를 서로 결합하는 방법론을 설명한다.

클래스라는 단어를 사용했다 하여서 SOLID 원칙이

객체 지향 소프트웨어에만 적용된다는 뜻은 아니다.

클래스는 단순히 함수와 데이터를 결합한 집합을 가리킨다.

소프트웨어 시스템은 모두 이러한 집합을 포함하고

이러한 집합이 클래스라고 불릴 수도 아닐 수도 있다.

SOLID 원칙은 이러한 집합에 적용된다.

SOLID 원칙의 목적은 변경에 유연하고, 이해가 쉽도록 하게 하고, 많은 SW 시스템에 사용되는 **컴포넌트**의 기반이 된다.

- 컴포넌트란
    
    
    **소프트웨어 및 웹 개발:** 재사용이 가능한 독립적인 소프트웨어 모듈(블록)을 의미
    
    - **프론트엔드(UI):** 화면을 구성하는 최소 단위. 버튼, 입력창, 체크박스 등이 해당. 이를 조립해 웹페이지나 앱 제작에 사용.
    - **백엔드 및 아키텍처:** 유지보수와 교체가 쉽도록 독립적인 기능을 수행하는 프로그램의 단위.
    
    **클래스(Class)**는 **객체를 만들기 위한 설계도**이며, 
    
    **컴포넌트(Component)**는 **”**독립적으로 작동하는 **재사용 가능한 부품”**입니다.

SRP : 단일 책임 원칙

→ 콘웨이 법칙에 따른 따름 정리 : SW 시스템이 가질 수 있는 최적의 구조는 시스템을 만드는 조직의 사회적 구조에 커다란 영향을 받음. 

→ 따라서 SW 모듈은 변경의 이유가 하나여야만 한다.

OCP : 개방 폐쇄 원칙

→ 1980년대에 버트란트 마이어에 의해 유명해진 원칙이다.

→ 기존 코드를 수정하기보다는 반드시 새로운 코드를 추가하는 방식으로 시스템의 행위를 변경할 수 있도록 설계해야만 SW 시스템을 쉽게 변경할 수 있다는 것의 원칙의 요지

LSP : 리스코프 치환 원칙

→ 1988년 바바라 리스코프가 정의한 하위 타입에 관한 원칙

→ 상호 대체 가능한 구성요소를 이용해 SW 시스템을 만들 수 있으려면 이들 구성요소는 반드시 서로 “치환 가능해야 한다”는 규칙을 반드시 지켜야 한다는 원칙

ISP : 인터페이스 분리 원칙

이 원칙을 따르면 SW 설계자는 사용하지 않은 것에 의존하지 않아야 한다.

DIP : 의존성 역전 원칙

고수준 정책을 구현하는 코드는 저수준 세부사항을 구현하는 코드에 절대로 의존해서는 안 된다.

대신 세부사항이 정책에 의존해야 한다.
