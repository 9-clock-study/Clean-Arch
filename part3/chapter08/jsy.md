# OCP

**"개체는 확장에는 열려있어야 하고, 변경에는 닫혀있어야 한다."**
-> s/w arch를 공부하는 가장 근본적 이유

if 요구사항을 살짝 확장하는 데 s/w를 엄청나게 수정해야 한다면?  
그 s/w를 설계한 arch는 잘못됨

OCP를 클래스와 모듈을 설계할 때 도움이 되는 원칙  
**다만 이것보다 아키텍쳐 컴포넌트 수준에서 OCP를 고려할 때 훨씬 더 중요한 의미를 가짐**

s/w 아키텍쳐가 훌륭하다면 변경되는 코드의 양은 가능한 한 최소화 될 것이다.

> 그럼 어떻게 해야 변경되는 코드가 최소로 될 수 있게 할 것인가?

서로 다른 목적으로 변경되는 요소를 적절하게 분리(SRP) 이들 사이의 의존성을 체계화(DIP)

책임을 분리했다면 두 책임 중 하나에서 변경이 발생하더라도 다른 하나는 변경되지 않도록 소스 코드 의존성을
조직화 해야 함 + 조직화한 구조에서 행위가 확장될 때 변경이 발생하지 않음을 보장해야함

클래스를 컴포넌트 단위로 구분하는게 중요.

> 대체 이 책에서 말하는 컴포넌트, 모듈, 클래스 이 정의가 뭐야 왤케 난잡해?
> OCP를 준수하기 위해서는 클래스도 컴포넌트 단위로 격리시켜야된다는 얘기인가?..

A컴포넌트에서 발생한 변경으로부터 B 컴포넌트를 보호하려면 A가 B에 의존해야한다.

변경이 일어나면 안되는 최상위 컴포넌트는 비즈니스 규칙을 포함해야한다.<지켜야되는 컴포넌트>
여기서 말하는 최상위 컴포넌트는 애플리케이션에서 가장 높은 수준의 정책을 포함한다.

보호의 계층구조가 수준이라는 개념을 바탕으로 어떻게 생성되는지 주목.

아키텍트는 기능이 어떻게 왜 언제 발생하는지에 따라 기능을 분리하고 분리한 기능을 컴포넌트 계층구조로 조직화한다.

# 방향성제어

OCP 원칙을 따르기 위해선 DIP가 필요
만약 중간에 <Interface>를 두지 않는다면 의존성이 바로 다른 컴포넌트로 향하게 됨.

```
a -> b

a에서 발생한 변경으로부터 B를 보호하려면 반드시 a가 b에 의존해야함

controller(b)
↑
presenter(a)



presenter(a)에서 발생한 변경으로부터 controller(b)를 보호하기 위해서는 presenter가 controller에 의존해야 한다.

즉, presenter는 controller에 의존해야 됨

근데 controller에서도 변경이 발생하면 presenter를 지켜줘야하는데 이를 DIP로 방향성 제어를 한다.

즉 중간에 interface를 둬서 서로 몰라도 되는 상태를 만든다.

```

의존성이 interactor -> DB로 향하게 되면 안됨 더 추상적인 interactor로 방향을 틀어야함 그래야
고수준 모듈을 보호할 수 있음
