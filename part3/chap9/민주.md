## 9장 LSP : 리스코프 치환 원칙

1988년 바바라 리스코프는 하위 타입을 아래와 같이 정의했다.

→ 여기에 필요한 것은 다음과 같은 치환 원칙이다.

1. S 타입의 객체 o1 각각에 대응하는 T 타입 객체 o2가 있다.
2. T타입을 이용해서 정의한 모든 프로그램 P에서 o2 자리에 o1을 치환하더라도 P의 행위가 변하지 않는다면 S는 T의 하위 타입이다.

리스코프 치환 원칙으로 알려진 이 개념을 이해하기 위해 예제를 살펴보자.

### 상속을 사용하도록 가이드하기

라이센스라는 클래스가 있다. 이 클래스는 calcFee() 메서드를 가진다.

Billing 애플리케이션에서 calcFee를 호출한다.

라이센스 클래스에는 개인 라이센스와 비즈니스 라이센스라는 두 가지 하위 타입이 존재한다.

이들 두 하위 타입은 서로 다른 알고리즘을 이용해 라이선스 비용을 계산한다.

이 설계는 LSP를 준수한다.

Billing 애플리케이션 행위가 라이센스 하위 타입 중 무엇을 사용하는지 전혀 의존하지 않기 때문이다.

이들 하위 타입은 모두 라이센스 타입을 치환할 수 있다.

### 정사각형과 직사각형 문제

LSP를 위반하는 전형적 문제로는 유명한 정사각형과 직사각형 문제가 있다.

이 예제는 Squre는 Rectangle의 하위 타입으로 적합하지 않다.

Rectangle의 높이와 너비는 서로 독립적으로 변경 가능하다.

반면, Squre의 높이와 너비는 반드시 함께 변경된다.

User는 대화하고 있는 상대가 Rectangle이라고 생각하므로 혼동이 생길 수 있다.

아래의 코드를 보면 혼동의 이유가 분명해진다.

```jsx
Rect r = new Squre()
r.setW(5);
r.setH(2);
assert(r.area() == 10);
```

Squre를 생성하면 assert문은 실패한다.

이런 형태의 LSP 위반을 막기 위한 유일한 방법은 

if문 등을 이용해서 Rectangle이 실제로 Squre인지를 검사하는 매커니즘을 User에 추가하는 것이다.

하지만 이렇게 하면 User의 행위가 사용하는 타입에 의존하게 되므로 결국 타입을 서로 치환할 수 없게 된다.

### LSP와 아키텍처

LSP는 상속을 사용하도록 가이드하는 방법 정도로 간주되었다.

하지만 시간이 지나면서 LSP는 인터페이스와 구현체에도 적용되는 광범위한 설계 원칙으로 변해왔다.

여기에서 말하는 인터페이스는 다양한 형태로 나타난다.

자바의 경우 인터페이스 하나와 이를 구현하는 여러 개의 클래스로 구성된다.

루비의 경우 동일한 메서드 시그니처를 공유하는 여러 개의 클래스로 구성된다.

또는 동일한 REST 인터페이스에 응답하는 서비스 집단일 수 있다.

잘 정의된 인터페이스와 그 인터페이스의 구현체끼리 상호 치환 가능성에 기대는 사용자들이 존재하다.

아키텍처 관점에서 LSP를 이해하는 최선의 방법은 이 원칙을 어겼을 때 **시스템 아키텍처에서 무슨 일이 일어나는지 관찰**하는 것이다.

### LSP 위배 사례

카카오 택시 같은 서비스를 통합하는 애플리케이션을 만든다 가정한다.

고객은 어느 택시업체인지 신경쓰지 않고 자신의 상황에 가장 적합한 택시를 찾는다.

고객이 이용할 택시를 결정하면 시스템은 REST 서비스를 통해 선택된 택시를 고객 위치로 파견한다.

택시 서비스의 URI가 운전기사 데이터베이스에 저장되어 있다 가정한다.

시스템이 고객에게 알맞은 기사를 선택하면, 해당 기사의 레코드로부터 URI 정보를 얻은 다음,

그 URI 정보를 이용하여 해당 기사를 고객 위치로 파견한다.

파견 서비스를 만들 때 다양한 택시업체가 동일한 REST 인터페이스를 반드시 준수하도록 만들어야 한다는 사실이다. 서로 다른 택시업체가 필드를 모두 동일한 방식으로 처리해야 한다.

애크미는 지역의 가장 큰 택시업체이며,

대표의 전처는 우리회사 대표의 아내가 되었다.

이러한 경우 예외 사항을 처리하는 로직을 추가해야 할 것이다.

애크미 소속 기사 파견하는 요청은 나머지 업체의 기사를 파견할 때와 다른 규칙을 이용해 구성한다.

이를 위해 가장 간단한 방법은 IF 문장을 추가해야 한다는 것이다.

하지만 실력 있는 아키텍트라면 당연히 시스템을 이런 식으로 구성하는 것을 용납하지 않는다.

아키텍트는 REST 서비스들의 인터페이스를 서로 치환 가능하지 않는다는 사실을 처리하는 중요한 복잡한 매커니즘을 추가해야 한다.

### 결론

LSP는 아키텍처 수준까지 확장할 수 있고, 반드시 확장해야만 한다.

치환 가능성을 조금이라도 위배하면 시스템 아키텍처가 오염되어 상당량의 별도 매커니즘을 추가해야 할 수 있다.

### LSP 느낀점

처음 LSP 서론 내용을 읽었을 때 상속에 대한 개념을 설명하는 것이 느껴졌다.

더 나아가서 정사각형과 직사각형 문제 예시로 상속의 캐스팅 문제를 서술한 것으로 보아

LSP의 가장 대표적 키워드는 앞에서 가장 먼저 말했던 **상속**인 것으로 보인다.

상속 개념 중 “하위 타입이 상위 타입을 따라가는 것”까지는 일치한다.

다만, 하위 타입이 상위 타입을 완전히 대체할 수 있어야 한다. 가 LSP인 것 같다.

따라서 다시 정리하면 LSP는 “프로그램의 객체는 프로그램의 정확성을 깨뜨리지 않고 하위타입의 인스턴스를 변경할 수 있다.”

해당 챕터의 택시 예제를 읽었을 때 자주 사용되는 예시로 생각나는 것은 

이전 챕터에서 설명한 결제 시스템이 좀 더 어울리는 것 같았다.

결제 시스템 코드 예시는 다음과 같다.

```jsx
PaymentService paymentService = new KakaoPayService();
```

이렇게 Pay 서비스에서 카카오페이 서비스 코드를 가져온다.

이런 경우에 다음과 같이 토스페이로 교체한다고 하자.

```jsx
PaymentService paymentService = new TossPayService();
```

이렇게 변경하여도 주문 서비스 코드는 전혀 수정되지 않는 것이 실무적으로 LSP의 예시라고 볼 수 있을 것 같다.
