## 7장 SRP : 단일 책임 원칙

의미가 가장 잘 전달되지 못한 원칙이 바로 **단일 책임 원칙**이다.

부적절한 이름 때문일 것.

프로그래머가 모든 모듈이 단 하나의 일만 해야 한다는 의미로 받아들이기 쉬움.

단 하나의 일만 해야 한다는 원칙은 사실 따로 있다.

그것은 바로 함수는 반드시 하나의 일만 해야 한다는 원칙이다.

이 원칙은 커다란 함수를 작은 함수로 리팩터링 하는 더 저수준에서 사용된다.

이 원칙은 SOLID도 SRP도 아니다.

SRP는 아래와 같이 기술되었다.

→ 단일 모듈은 변경의 이유가 하나, 오직 하나뿐이어야 한다.

SW 시스템은 사용자와 이해관계자를 만족시키기 위해 변경된다.

이 원칙은 아래와 같이 바꿔 말할 수 있다.

→ 하나의 모듈은 하나의, 오직 하나의 “사용자” 또는 “이해관계자”에 대해서만 책임져야 한다.

하지만 사용자와 이해관계자라는 단어를 사용하는 것은 올바르지 않음.

시스템이 동일한 방식으로 변경되기를 원하는 사용자나 이해관계자가 두 명이 된다면 이야기가 달라짐.

집단, 해당 변경을 요청하는 한 명 이상의 사람들로 변경해서

이러한 집단을 Actor라고 부르겠다.

이렇게 SRP의 최종 버전은 다음과 같다.

### “하나의 모듈은 하나의, 오직 하나의 액터에 대해서만 책임져야 한다.”

모듈이란 무슨 뜻인가? → 단순하게 소스 파일.

일부 언어와 개발 환경에서는 코드를 소스 파일에 저장하지 않는다.

이러한 경우 모듈은 함수와 데이터 구조로 구성된 응집된 집합이다.

“응집된”이란 단어가 SRP를 암시하고, 단일 액터를 책임지는 코드를 함께 묶어주는 힘이 응집성이다.

### 징후 1) 우발적 중복

서로 다른 액터가 의존하는 코드를 가까이 배치하는 문제가 종종 발생한다.

SRP는 서로 다른 액터가 의존하는 코드를 서로 분리해야 한다고 말한다.

### 징후 2) 병합

소스 파일에 다양한 메서드를 포함하면 병합이 발생한다고 한다.

특히 메서드가 서로 다른 액터를 책임지면 병합이 발생할 가능성이 높음.

두 명의 개발자가 작업을 하다가 변경사항에서 충돌이 일어나고, 결과적으로 병합이 발생함.

모두 많은 사람이 서로 다른 목적으로 동일한 소스 파일을 변경하는 경우 해당한다.

이 문제를 벗어나는 방법은

**서로 다른 액터를 뒷받침하는 코드를 서로 분리하는 것**이다.

### 해결책

모두 다른 메서드를 각기 다른 클래스로 이동시키는 방식이 해결책이 된다.

확실한 해결책으로 데이터와 메서드를 분리하는 방식.

즉, 아무런 메서드가 없는 EmployeeData 클래스를 만들어

세 개의 클래스가 공유하도록 한다.

각 클래스는 자신의 메서드에 반드시 필요한 소스코드만 포함한다.

세 클래스는 서로의 존재를 몰라야 한다.

따라서 우연한 중복을 피할 수 있다.

이 해결책은 세 가지 클래스를 인스턴스화하고 추적해야 한다는 게 단점이다.

이러한 난관에서 빠져나올 때 흔히 쓰는 기법으로 **퍼사드 패턴**이 있다.

퍼사드 클래스에는 코드가 없고, 세 클래스의 객체 생성 및 요청된 메서드를 가지는 객체로 위임하는 일을 책임진다.

가장 중요한 업무규칙을 데이터와 가깝게 배치하는 방식을 선호하고 이 경우 가장 중요한 메서드는 클래스에 그대로 유지하지만 그 외 덜 중요한 나머지 메서드를 퍼사드로 사용할 수 잇음.

모든 클래스는 반드시 하나의 메서드를 가져야 한다는 주장에 근거하여 앞의 해결책에 반대할 수 있음.

### 결론

단일 책임 원칙은 메서드와 클래스 수준의 원칙이다.

이보다 상위의 두 수준에서도 다른 형태로 다시 등장한다.

컴포넌트 수준에서는 공통 폐쇄 원칙(Common Closure Principle)이 된다.

아키텍처 수준에서는 아키텍처 경계의 생성을 책임지는 변경의 축이 된다.

### 7장 단일 책임 원칙 느낀점

이전까지 SRP의 대표적인 예시는 싱글톤 패턴이라고 생각하고,

단순히 책에서 나온 얘기처럼 하나의 메서드와 하나의 데이터를 따로따로 관리하는 수준이라 생각했다.

예시 코드로는 이런 코드를 **싱글톤 패턴**이라 생각하고 **단일 책임 원칙**이라 생각했다.

**Before**

```jsx
int num = 0;
if(num = 1){
...
}else {
}
```

**After**

```jsx
int num = 0;
if(num = 1){
...
}

if(num = 2){
...
}
```

책에서 말한 거처럼 이러한 패턴들로 하나를 분리한다는 개념이 아니라

하나로 분리하지 않으면 병합으로 인한 충돌이 생길 것이고,

하나로 분리하는 것에도 문제가 생길 수 있다 생각이 들었다.

가장 흥미로운 점은 이전에 배운 디자인 패턴의 퍼사드 패턴이 해결책이 된다는 점이 흥미로웠다.

해당 내용으로 보면 모듈 단위, 하나의 액터를 분리해서 책임을 진다는 설명으로 미루어봐서

스프링에서 Controller, Service, Repository 등으로 역할을 나누어

각각의 클래스가 특정 기능과 관심사에만 집중할 수 있는 것이 SRP 중 하나라고 볼 수 있다.
