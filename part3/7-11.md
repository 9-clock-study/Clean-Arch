# SOLID 원칙 정리

SOLID 원칙 : **변경을 최소화하고 의존성을 통제하기 위한 설계 원칙**

---

## 1. SRP: 단일 책임 원칙

### 개념

“단일 책임”은 다음과 같은 의미가 아님.

```text
하나의 함수는 단 하나의 일만 해야 한다.
```

이건 그냥 좋은 함수 설계 원칙(SRP의 핵심은 아님)

SRP의 핵심은 다음과 같다.

```text
하나의 모듈은 하나의 사용자 또는 하나의 액터에 대해서만 책임져야 한다.
```

액터 == 해당 모듈의 변경을 요구하는 주체
어떤 모듈이 여러 액터의 요구사항에 동시에 영향을 받는다면, 그 모듈은 여러 이유로 변경될 수 있게 된다.

```text
하나의 모듈은 오직 하나의 변경 이유만 가져야 한다.
```

---

## 2. SRP와 응집성

응집성 : 서로 밀접하게 관련된 코드들이 하나의 단위로 잘 모여 있는 정도

```text
모듈 == 함수와 데이터 구조로 구성된 응집된 집합
```

=> SRP는 같은 액터의 요구에 의해 함께 변경되는 코드들을 하나로 묶는 원칙

---

## 3. SRP에 위배되는 경우

하나의 모듈이 여러 액터의 요구사항을 동시에 처리하게되면,
서로 관련 없는 변경이 하나의 코드에 집중되고, 수정된 부분에 대한 영향 범위가 커짐

### 1) 우발적 중복

우발적 중복 : 서로 다른 액터를 위한 코드가 우연히 같은 모듈 안에 들어가면서 발생하는 중복

겉으로 보기에는 같은 기능처럼 보여도, 실제로는 서로 다른 이유로 변경될 수 있음
이 경우 하나의 액터를 위해 코드를 수정했는데, 다른 액터가 사용하는 기능까지 영향을 받음

```text
SOLUTION
서로 다른 액터에 의존하는 코드를 분리
서로 다른 변경 이유를 가진 기능을 다른 모듈로 분리
```

=> 변경 이유가 다르면 분리하는 것이 안전한 설계

---

### 2) 병합 문제

병합 문제 : 여러 사람이 서로 다른 이유로 같은 파일이나 모듈을 수정하면서 발생 (아마 GIT에서 MERGE충돌이랑 비슷한 맥락이지 않을 까 싶음)

하나의 모듈이 여러 액터에 대한 책임을 동시에 가지고 있는 경우, 각각의 다른 요구사항이 같은 코드에 반영되면서 충돌 가능성이 커짐

```text
SOLUTION
데이터와 메서드 분리
서로 다른 책임을 가진 클래스로 분리
필요한 경우 파사드 패턴 사용
```

파사드 패턴 : 외부 - 단순한 인터페이스를 제공,  
내부 -실제 책임을 가진 객체들에게 요청 위임

=> 사용자는 하나의 단순한 객체를 사용하는 것처럼 보이지만, 실제 처리는 역할에 따라 분리된 객체들이 담당하는 구조

---

## 4. OCP: 개방-폐쇄 원칙

### 개념

```text
소프트웨어 개체는 확장에는 열려 있어야 하고, 변경에는 닫혀 있어야 한다.
```

새로운 요구사항이 생겼을 때 기존 코드를 직접 수정 지양 <<< 새로운 코드를 추가하는 방식으로 기능 확장

```text
확장에 열려 있다는 것
→ 새로운 기능이나 정책을 추가할 수 있음

변경에 닫혀 있다는 것
→ 기존 코드를 직접 수정하지 않아도 됨
```

=> 확장은 가능하지만, 그 확장을 위해 기존 코드가 계속 변경되면 안 됨!!

---

## 5. OCP의 핵심 의미

```text
변경이 발생하더라도 기존 코드의 수정 범위를 최소화하는 구조
```

기존 코드를 직접 수정하는 대신,
새로운 구현을 추가하고 기존 구조에 연결하는 방식으로 확장

OCP는 변경을 피하는 원칙이 아니라,  
변경의 영향을 통제하는 원칙

---

## 6. OCP와 아키텍처

아키텍처가 잘 설계되어 있으면 고수준 정책은 저수준 세부사항의 변경으로부터 보호가 됨

```text
중요한 정책
→ 쉽게 바뀌면 안 되는 핵심 규칙

세부사항
→ 화면, 데이터베이스, 프레임워크, 외부 시스템 등 바뀌기 쉬운 요소
```

OCP를 잘 적용한 구조에서는 세부사항이 바뀌어도 중요한 정책은 직접 수정되지 않음.
즉, 변경 가능성이 높은 부분과 보호해야 할 부분을 분리하는 것이 핵심

---

## 8. LSP: 리스코프 치환 원칙

```text
하위 타입은 상위 타입을 대체할 수 있어야 한다.
```

어떤 코드가 상위 타입을 사용하고 있다면,  
그 자리에 하위 타입이 들어와도 프로그램의 동작은 호환되어야 함

LSP는 단순히 상속 관계 확인보다는, 실제 동작이 기대를 깨지 않는지가 중요

---

## 9. LSP의 핵심 의미

LSP는 다음과 같은 상황을 경계

```text
- 상위 타입처럼 보이지만 실제로는 다르게 동작하는 하위 타입
- 상위 타입의 약속을 지키지 않는 하위 타입
- 하위 타입으로 교체했을 때 기존 코드가 깨지는 구조
```

객체지향에서 다형성을 사용하려면,  
상위 타입을 사용하는 코드는 구체적인 하위 타입이 무엇인지 몰라도 안전하게 동작해야 함

=> LSP는 다형성이 제대로 작동하기 위한 조건

---

## 10. ISP: 인터페이스 분리 원칙

```text
클라이언트는 자신이 사용하지 않는 메서드에 의존하지 않아야 한다.
```

클라이언트 : 인터페이스를 사용하는 쪽
=> 어떤 코드가 특정 기능만 딱 필요로 하는데,
큰 인터페이스에 그 기능과 상관없는 메서드까지 포함되어서 의존한다면 문제 발생

```text
큰 인터페이스 하나에 여러 역할을 몰아넣지 않고,
사용 목적에 따라 작은 인터페이스로 분리
```

---

## 11. ISP가 필요한 이유

인터페이스가 너무 크면 사용하는 쪽은 실제로 필요하지 않은 기능까지 알고 있게 됨

```text
사용하지 않는 기능의 변경에도 영향을 받음
인터페이스를 구현하는 클래스가 불필요한 메서드까지 구현해야 함
역할이 다른 기능들이 하나의 약속에 묶임
변경의 영향 범위가 넓어짐
```

=> ISP는 사용하는 쪽의 필요에 맞게 의존 범위를 줄이는 원칙

```text
필요한 것만 알게 만들기
사용하지 않는 것에는 의존하지 않게 만들기
인터페이스를 역할 단위로 나누기
```

---

## 12. ISP와 추상 팩토리 패턴

추상 팩토리 패턴 : 객체를 직접 생성하지 않고,  
객체 생성을 담당하는 추상적인 공장을 통해 필요한 객체를 얻는 방식

```text
사용하는 쪽은 구체적인 클래스 생성 방식을 모름
사용하는 쪽은 추상화된 생성 규칙만 앎
실제 생성되는 객체는 바깥에서 결정
```

=> ISP와 연결되는 지점은 **사용하는 쪽이 필요한 생성 기능만 알게 해야 한다는 점**

```text
너무 큰 팩토리 인터페이스
→ 여러 종류의 객체 생성 책임이 한곳에 모임
→ 사용하는 쪽이 필요 없는 생성 기능까지 알게 됨
→ 변경 영향 범위가 커짐
```

ISP를 적용하면 추상 팩토리도 역할에 따라 나눌 수 있다.

```text
필요한 객체군을 생성하는 작은 팩토리 인터페이스
클라이언트가 실제로 사용하는 생성 메서드만 포함하는 인터페이스
역할별로 분리된 생성 책임
```

=> 추상 팩토리 패턴은 구체적인 객체 생성을 숨기는 데 도움을 주고,  
ISP는 그 추상 팩토리의 인터페이스가 너무 비대해지지 않도록 도움

```text
추상 팩토리 패턴
→ 구체적인 객체 생성 방식을 숨기는 패턴

인터페이스 분리 원칙
→ 사용하는 쪽이 필요하지 않은 생성 기능에 의존하지 않게 만드는 원칙

둘의 연결
→ 객체 생성도 추상화하되, 그 추상화 역시 역할별로 작고 명확하게 분리
```

---

## 13. DIP: 의존성 역전 원칙

```text
중요한 코드는 바뀌기 쉬운 구체적인 기술에 의존하지 않아야 한다.
구체적인 기술이 중요한 코드가 정한 추상적인 규칙에 맞춰 들어와야 한다.
```

의존성 역전 : 중요한 코드가 구체적인 기술을 직접 알지 않게 만드는 원칙

일반적인 코드 구조

```text
중요한 코드 → 구체적인 기술
```

이 구조에서는 구체적인 기술이 바뀔 때 중요한 코드도 함께 수정될 가능성이 높음

DIP에 의한 구조

```text
중요한 코드 → 약속된 규칙 ← 구체적인 기술
```

---

## 14. DIP의 핵심 의미

DIP에서 중요한 것은 “구체적인 것”과 “추상적인 것”의 방향

```text
구체적인 것
→ 데이터베이스, 화면, 프레임워크, 외부 API, 파일 저장 방식처럼 바뀌기 쉬운 것

추상적인 것
→ 중요한 코드가 필요로 하는 약속된 규칙
```

```text
중요한 코드는 구체적인 기술을 직접 알지 않음
중요한 코드는 필요한 규칙만 앎
구체적인 기술은 그 규칙에 맞춰 연결됨
```

=> DIP는 중요한 코드를 바뀌기 쉬운 것들로부터 보호하기 위한 원칙

---

## 15. DIP와 의존성 규칙

```text
소스코드 의존성은 반드시 안쪽을 향해야 한다.
```

안쪽 : 중요한 규칙이 있는 영역
바깥쪽 : 화면, 데이터베이스, 프레임워크, 외부 시스템 같은 세부사항이 있는 영역

```text
안쪽
→ 중요한 규칙, 핵심 로직, 유스케이스

바깥쪽
→ UI, DB, 프레임워크, 외부 API, 장치, 네트워크
```

```text
안쪽 코드는 바깥쪽 코드를 몰라야 함
바깥쪽 코드는 안쪽 코드에 의존할 수 있음
이름, 클래스, 함수, 변수 등 바깥쪽에 있는 어떤 것도 안쪽 코드에 등장하면 안 됨
```

DIP는 이 의존성 규칙을 코드 수준에서 가능하게 만드는 원칙

보통은 안쪽의 중요한 코드가 바깥쪽의 구체적인 기술을 직접 호출하기 쉬운데,
그렇게 되면 의존성 규칙을 위반하게 됨
안쪽 코드가 바깥쪽 기술을 알아버리기 때문.

DIP를 적용하면 중간에 추상적인 규칙을 둠

```text
안쪽 중요한 코드 → 추상적인 규칙 ← 바깥쪽 구체적인 기술
```

=> 안쪽 코드는 바깥쪽 기술을 직접 알지 않게 되고,
바깥쪽 기술이 안쪽에서 정한 규칙에 맞춰 들어오게 됨

```text
의존성 규칙
→ 코드 의존성이 안쪽을 향해야 한다는 아키텍처 규칙

의존성 역전 원칙
→ 그 규칙을 지키기 위해 구체적인 기술 의존을 추상화로 뒤집는 설계 원칙
```

=> DIP는 의존성 규칙을 실현하기 위한 핵심 원칙이기도 함

---

## 16. SOLID 다섯 원칙의 연결

```text
SRP
→ 하나의 모듈이 하나의 변경 이유만 갖도록 책임을 분리

OCP
→ 새로운 요구사항이 생겨도 기존 코드를 직접 수정하지 않고 확장할 수 있는 구조

LSP
→ 확장된 구현이 기존 약속을 깨지 않고 대체 가능해야 하는 조건

ISP
→ 사용하는 쪽이 필요하지 않은 기능에 의존하지 않도록 인터페이스를 분리

DIP
→ 중요한 코드가 구체적인 기술이 아니라 추상적인 규칙에 의존하도록 의존 방향을 조정
```

이 다섯 원칙 모두 변경의 영향을 줄이기 위한 방향으로 연결된다는 점이 중요

```text
SRP는 변경 이유를 분리
OCP는 기존 코드 수정을 최소화
LSP는 확장된 구현의 안전한 교체를 보장
ISP는 불필요한 의존을 줄임
DIP는 중요한 코드를 바뀌기 쉬운 기술로부터 보호
```

# 원칙 한 줄 정리

```text
SRP
→ 변경 이유를 하나로 제한하는 원칙

OCP
→ 기존 코드를 직접 수정하지 않고 확장할 수 있게 만드는 원칙

LSP
→ 하위 타입이 상위 타입을 안전하게 대체할 수 있게 만드는 원칙

ISP
→ 사용하지 않는 기능에 의존하지 않도록 인터페이스를 분리하는 원칙

DIP
→ 중요한 코드가 구체적인 기술이 아니라 추상적인 규칙에 의존하게 만드는 원칙
```
