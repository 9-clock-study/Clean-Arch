## 8장 OCP : 개방 폐쇄 원칙

개방 폐쇄 원칙이라는 용어는 버트란트 마이어가 만들었는데, 정의는 다음과 같다.

→ 소프트웨어 개체는 확장에는 열려 있어야 하고, 변경에는 닫혀 있어야 한다.

다시 말해 SW 개체의 행위는 확장할 수 있어야 하지만,

이때 개체를 변경해서는 안 된다.

SW 아키텍처를 공부하는 가장 근본적인 이유는 바로 이 때문이다.

만약 요구사항을 살짝 확장하는 데 SW를 엄청나게 수정해야 한다면,

그 SW 시스템은 설계한 아키텍트는 엄청난 실패에 맞닥뜨린다는 것이다.

SW 설계를 공부하기 시작한 지 얼마 안 된 사람들 대다수는 OCP를 클래스와 모듈을 설계할 때 도움되는 원칙이라고 알고 있다.

하지만 아키텍처 컴포넌트 수준에서 OCP를 고려할 때 훨씬 중요한 의미를 가진다.

### 사고 실험

웹 페이지 예시) 재무재표 웹 페이지

요구사항 → 데이터는 스크롤 할 수 있고, 음수는 빨간색으로 출력

이해관계자가 동일한 정보를 변환해서 새로운 요구사항을 요구함.

이럴 경우 당연히 새로운 코드를 작성해야 하는데, 원래 코드를 얼마나 수정해야 할까?

SW 아키텍처가 훌륭하면 변경되는 코드의 양이 최소화될 것이다.

이상적인 변경량은 0이다.

서로 다른 목적으로 변경되는 요소를 적절하게 분리하고(단일 책임 원칙 SRP),

이들 요소 사이의 의존성을 체계화함으로써(DIP 의존성 역전 원칙) 변경량을 최소화할 수 있다.

의존성이 소스 코드 의존성을 나타낸다는 사실이다.

또 다른 점은 이중선은 화살표와 오직 한 방향으로만 교차한다는 사실이다.

모든 컴포넌트 관계는 단방향으로 이루어진다는뜻이다.

화살표는 변경으로부터 보호하려는 컴포넌트를 향하도록 그려진다.

A 컴포넌트에 발생한 변경으로부터 B 컴포넌트를 보호하려면 반드시 A 컴포넌트가 B 컴포넌트에 의존해야 한다.

아키텍트는 기능이 어떻게(How), 왜 (Why), 언제 (When) 발생하는지에 따라서 기능을 분리하고,

분리한 기능을 컴포넌트의 계층구조로 조직화한다.

컴포넌트 계층 구조를 이와 같이 조직화하면

저수준 컴포넌트에서 발생한 변경으로부터 고수준 컴포넌트를 보호할 수 있다.

### 방향성 제어

앞서 설명한 다이어그램은 컴포넌트간 의존성이 제대로 된 방향으로 향하고 있음을 확실히 보여주기 위한 다이어그램이었다.

Gateway 인터페이스는 Generator와 DataMapper 사이에 위치하는데, 이는 **의존성 역전**시키기 위해서다.

Gateway 인터페이스가 없었다면, 의존성이 Intreracotr 컴포넌트에서 Database 컴포넌트로 바로 향하게 된다.

### 정보 은닉

인터페이스는 방향성 제어와는 다른 목적을 가진다.

인터페이스는 Controller가 Interactor 내부에 대해 알지 못하도록 막기 위해서 존재한다.

만약 이 인터페이스가 없었다면, Controller는 추이 종속성을 가지게 된다.

추이 종속성을 가지게 되면, **SW 엔티티는 자신이 직접 사용하지 않는 요소에는 절대 의존해서 안 된다**는 SW 원칙을 위반하게 된다.

이 내용은 인터페이스 분리 원칙(ISP), 공통 재사용 원칙(CRP)을 설명할 때 다시 설명한다.

다시 말해 Controller에서 발생한 변경으로부터 Interactor를 보호하는 일의 우선순위가 가장 높지만,

반대로 Interactor에서 발생한 변경으로부터 Controller도 보호되기를 바란다.

이를 위해 Interactor 내부를 은닉한다.

### 결론

OCP는 시스템의 아키텍처를 떠받치는 원동력 중 하나다.

OCP의 목표는 시스템을 확장하기 쉬운 동시에

변경으로 인해 시스템이 너무 많은 영향을 받지 않도록 하는 데 있다.

이러한 목표를 달성하려면 시스템을 컴포넌트 단위로 분리하고,

저수준 컴포넌트에서 발생한 변경으로부터 고수준 컴포넌트를 보호할 수 있는 형태의

의존성 계층 구조가 만들어지도록 해야 한다.

### OCP 느낀점

SRP 장에서도 느꼈지만, 이번 OCP 챕터에서 OCP 개방 폐쇄 원칙보다 더 많이 나오는 원칙이 있다.

바로 의존성 역전 원칙(DIP)이다.

우선적으로 이런 식으로 OCP를 설명하며 DIP를 설명할 수밖에 없는 이유에 대해서 생각해봤다.

OCP로 확장에 열려있고 변경에 닫혀야 한다는 점을 활용해서

DIP를 해결한다는 점 때문이 아닐까 생각했다.

SRP와 가까운 개념이라고 생각했지만,

OCP와 DIP를 설명하기 가장 좋은 스프링에서의 예제는 Service와 ServiceImpl 구조가 아닐까 싶었다.

단순히 DIP를 해결하기 위해 이렇게 나눈 구조라고 생각했는데,

이 챕터에서 설명하는 내용으로 보았을 때 확장성을 위해서 사용하는 점을 고려했을 때

위에서 말한 Service와 ServiceImpl이 그렇다고 볼 수 있다.

ServiceImpl에서 비즈니스 서비스 로직의 구현체 메서드만 작성하고,

Service에서는 메서드만 정의하는 방식이 

책에서 말하는 OCP와 DIP를 설명하는 가장 좋은 예시라고 볼 수 있었다.

하지만 결국 해결하고자 하는 목표는 DIP이기 때문에 나는 OCP에도 해당하지만,

DIP가 더 맞는 것 같다고 생각은 한다.

좀 더 알맞는 스프링에서의 OCP는 위와 같이 구현체를 구현하면서 의존성 주입을 해결하는 문제가 무엇인지 찾아보았다.

애초 Spring은 의존성 주입을 활용한다. 그리고 객체지향의 다형성을 활용한다.

이러한 점이 새로운 기능을 추가할 때 기존 코드를 변경하지 않고 책에서 설명한 것과 같이 확장성이 높다.

책에서 말하는 컴포넌트와 기능적으로 설명을 해보자면 다음과 같다.

새로운 서비스에 새로운 인증 기능을 추가해야 할 때,

새로운 AuthenticationService 인터페이스를 구현한다.

이 인터페이스를 통해서 새로운 인증 방식을 추가할 수 있다.

또한, 기존 코드를 굳이 수정할 필요 없이 새로운 구현체를 생성하여 연결한다.

즉, 인터페이스를 통해 새로운 구현체를 생성하여 확장에 열려있어야 함을 의미한다.

문제점이 있다.

하지만 위에 예시로 든 인증 기능은 개발자가 직접 Service를 구현한 Class로 구현 객체를 변경하려면 코드를 직접 변경해야 한다.

이 문제점을 통해 다형성을 지켰지만 OCP 원칙을 지키지 못한다.

하지만 Spring을 통해 개발을 하면 스프링 빈 등록과 Spring Container를 통해 위 문제점을 보완하며 OCP 원칙을 지킬 수 있을 것이다.

결제 시스템 또한 인터페이스로 카카오페이, 토스페이, 신용카드 등 구현체를 만든다면 확장성을 위해 연결하는 방식이니 이것 또한 OCP라고 볼 수 있을 것 같다.
