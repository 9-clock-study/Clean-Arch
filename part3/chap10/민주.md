## 10장 ISP : 인터페이스 분리 원칙

다수의 사용자가 OPS 클래스의 오퍼레이션을 사용한다.

User1은 오직 op1을, User2는 op2만을, User3은 op3만을 사용한다 가정해보자.

그리고 OPS가 정적 타입 언어로 작성된 클래스라고 해보자.

이 경우 User1에서는 op2와 op3을 전혀 사용하지 않음에도 User1의 소스 코드는 이 두 메서드에 의존하게 된다. 

이러한 의존성으로 인해 OPS 클래스에서 op2의 소스 코드가 변경되면 User1도 다시 컴파일 한 후 새로 배포해야 한다.

사실 User1과 관련된 코드는 전혀 변경되지 않았음에도 그렇다.

이러한 문제는 오퍼레이션을 인터페이스 단위로 분리하여 해결할 수 있다.

이번에도 마찬가지로 정적 타입 언어로 이 다이어그램을 구현했다 가정하자.

User1의 소스 코드는 U10ps와 op1에는 의존하지만 OPS에는 의존하지 않게 된다.

따라서 OPS에서 발생한 변경이 User1과는 전혀 관계없는 변경이라면,

User1을 다시 컴파일하고 새로 배포하는 상황은 초래되지 않는다.

### ISP와 언어

정적 타입 언어는 사용자가 import, use 또는 include와 같은 타입 선언문을 사용하도록 강제한다.

이처럼 소스 코드에 포함된 선언문을 사용하도록 강제한다.

이처럼 소스 코드에 포함된 선언문으로 인해 소스 코드 의존성이 발생하고,

이로 인해 재컴파일 또는 재배포가 강제되는 상황이 무조건 초래된다.

루비나 파이썬과 같은 동적 타입 언어에서는 소스 코드에 이러한 선언문이 존재하지 않는다.

대신 런타임에 추론이 발생한다.

따라서 소스 코드 의존성이 아예 없으며 결국 재컴파일과 재배포가 필요없다.

동적 타입 언어를 사용하면 정적 타입 언어를 사용할 때보다 유연하며 결합도가 낮은 시스템을 만들 수 있는 이유는 바로 이 떄문이다.

사실 ISP는 아키텍처가 아니라, 언어와 관련된 문제라고 결론내릴 여지가 있다.

### ISP와 아키텍처

한걸음 물러서서 ISP를 사용하는 근본적인 이유를 살펴보면 다음과 같다.

필요 이상으로 많은 것을 포함하는 모듈에 의존하는 것은 해로운 일이다.

소스 코드 의존성의 경우 이는 분명한 사실인데, 불필요한 재컴파일과 재배포를 강제하기 때문이다.

하지만 더 고수준인 아키텍처 수준에서도 마찬가지 상황이 발생한다.

S 시스템 구축에 참여하는 아키텍트가 있다 가정하자.

아키텍트는 F라는 프레임워크를 시스템에 도입하기를 원한다.

그리고 F 프레임워크 개발자는 특정한 D 데이터베이스를 반드시 사용하도록 만들었다 가정하자.

따라서 S는 F에 의존하고, F는 다시 D에 의존한다.

F에서는 불필요한 기능, 따라서 S와 관계 없는 기능은 D에 포함된다 가정하자.

그 기능 때문에 D 내부가 변경된다면 F를 재배포해야 할 수도 있고,

따라서 S까지 재배포해야 할지 모른다.

더 심각한 문제는 D 내부의 기능 중 F와 S에서 불필요한 기능에 문제가 생겨도

F와 S에 영향을 준다는 사실이다.

### 결론

이번 장에서의 교훈은 불필요한 것에 의존하면 예상치도 못한 문제에 빠진다는 사실이다.

차후 13장 컴포넌트 응집도에서 공통 재사용 원칙을 논할 때 자세히 설명하겠다.

### ISP 느낀점

해당 장에서 설명하는 내용이 짧아서인지 크게 와닿지는 않았다.

특히나 SOLID 중에서도 가장 와닿지 않는 원칙이 ISP였는데,

이번 장의 설명이 짧으니 더 그렇게 느껴졌다.

다만, 이번 장의 내용을 보고 확실하게 알게 된 점은 결국 인터페이스를 분리함으로써 좋은 아키텍처를 만든다는 점은 알게 되었다.

특히나 우리는 이번 장에서 ISP에 대해 알아보며 다음과 같은 예시를 보았다.

데이터베이스가 변경되면 스프링 프레임워크를 재배포해야 할 수도 있고,

이러한 경우 소프트웨어를 재배포해야 한다고.

이 예시로는 예를 들어 JPA 환경에서 엔티티에 칼럼을 추가하면

스프링을 재배포하고, 이 경우 소프트웨어를 다시 재배포해야 할 수 있다.

좀 더 구체적인 예제는 다음과 같다.

Spring에서는 인터페이스를 분리하여 해결하는데,

작게 분리하는 것은 클라이언트가 필요로 하는 기능에만 해당하는 작은 인터페이스를 정의하여 사용하는 것을 의미한다.

예를 들어 UserService 인터페이스는 createUser, updateUser와 같은 사용자 관리와 관련된 메서드만 포함한다. 대신 createUser나 updateUser 메서드는 사용자 관리에 필요한 서비스에 의존하고, 다른 기능은 사용하지 않는다.

또한, 앞서 말했던 정적 타입 언어 예시로는 이전에 C로 개발을 했을 때가 생각났다.

특히 게임개발은 C언어 계열의 엔진을 사용하는데,

항상 사소한 변경이 일어나도 새로 재배포를 해야 하는 경우가 많고

심지어 테스트를 하기 위한 그 빌드 과정이 오래 걸리는 게 단점이라고 생각했다.

같은 내용의 이치일지 몰라도 이러한 점이 이번 장에서 설명했던 내용이라고 생각하게 되었다.
