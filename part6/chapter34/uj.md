# Clean Architecture 6부 34장 정리 : 빠져 있는 장

설계와 코드 조직화에 대한 접근법.

아키텍처를 그림으로 잘 그리는 것만으로는 부족함.
실제 코드와 패키지 구조가 아키텍처의 의도를 드러내고, 의존성 규칙을 지킬 수 있어야 함.

### 1. 계층 기반 패키지 (수평 계층형 아키텍처)

웹, 업무 규칙, 영속성 코드 등을 기술적 역할에 따라 수평 계층으로 분리.

예)

- Web
- Service
- Repository

구조가 단순하고 익숙함.

하지만 코드가 커질수록 하나의 기능과 관련된 코드가 여러 패키지에 흩어짐.

또한 계층을 나눴다고 해도 실제 코드에서 의존성을 강제하지 않으면 Web에서 Repository에 직접 접근하는 것도 가능.

즉, **폴더 구조만 계층형일 뿐 실제 아키텍처는 무너질 수 있음.**

---

### 2. 기능 기반 패키지

기술적 역할이 아니라 **기능이나 도메인을 기준으로 코드를 수직적으로 분리**.

예)

- Order
- User
- Product

Order와 관련된 Controller, Service, Repository 등을 하나의 기능 단위로 묶음.

하나의 기능과 관련된 코드가 가까이 위치하기 때문에 코드를 찾고 이해하기 쉬움.

하지만 내부 구조를 제대로 통제하지 않으면 여전히 각 클래스가 서로 자유롭게 접근할 수 있음.

---

### 3. 포트와 어댑터

도메인(내부)과 인프라(외부)를 분리.

내부에는 업무 규칙이 존재하고, 외부에는 Web, DB 등의 기술적 세부사항이 존재.

외부 → 내부 방향으로 의존.

도메인은 Web이나 DB를 몰라야 함.

Port는 내부와 외부가 통신하기 위한 경계.
Adapter는 Web, DB 같은 외부 기술을 Port에 연결하는 구현체.

의존성 규칙을 코드 구조에 적용한 형태.

!! 패키지를 나눴다는 이유만으로 의존성 규칙이 자동으로 지켜지는 것은 아님.

---

### 4. 컴포넌트 기반 패키지

관련된 업무 기능과 해당 기능에 필요한 코드를 **하나의 컴포넌트 단위로 묶음**.

작가의 컴포넌트에 대한 정의 :

> 멋지고 깔끔한 인터페이스로 감싸진 연관된 기능들의 묶음. 애플리케이션과 같은 실행 환경 내부에 존재.

컴포넌트 외부에서는 공개된 인터페이스를 통해서만 접근.

예를 들어 Order 컴포넌트가 있다면 Web에서는 Order 컴포넌트의 인터페이스를 호출.

Web → Order Component

Order Component 내부에는 업무 로직과 영속성 관련 코드가 존재할 수 있음.

하지만 Web이 내부 Repository에 직접 접근할 수 없도록 숨김.

Web → Order Interface → Business Logic → Repository

**접근 가능한 코드 자체를 제한해서 아키텍처 규칙을 강제**.
