# 빠져 있는 장

## 계층 기반 패키지

- 수평 계층형 아키텍처 (가장 단순)

```
layer 1 : xxxContorller

layer 2 : xxxService

layer 3 : repository
```

### 장점

- 처음 시작하기에 가장 적합
- 복잡함을 겪지 않고 무언가를 작동시켜주는 가장 빠른 방법

### 단점

- 소프트웨어가 커질수록 비대해진다.(분리가 필요함)
- 업무 도메인에 대해 아무것도 말해주지 않는다.

## 기능 기반 패키지

- 서로 연관된 기능 , 도메인 개념, 또는 Aggregate Root에 기반해 수직의 얇은 조각으로 코드를 나누는 방식
- 계층 기반 패키지를 리팩터링한 형태

- 코드의 상위 수준 구조가 업무 도메인에 대해 무언가를 알려줌

  > 뭘 알려준다는 건지는 모르겠음 .. 계층 기반에서도 주문 서비스인건 알겠던데..

- 하나의 패키지에 담겨 있어 유스케이스 변경이 용이

## 포트와 어댑터

- 포트와 어댑터, 헥사고날 등의 방식으로 접근하는 이유는 업무/도메인에 초점을 둔 코드가 기술적인 세부 구현과 독립적이며 분리된 아키텍처를 만들기 위함.

- 내부(도메인), 외부(인프라)로 구성됨

```
************************
*          out         *
*  ******************  *
*  *       in       *  *
*  ******************  *
*                      *
************************
```

- **주요규칙** : 외부가 내부에 의존하며 그 반대는 절대 안됨

- 도메인 주도설계: 유비쿼터스 도메인 언어 관점에서 기술

## 컴포넌트 기반 패키지

- 큰 단위의 단일 컴포넌트와 관련된 모든 책임을 하나의 자바 패키지로 묶는 데 주안점을 둠
- 서비스 중심적인 시각(MSA와도 동일)
- 사용자 인터페이스를 큰 단위의 컴포넌트로부터 분리해서 유지

- 이 접근법에서는 업무 로직과 영속성 관련 코드를 하나로 묶음 -> 이를 컴포넌트라 부름

```
컴포넌트는 배포 단위. 컴포넌트는 시스템의 구성 요소로 배포할 수 있는 가장 작은 단위, 자바의 경우 jar
- 밥 삼촌

마틴이형은 좀 다름
컴포넌트는 멋지고 깔끔한 인터페이스로 감싸진 연관된 기능들의 묶음, 애플리케이션과 같은 실행환경 내부에 존재
```

- 컴포넌트 기반 패키지의 주된 이점 : xxx와 관련된 무언가를 코딩해야될 때 오직 한 곳 xxxComponents만 건들면된다는 것.
